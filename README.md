# 容量评估：架构师必须补上的一门工程课

所谓容量评估，本质上不是问“系统能扛多少 QPS”，而是问一个更根本的问题：这个系统在未来某个规模下，是否还能以可接受的成本、可接受的稳定性、可接受的用户体验继续运行。

很多工程师在职业早期并不太关心这个问题。因为在用户量小的时候，系统的很多问题都会被机器性能掩盖。代码写得粗糙一点，数据库查询慢一点，Redis 用得随意一点，日志打得多一点，似乎都没有什么严重后果。

但是，当一个系统从几千用户走向几十万用户、几百万用户，事情就变了。你会发现，原来软件系统并不是一个抽象的逻辑世界，它最终要落在 CPU、内存、磁盘、网络、数据库连接、GPU 显存、云账单这些非常具体的东西上。

这就是容量评估的意义。

它不是一门玄学，也不是资深工程师靠经验拍脑袋的艺术。归根结底，它是一套工程方法论：先建立用户行为模型，再推导资源消耗，再找到瓶颈，再设计扩容和降级方案，最后把成本也算清楚。

## 一、什么是容量评估

容量评估，英文叫 Capacity Planning。简单讲，就是预测系统未来的资源消耗，并提前设计系统的承载能力。

这里有几个关键词。

第一，预测。容量评估不是系统已经崩了以后再去救火，而是在系统还没有达到那个规模之前，就大致知道它会在哪里出问题。

第二，资源消耗。一个系统消耗的不是一个单一资源，而是一组资源：CPU、内存、磁盘、网络、数据库、缓存、消息队列、对象存储、GPU、第三方 API 调用次数，以及云成本。

第三，承载能力。容量不是越大越好。一个系统当然可以通过多买机器来提高承载能力，但如果每增长一倍用户，成本就增长三倍，这个系统在商业上也是不可持续的。

因此，容量评估的核心目标可以概括为六个字：不崩、不浪费。

展开讲，它包括：

| 目标 | 含义 |
| --- | --- |
| 不崩 | 流量上涨时系统不会直接不可用 |
| 不浪费 | 不盲目购买机器和云资源 |
| 可扩展 | 后续可以平滑扩容 |
| 可预测 | 知道什么时候会出现风险 |
| 可量化 | 用数据而不是感觉做决策 |
| 可预算 | 能提前估算成本和毛利空间 |

很多公司早期靠“先上线再说”活下来，到了中后期却会被“先扩容再说”拖垮。前者是创业速度问题，后者是工程成熟度问题。

## 二、为什么很多工程师不懂容量评估

这里有一个很常见的误解：很多人以为容量评估就是 TPS 或 QPS。

这是不够的。

QPS 只是系统容量的一个入口指标，就像体温只是健康指标之一。一个人发烧可能是感冒，也可能是感染；一个系统 QPS 高，也可能真正的瓶颈在数据库、Redis、网络带宽、磁盘 IO、线程池、GC，甚至云厂商的 egress cost。

我在技术史中反复看到一个规律：真正决定系统规模的，往往不是最显眼的那个指标，而是最容易被忽略的底层约束。

早期的互联网公司做搜索，看起来竞争的是搜索算法，实际上背后还要竞争网页抓取能力、索引构建能力、分布式存储能力、数据中心能力和成本控制能力。Google 之所以能够把搜索做成全球级系统，并不只是因为 PageRank 这个算法，而是因为它把大规模计算、大规模存储和工程成本控制变成了一整套体系。

今天我们做 Web 系统、实时语音系统、AI 应用，也是同样的道理。表面上看是产品功能，底层看是资源模型。

容量评估，就是把这个资源模型看清楚。

## 三、容量评估到底评估什么

一个成熟系统的容量评估，至少要看九类容量。

### 1. 流量容量：系统入口有多大

流量容量是最容易被理解的部分，也是容量评估的起点。

常见指标包括：

| 指标 | 含义 |
| --- | --- |
| QPS | 每秒查询数 |
| TPS | 每秒事务数 |
| RPS | 每秒请求数 |
| DAU | 日活用户 |
| MAU | 月活用户 |
| CCU | 同时在线人数 |
| Peak Traffic | 峰值流量 |
| Average Traffic | 平均流量 |
| Burst Traffic | 突发流量 |

新手最容易犯的错误，是把 DAU 直接当成并发量。

比如，一个产品有 100 万 DAU，并不表示有 100 万人同时在线。真正要看的是高峰时段有多少用户活跃，以及每个用户在这个时段会产生多少请求。

举一个简单例子：

假设一个系统有 100 万 DAU，其中 20% 的用户会在晚高峰活跃。每个活跃用户平均每分钟发起 5 次请求。那么峰值 QPS 大约是：

```text
QPS = 1000000 × 20% × 5 ÷ 60
    ≈ 16666
```

这个数字虽然粗糙，但已经比“我们有 100 万用户，所以要按 100 万并发设计”可靠得多。

容量评估最重要的第一步，就是不要直接从用户数跳到机器数，而要经过中间的用户行为模型。

用户数只是人口规模，请求才是真正落到服务器上的负载。

### 2. 存储容量：数据会不会把系统拖垮

很多系统不是被流量打死的，而是被数据量拖死的。

流量问题通常来得急，容易被发现；存储问题来得慢，容易被忽视。等到数据库磁盘满了、Redis 内存爆了、Kafka Topic 堆积了、ClickHouse Merge 跑不动了，团队才意识到自己从来没有认真算过数据增长。

存储容量需要评估这些维度：

| 维度 | 例子 |
| --- | --- |
| 每日新增数据 | 每天新增多少订单、日志、消息、文件 |
| 总存储量 | GB、TB、PB |
| 热数据 | 最近 7 天、30 天的高频访问数据 |
| 冷数据 | 历史归档数据 |
| 索引大小 | MySQL 二级索引、全文索引 |
| 日志容量 | ELK、ClickHouse、对象存储日志 |
| 对象存储 | 图片、音频、视频、附件 |
| 备份容量 | 全量备份、增量备份 |
| 副本数量 | 主从、三副本、跨机房复制 |

一个很实用的估算方法是：

```text
总容量 = 每条数据大小 × 每日新增条数 × 保留天数 × 副本系数 × 索引膨胀系数
```

比如，一条日志平均 2KB，每天 10 亿条，保留 30 天，三副本，索引和压缩后按 1.5 倍计算：

```text
2KB × 10亿 × 30 × 3 × 1.5
≈ 270TB
```

这时你就会发现，日志不是免费的。很多公司云账单里增长最快的部分，不是业务数据库，而是日志、监控和链路追踪数据。

新手要养成一个习惯：凡是会持续增长的东西，都要问三个问题。

第一，每天增长多少？

第二，保留多久？

第三，谁来清理？

没有清理策略的数据，迟早会变成事故。

### 3. 计算容量：CPU 到底够不够

计算容量主要看 CPU 或 GPU 是否足够处理业务逻辑。

不同系统的计算特征不同：

| 类型 | 例子 |
| --- | --- |
| CPU 密集型 | 视频编码、加密、压缩、复杂计算 |
| IO 密集型 | 数据库读写、文件读写 |
| 内存密集型 | Redis、实时分析 |
| GPU 密集型 | AI 推理、模型训练 |
| 网络密集型 | 网关、代理、音视频传输 |

很多初学者看 CPU，只看利用率。例如 CPU 使用率 80%，就认为 CPU 快满了。事实上，CPU 分析要细得多。

你至少需要理解：

| 指标 | 含义 |
| --- | --- |
| CPU Load | 运行队列压力，不等于 CPU 使用率 |
| User CPU | 用户态代码消耗 |
| System CPU | 内核态消耗 |
| Context Switch | 上下文切换次数 |
| Run Queue | 等待运行的线程队列 |
| Cache Miss | CPU 缓存未命中 |
| GC Stop The World | 垃圾回收暂停 |
| Thread Pool Saturation | 线程池饱和 |
| Goroutine Scheduling | Go 程序调度开销 |

举个例子，一个 Java 服务 CPU 很高，可能不是业务计算真的复杂，而是对象创建太多导致 GC 频繁。一个 Go 服务延迟上升，可能不是 CPU 不够，而是 goroutine 太多、锁竞争严重或者网络调用阻塞。

容量评估不是看到 CPU 高就加机器，而是要知道 CPU 为什么高。

这就是高级工程师和普通工程师的区别。

### 4. 内存容量：系统最容易被忽视的风险

很多系统崩溃，不是 CPU 不够，而是内存出了问题。

内存问题通常有几种：

| 问题 | 表现 |
| --- | --- |
| 内存泄漏 | 内存持续上涨，不回落 |
| GC 压力 | 延迟抖动，P99 飙升 |
| Cache 失控 | 缓存越积越大 |
| 大对象 | 一次请求占用大量内存 |
| Swap | 系统变慢，延迟不可控 |
| OOM Killer | 进程被 Linux 杀掉 |
| 内存碎片 | 看似有内存，实际不可用 |

对 Java 程序，要理解 JVM Heap、Young GC、Old GC、Full GC。对 Go 程序，要理解 Go Heap、GC Pace、对象逃逸。对 Linux 进程，要看 RSS，而不是只看语言运行时内部的内存统计。

很多线上事故的路径非常相似：

```text
流量上涨
→ 对象创建增加
→ GC 压力增大
→ 请求变慢
→ 请求堆积
→ 内存继续上涨
→ OOM
→ 服务重启
→ 流量打到剩余节点
→ 连锁故障
```

这类事故看起来是内存问题，实际上是容量模型没有设计好。

### 5. 网络容量：开发者最容易低估的瓶颈

很多开发者习惯把网络当成透明的东西，好像请求发出去就自然会回来。到了大规模系统里，网络本身就是核心资源。

你需要理解：

| 内容 | 含义 |
| --- | --- |
| 带宽 | Mbps、Gbps |
| RTT | 网络往返延迟 |
| TCP 连接数 | 长连接和短连接压力 |
| WebSocket | 长连接容量 |
| Connection Pool | 连接池大小 |
| SYN Flood | 半连接攻击或异常流量 |
| NIC 吞吐 | 网卡能力 |
| CDN 回源 | 源站压力 |
| Egress Cost | 云厂商出网费用 |

特别是 AI 系统和实时语音系统，网络容量往往比传统 Web 更重要。

比如语音流式系统，每个用户不是发一个 HTTP 请求就结束，而是持续上传音频流，同时接收识别结果或模型输出。这里要评估的不只是 QPS，而是同时连接数、单连接带宽、心跳频率、断线重连、backpressure 和网关连接状态管理。

一个简单估算是：

```text
总带宽 = 同时在线连接数 × 单连接平均带宽
```

如果 5 万个用户同时进行语音流式输入，每个连接平均上行 32kbps，那么仅上行带宽就是：

```text
50000 × 32kbps = 1.6Gbps
```

这还没有算协议开销、下行数据、TLS、重传和峰值波动。

所以，实时系统的容量评估不能只看请求数，要看连接数和持续流量。

### 6. 数据库容量：架构师的基本功

数据库容量是架构师绕不开的能力。

需要评估的内容包括：

| 内容 | 说明 |
| --- | --- |
| 单表容量 | 一张表能承受多少行 |
| 索引容量 | 索引占多少空间 |
| Buffer Pool | 热数据是否能放进内存 |
| 连接数 | 数据库连接是否耗尽 |
| 慢查询 | 是否拖垮整体系统 |
| 主从延迟 | 读写分离是否可靠 |
| WAL/Redo Log | 写入日志压力 |
| Binlog | 同步和备份压力 |
| 热点数据 | 单行、单分片是否过热 |
| 分库分表 | 横向扩展能力 |

一个常见错误是只看表里的数据大小，不看索引大小。很多 MySQL 表，索引占用空间比数据本身还大。查询性能也不是由“表有多大”单独决定，而是由查询模式、索引设计、Buffer Pool 命中率、磁盘 IO 和锁冲突共同决定。

数据库容量评估至少要回答几个问题：

1. 单表数据一年后有多少行？
2. 主要查询是否都能走索引？
3. 热数据能否放进 Buffer Pool？
4. 写入峰值会不会拖慢主从复制？
5. 如果单库撑不住，按什么维度拆分？
6. 拆分以后，跨分片查询怎么办？

很多团队直到数据库已经撑不住了才开始分库分表，这是非常痛苦的。因为数据拆分不是简单把表切开，它会改变查询、事务、排序、分页、统计、数据修复和运维方式。

容量规划的价值，就是让这些决定提前发生。

### 7. 缓存容量：Redis 不是无限内存

很多大型系统，本质上是数据库系统加 Redis 系统。

Redis 很快，但它并不神奇。Redis 的容量问题通常集中在几个方面：

| 内容 | 说明 |
| --- | --- |
| Key 数量 | 总共有多少 Key |
| Value 大小 | 每个 Key 平均多大 |
| 热 Key | 某个 Key 被极高频访问 |
| 大 Key | 单个 Key 过大，阻塞 Redis |
| 命中率 | 缓存是否真的减少数据库压力 |
| 淘汰策略 | 内存满了以后怎么处理 |
| 内存碎片率 | 实际占用大于逻辑数据 |
| 持久化开销 | RDB、AOF 带来的额外压力 |
| 网络 IO | Redis 吞吐也受网络影响 |

Redis 容量估算可以从一个简单公式开始：

```text
Redis 内存 ≈ Key 数量 × 平均 Key/Value 大小 × 编码开销 × 冗余系数
```

例如 1000 万个 Key，每个 Value 平均 1KB，不考虑其他开销就是 10GB。但 Redis 有对象头、字典、过期时间、内存分配器碎片等额外开销，实际可能需要 20GB 甚至更多。

新手还要特别警惕两个问题：热 Key 和大 Key。

热 Key 会导致 Redis Cluster 中某个节点压力极高，其他节点却很空。大 Key 会导致单次操作阻塞 Redis 主线程，引发延迟抖动。

缓存系统看似简单，实际上是容量规划里最容易隐藏风险的部分。

### 8. 消息队列容量：积压不是暂时现象

Kafka、RabbitMQ 这类消息队列，常常被用来削峰填谷。但如果没有容量评估，消息队列也会变成事故放大器。

需要评估：

| 内容 | 说明 |
| --- | --- |
| Topic 分区数 | 决定并发消费能力 |
| 生产速度 | 每秒写入多少消息 |
| 消费速度 | 每秒处理多少消息 |
| 积压容量 | 最坏情况下能堆多少 |
| Retention | 消息保留多久 |
| 副本数 | 数据可靠性与磁盘成本 |
| Broker 容量 | CPU、磁盘、网络 |
| 磁盘吞吐 | 顺序写和读放大 |

消息队列的核心公式很简单：

```text
积压增长速度 = 生产速度 - 消费速度
```

如果生产速度是每秒 10 万条，消费速度是每秒 7 万条，那么每秒积压 3 万条。看起来一分钟只是 180 万条，但持续一小时就是 1.08 亿条。

队列积压不是一个静态问题，而是一个时间函数。只要消费速度长期低于生产速度，系统迟早会崩。

### 9. AI 系统容量：新的瓶颈模型

如果说传统 Web 系统的核心指标是 QPS，那么 AI 推理系统的核心指标就变成了 Token。

AI 系统和传统系统最大的不同是：请求之间差异巨大。

一个普通 HTTP 请求可能几十毫秒结束，而一个 LLM 请求可能持续几十秒；一个用户输入 200 个 token，另一个用户可能输入 10 万 token；有的请求只生成一句话，有的请求要生成几千字。

因此 AI 系统容量要评估这些指标：

| 维度 | 说明 |
| --- | --- |
| Token 吞吐 | 每秒处理多少输入和输出 token |
| GPU 显存 | 模型权重、KV Cache、batch 占用 |
| Context 长度 | 8k、32k、128k 带来不同成本 |
| 并发生成数 | 同时有多少请求在生成 |
| Batch Size | 批处理大小影响吞吐和延迟 |
| KV Cache | 长上下文推理的重要成本 |
| 模型加载时间 | 冷启动和切换模型成本 |
| GPU 利用率 | GPU 是否真正被用满 |
| Streaming | 流式输出体验 |
| TTFT | Time To First Token |
| TPOT | Time Per Output Token |

AI 系统最重要的指标包括：

| 指标 | 含义 |
| --- | --- |
| TTFT | 用户多久看到第一个 token |
| TPOT | 每生成一个 token 需要多久 |
| Tokens/s | 单卡或集群吞吐 |
| Context Window | 上下文窗口大小 |
| KV Cache 命中率 | 复用上下文的能力 |
| GPU Occupancy | GPU 利用率 |

比如，一个模型单卡可以生成 100 tokens/s。如果平均每个请求生成 500 tokens，那么理想情况下每秒只能完成 0.2 个请求。也就是说，它的 QPS 不是由 HTTP 网关决定的，而是由 token 生成速度决定的。

这也是为什么 AI 产品必须做成本模型。

传统 SaaS 的边际成本可能很低，但 AI 产品每一次生成都在消耗真实的 GPU 时间或 API token。用户越活跃，成本越高。如果没有配额、缓存、模型路由、batching 和降级策略，产品越成功，亏损可能越严重。

## 四、真正高级的容量评估能力

前面讲的是“评估什么”。接下来要讲“怎么评估”。

新手容易从组件出发：MySQL 怎么优化，Redis 怎么扩容，Kafka 怎么调参数。高级工程师会从用户行为出发。

这两者的差别很大。

### 1. 建立用户行为模型

容量评估的第一步，不是算机器，而是画出用户行为链路。

例如，一个实时语音 AI 产品，用户按下快捷键开始输入：

```text
按下 Fn
→ 建立 WebSocket 连接
→ 上传音频流
→ 实时 ASR
→ LLM 后处理
→ 流式返回结果
→ 客户端展示
→ 写入会话记录
```

每个环节都会消耗资源：

| 环节 | 资源消耗 |
| --- | --- |
| WebSocket | 长连接、内存、网关连接数 |
| 音频流 | 上行带宽、包处理 |
| ASR | CPU/GPU、推理延迟 |
| LLM | token、GPU 显存、KV Cache |
| 后处理 | CPU、规则引擎 |
| Redis Session | 内存、过期策略 |
| 数据库存储 | 写入、索引、归档 |
| 日志监控 | 存储、查询、成本 |

这才是容量评估的正确入口。

用户不是抽象的 DAU，而是一组行为。行为不是抽象的请求，而是一条资源消耗链路。

### 2. 找到真正的瓶颈

瓶颈定位是容量评估中最能拉开差距的能力。

普通工程师看到系统慢，会说：“CPU 高了，加机器吧。”

高级工程师会问：

1. CPU 高是用户态还是内核态？
2. 是业务计算、GC、序列化、加密，还是日志？
3. 是所有节点都高，还是某几个节点高？
4. 增加机器后，瓶颈是否会转移到数据库？
5. 如果 QPS 翻倍，哪个资源先到上限？
6. 扩容是否线性有效？

系统瓶颈通常遵循木桶原理。最短的木板可能是数据库连接数，也可能是 Redis 热 Key，也可能是 Kafka 分区数，也可能是 GPU KV Cache，也可能是云厂商带宽上限。

容量评估要做的，就是在事故发生之前找到那块短板。

### 3. 建立压测体系

没有压测的容量评估，大概率只是猜测。

常见压测工具包括：

| 工具 | 用途 |
| --- | --- |
| wrk | HTTP 高性能压测 |
| k6 | 现代压测脚本，适合场景化测试 |
| JMeter | 企业传统压测 |
| Locust | Python 用户行为模拟 |
| vegeta | Go 生态常用压测 |
| hey | 简单 HTTP 压测 |

压测也有不同类型：

| 类型 | 目的 |
| --- | --- |
| 阶梯压测 | 逐步增加流量，找到拐点 |
| 峰值压测 | 验证系统能否扛住峰值 |
| 稳定性压测 | 长时间运行，观察泄漏和抖动 |
| 故障压测 | 模拟依赖异常 |
| 混沌工程 | 验证系统在故障下的韧性 |

一份好的压测报告，不应该只写“系统能扛 2 万 QPS”。它至少要包括：

1. 测试场景是什么？
2. 用户行为是否真实？
3. 请求比例是否接近线上？
4. P50、P95、P99 延迟是多少？
5. CPU、内存、网络、磁盘分别如何变化？
6. 数据库和缓存是否出现瓶颈？
7. 系统拐点在哪里？
8. 继续扩容是否线性有效？
9. 失败模式是什么？

很多压测看起来很专业，实际上没什么价值。因为它只压了一个接口，而且请求数据完全一样，缓存命中率接近 100%。这类压测测到的不是系统能力，而是缓存能力。

### 4. 把成本纳入容量评估

高级架构师不只是让系统扛得住，还要让公司扛得起。

云时代有一个特点：扩容变得非常容易，浪费也变得非常容易。

你需要评估：

| 成本项 | 说明 |
| --- | --- |
| 计算成本 | ECS、容器、Kubernetes 节点 |
| GPU 成本 | AI 系统核心成本 |
| 存储成本 | 数据库、对象存储、快照 |
| 带宽成本 | 出网流量常常很贵 |
| CDN 成本 | 分发和回源 |
| Redis 成本 | 高规格内存实例昂贵 |
| ClickHouse 成本 | 日志和分析数据膨胀 |
| 第三方 API | 按调用或 token 收费 |
| 监控日志 | 容易被低估 |

AI 产品尤其如此。

比如你做一个 AI 写作或语音产品，每个用户每天消耗 5 万 token。如果有 10 万日活，就是每天 50 亿 token。哪怕每百万 token 成本很低，总量上来以后也是很大的支出。

因此 AI 产品从第一天起就要有成本模型：

```text
单用户日成本 = 输入 token 成本 + 输出 token 成本 + ASR 成本 + 存储成本 + 带宽成本
```

再进一步：

```text
毛利 = 用户收入 - 单用户资源成本 - 基础设施摊销 - 第三方服务成本
```

没有成本模型的 AI 产品，就像没有仪表盘的飞机，飞得越快，风险越大。

### 5. 理解 SLA、SLO 和 Error Budget

现代系统不能只说“尽量稳定”。稳定性也要量化。

三个概念很重要：

| 概念 | 含义 |
| --- | --- |
| SLA | 对客户或用户的承诺 |
| SLO | 团队内部设定的稳定性目标 |
| SLI | 用来衡量目标的指标 |
| Error Budget | 可容忍的失败额度 |

比如，一个系统的 SLO 是 99.9% 可用性。一个月大约 30 天，也就是 43200 分钟。99.9% 可用意味着每月最多不可用约 43.2 分钟。

这个 43.2 分钟就是错误预算的一部分。

它的意义在于：稳定性不是绝对的，也不是越高越好。99.999% 可用性当然很好，但成本可能极高。工程的本质就是在目标、成本和约束之间做理性选择。

## 五、不同阶段的工程师应该达到什么水平

容量评估能力，实际上也是工程师成长层次的分水岭。

### 初级工程师

初级工程师主要关注功能是否能跑通。

这个阶段最重要的是写出正确代码，理解基本的 HTTP、数据库、缓存和日志。至于系统什么时候会崩，通常还没有直觉。

这并不丢人。每个人都要从这里开始。

### 中级工程师

中级工程师开始知道一些系统风险：

1. Redis 可能会爆内存。
2. MySQL 查询可能会变慢。
3. 接口可能会超时。
4. 服务需要限流和重试。
5. 慢查询需要加索引。

这个阶段能做局部优化，但通常还缺少全局容量模型。

### 高级开发者

高级开发者必须能做基本估算：

1. 一个功能上线后大概带来多少 QPS。
2. Redis 需要多少内存。
3. MySQL 表一年后有多大。
4. 日志一天会产生多少。
5. 带宽峰值是多少。
6. P99 延迟为什么上升。
7. 压测结果是否可信。

高级开发者还要能定位瓶颈，而不是只会加机器。

### 架构师

架构师要看得更远。

他要能做未来 1 到 3 年容量规划，设计多机房架构，规划成本，设计扩容方案、降级方案和灾难恢复方案。

架构师关心的不只是“今天系统能不能跑”，而是“系统增长十倍后，架构还是否成立”。

### SRE / 运维负责人

SRE 更关注系统运行状态和自动化能力。

他需要建立监控体系、告警体系、自动扩缩容体系、容量预测体系和故障演练机制。在 Kubernetes 环境下，还要理解节点资源调度、Pod request/limit、HPA、VPA、Cluster Autoscaler 等能力。

开发者负责把系统造出来，SRE 负责让系统长期可靠地活着。

## 六、推荐学习路线

容量评估不是一门孤立的课，它建立在计算机系统、网络、数据库、性能分析和分布式系统之上。

学习顺序很重要。很多人一上来就学 Kubernetes、Kafka、微服务，其实是倒过来了。底层资源都不理解，学再多框架也只是知道一些名词。

### 第一阶段：计算机资源基础

先学 Linux 和操作系统资源。

必须理解：

1. CPU Load
2. Memory
3. IO
4. Network
5. epoll
6. 文件系统
7. Page Cache
8. mmap
9. 零拷贝
10. 进程、线程、上下文切换

推荐读：

1. 《性能之巅》
2. 《Systems Performance》
3. 《深入理解 Linux 内核》

这一阶段的目标不是背命令，而是建立资源直觉。你要知道一个请求进入服务器后，经历了哪些内核和用户态过程。

### 第二阶段：网络基础

网络是分布式系统的地基。

必须掌握：

1. TCP/IP
2. HTTP/1.1、HTTP/2、HTTP/3
3. 长连接
4. WebSocket
5. QUIC
6. CDN
7. DNS
8. TLS
9. 连接池
10. 超时、重试、限流

做实时语音和 AI 流式产品的人，尤其要重视 WebSocket、HTTP/2 streaming、网络抖动、backpressure 和断线重连。

### 第三阶段：数据库容量

这一阶段重点学 MySQL、Redis 和 Kafka。

MySQL 要理解：

1. B+ 树索引
2. Buffer Pool
3. 事务隔离级别
4. MVCC
5. Redo Log
6. Binlog
7. 慢查询
8. 主从复制
9. 分库分表

Redis 要理解：

1. 单线程模型
2. 数据结构
3. 内存开销
4. 淘汰策略
5. RDB/AOF
6. Cluster
7. 热 Key 和大 Key

Kafka 要理解：

1. Topic
2. Partition
3. Consumer Group
4. Offset
5. Retention
6. 副本
7. 顺序写
8. 消费积压

### 第四阶段：性能分析

性能分析是把“感觉”变成“证据”的工具。

必须掌握：

1. flame graph
2. pprof
3. perf
4. tracing
5. eBPF
6. APM
7. 慢日志
8. 系统指标关联分析

看到延迟升高时，不要急着改代码。先把证据链建立起来：请求在哪个阶段耗时，哪个函数占 CPU，哪个依赖变慢，哪个资源接近上限。

### 第五阶段：压测体系

这一阶段学习如何设计真实压测。

工具可以从 k6 和 wrk 开始。k6 适合写用户场景，wrk 适合压 HTTP 极限。

你要学会写压测报告，而不只是跑一个命令。

好的压测报告应该告诉团队：系统当前容量是多少，瓶颈是什么，扩容方式是否有效，继续增长会在哪里出问题。

### 第六阶段：分布式系统容量

当单机资源不够时，就进入分布式系统。

必须理解：

1. CAP
2. 一致性
3. 分片
4. 复制
5. 服务发现
6. Service Mesh
7. Kubernetes
8. Elastic Scaling
9. 限流降级
10. 多机房灾备

这一阶段最重要的认识是：分布式系统不是免费午餐。它解决单机容量问题，同时引入一致性、网络分区、运维复杂度和故障传播问题。

### 第七阶段：AI 系统容量

如果你现在做 AI 产品，这一阶段非常重要。

需要重点学习：

1. vLLM
2. TensorRT-LLM
3. Ollama
4. KV Cache
5. Continuous Batching
6. Batch Scheduling
7. CUDA 基础
8. GPU 显存计算
9. Tensor Parallel
10. Pipeline Parallel
11. TTFT、TPOT、Tokens/s

AI 推理容量将是未来几年非常值钱的工程能力。因为它同时涉及模型、系统、GPU、成本和用户体验。

## 七、结合 Typeflux，最值得优先学习什么

如果你现在做的是 Typeflux 这样的产品，涉及语音流式、AI 推理、macOS 客户端和云端 API，那么我认为优先级应该很清楚。

### 第一，AI 推理容量

这是最核心的成本和体验来源。

你要知道：

1. 每个用户平均消耗多少 token。
2. 峰值时有多少并发生成。
3. TTFT 是否足够低。
4. TPOT 是否稳定。
5. GPU 利用率是否健康。
6. 长上下文是否导致 KV Cache 膨胀。
7. 哪些场景可以用小模型。
8. 哪些请求可以缓存。
9. 哪些用户需要配额。
10. 如何做模型路由。

AI 产品最怕的是技术上能跑，商业上跑不动。

### 第二，WebSocket 长连接容量

实时语音依赖长连接和流式传输。

你要重点关注：

1. 单机最大连接数。
2. 每个连接占用多少内存。
3. 心跳频率。
4. 断线重连策略。
5. backpressure。
6. 网关是否支持水平扩展。
7. 连接状态是否能迁移。
8. 流量突增时如何限流。
9. 客户端弱网环境如何处理。

长连接系统和普通 HTTP 系统不同。HTTP 请求结束后连接可以释放，而 WebSocket 会长时间占用服务器资源。

### 第三，Redis 和 Kafka

实时 AI 系统发展到一定阶段，通常会需要状态管理和异步处理。

Redis 可能用于：

1. Session 状态。
2. 用户配额。
3. 热数据缓存。
4. 分布式锁。
5. 临时上下文。
6. 速率限制。

Kafka 或其他消息队列可能用于：

1. 音频任务异步处理。
2. 日志采集。
3. 事件流。
4. 用户行为分析。
5. 模型调用记录。
6. 后台批处理。

这些组件一旦进入核心链路，就必须有容量规划。

### 第四，成本优化

AI 产品最难的不是把功能做出来，而是把单位经济模型做成立。

你需要建立：

```text
用户请求
→ token 消耗
→ GPU/API 成本
→ 存储和带宽成本
→ 用户收入
→ 毛利
```

然后围绕这个模型优化：

1. batching
2. cache
3. 小模型优先
4. 模型路由
5. 用户配额
6. 上下文裁剪
7. 摘要压缩
8. 异步降级
9. 免费用户限制
10. 高级用户差异化

这不是单纯的技术优化，而是产品、工程和商业的交汇点。

## 八、最有效的实践方式

容量评估不能只靠看书。你必须做实验。

### 项目 1：压测自己的 API

用 wrk 或 k6 压测一个真实接口。

观察：

1. QPS
2. P50、P95、P99
3. CPU
4. 内存
5. 数据库连接
6. Redis 命中率
7. 错误率

然后逐步增加并发，找到系统拐点。

### 项目 2：做 Redis 容量实验

自己构造：

1. 100 万 Key
2. 1000 万 Key
3. 大 Key
4. 热 Key
5. 不同淘汰策略
6. RDB/AOF 开启和关闭

观察内存、延迟和阻塞情况。

这个实验做完，你对 Redis 的理解会比只看文档深很多。

### 项目 3：做 WebSocket 长连接实验

搭一个简单 WebSocket 服务，测试：

1. 1 万连接
2. 5 万连接
3. 心跳
4. 弱网断开
5. 重连
6. 服务端广播
7. 单连接内存占用
8. 网关 CPU 和带宽

实时系统的很多问题，只有在长连接规模上来后才会暴露。

### 项目 4：做 AI 推理容量实验

选择 Qwen、Llama 或其他开源模型，用 vLLM 或 Ollama 做实验。

观察：

1. tokens/s
2. TTFT
3. TPOT
4. GPU 显存
5. batch size
6. context length
7. 并发请求
8. 流式输出体验

你会发现，AI 推理系统的容量不是一个固定数字，而是一组变量之间的平衡。

## 九、最终要形成的思维方式

真正高级的工程师，脑子里会自动形成一条链路：

```text
用户规模
→ 用户行为模型
→ 请求链路
→ 资源消耗
→ 系统瓶颈
→ 扩容方案
→ 成本模型
→ 风险模型
```

这条链路，就是架构能力的核心。

很多人以为架构师的能力是会画复杂的架构图，会说很多分布式系统名词。其实不是。架构师最重要的能力，是在系统还没有变复杂之前，就能看见它未来会在哪里变复杂；在事故还没有发生之前，就知道它大概率会以什么方式发生；在公司还没有花冤枉钱之前，就知道哪些资源值得买，哪些资源不值得买。

容量评估就是这种能力的训练场。

它要求你既懂代码，又懂系统；既懂技术，又懂成本；既能看今天的指标，又能推演未来的增长。

说到底，容量评估不是一门“运维课”，而是一门“工程判断课”。它训练的不是某个工具的使用，而是你对系统边界、增长规律和资源约束的理解。

当你能从一个产品功能，推导出它的流量、存储、计算、网络、数据库、缓存、消息队列、AI 推理和成本模型时，你就不再只是一个写功能的开发者，而开始真正进入架构师的世界。
