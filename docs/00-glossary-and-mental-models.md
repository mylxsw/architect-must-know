# 预备章 先把容量评估里的专业词讲清楚

初学容量评估，最难的不是公式，而是术语。很多文章一上来就说 QPS、P99、CPU Load、Buffer Pool、GC、KV Cache、Error Budget，初学者看似读懂了，真正做事时却不知道这些词和自己的系统有什么关系。

所谓专业能力，本质上是能把抽象词汇还原成真实世界里的现象。你看到 P99，不只是知道它叫 99 分位延迟，而是能想到：是不是有一批用户正在变慢，线程池是不是被占住，下游是不是偶发抖动。你看到 Buffer Pool，不只是知道它是 MySQL 的缓存，而是能想到：热数据是否放得下，查询是不是开始读磁盘。

这一章先把常用词讲清楚。后面的章节再谈方法，就不会悬在空中。

## 1. 流量类术语

### QPS、RPS、TPS 到底有什么区别

这三个词经常混用，但它们的侧重点不同。

| 术语 | 全称 | 白话解释 | 常见场景 |
| --- | --- | --- | --- |
| QPS | Queries Per Second | 每秒查询数 | 搜索、读接口、数据库查询 |
| RPS | Requests Per Second | 每秒请求数 | HTTP API、网关 |
| TPS | Transactions Per Second | 每秒事务数 | 下单、支付、数据库事务 |

如果一个接口只是查商品详情，通常说 QPS 或 RPS 都可以。如果一个接口会创建订单、扣库存、写交易记录，叫 TPS 更贴切，因为它强调“事务”。

初学者可以先这样记：

```text
RPS 看入口请求
QPS 看查询压力
TPS 看业务事务
```

真正做容量评估时，不要纠结名字，而要问：这个数字背后会落到哪些资源上。

比如 1000 RPS 的登录接口，可能每秒产生 1000 次密码校验、1000 次 Redis 查询、1000 次数据库读、1000 条登录日志。入口只有一个数字，资源消耗却是一串。

### DAU、MAU、CCU 为什么不能混用

| 术语 | 白话解释 | 关键点 |
| --- | --- | --- |
| DAU | 一天来过多少用户 | 不是同时在线 |
| MAU | 一个月来过多少用户 | 更偏产品规模 |
| CCU | 同时在线用户数 | 更接近容量压力 |

很多初学者会把“100 万 DAU”理解成“100 万并发”。这是严重误解。

一个有 100 万 DAU 的产品，可能晚高峰只有 5 万人同时活跃；也可能因为活动推送，短时间有 30 万人涌入。**容量评估要关心的是流量如何在时间上分布。**

一个常用估算是：

```text
峰值并发 ≈ DAU × 高峰活跃比例 × 平均使用时长(分钟) ÷ 高峰窗口时长(分钟)
```

假设 100 万 DAU，20% 用户在晚高峰活跃，平均每次使用 10 分钟，高峰窗口 2 小时（120 分钟）：

```text
峰值并发 ≈ 1000000 × 20% × 10 ÷ 120
        ≈ 16667
```

这个公式的逻辑是：高峰期有 20 万人会来，每人停留 10 分钟，而高峰窗口有 120 分钟，所以任意时刻大约有 20 万 × (10/120) ≈ 1.67 万人同时在线。

这个数字不精确，但比拍脑袋可靠。**工程上很多事情不需要一开始就精确，需要先有量级判断。**

## 2. 延迟类术语

### 平均延迟为什么会骗人

平均延迟是所有请求耗时加起来除以请求数。它容易理解，但很容易骗人。

假设有 100 个请求：

```text
99 个请求耗时 20ms
1 个请求耗时 8000ms
```

平均延迟：

```text
(99 × 20 + 1 × 8000) ÷ 100 = (1980 + 8000) ÷ 100 = 99.8ms
```

看起来不到 100ms，好像不错。但那个 8 秒的请求对用户来说已经很糟糕，而且它可能占住连接、线程和内存，进一步拖慢系统。

### P50、P95、P99 怎么理解

| 指标 | 白话解释 | 你应该怎么用 |
| --- | --- | --- |
| P50 | 一半请求比它快 | 看普通用户体验 |
| P95 | 95% 请求比它快 | 看大多数用户是否稳定 |
| P99 | 99% 请求比它快 | 看尾部风险和系统抖动 |

如果 P50 很好，P99 很差，说明系统不是整体慢，而是有一部分请求特别慢。常见原因包括：

1. **某些请求参数导致慢 SQL。** 大多数查询走索引，毫秒级返回。但少数查询条件命中了全表扫描或回表，耗时从 2ms 飙到 2s。根本原因是数据分布不均匀——比如一个租户有 90% 的数据，普通用户查不到它，但这个租户自己的查询就会特别慢。
2. **缓存偶尔未命中。** 缓存命中时 1ms 返回，未命中时要回源查数据库，可能要 200ms。缓存未命中的原因通常是：冷启动时缓存为空、缓存过期刚好被赶上、或者某个冷门 key 从来没被缓存过。P50 反映的是缓存命中时的体验，P99 反映的是回源时的体验。
3. **GC 偶尔暂停。** Java/Go 等带垃圾回收的语言，在堆内存积累到一定程度时会触发 GC，暂停所有业务线程。平时 GC 几乎无感知（几毫秒），但当堆内存压力大时，一次 Full GC 可能暂停几百毫秒甚至秒级。这 1% 的慢请求，很可能正好撞上了 GC 暂停窗口。
4. **下游服务偶发抖动。** 你的服务依赖别人的接口，大多数时候下游响应很快，但下游自己也会遇到 GC、负载抖动、网络波动等问题。你的服务只是被动承受——下游慢 3 秒，你就慢 3 秒。而且微服务调用链越长，任何一个节点抖动都会传导到上游。
5. **队列里有任务积压。** 异步处理正常时，任务入队后很快被消费。但当流量突增或消费者暂时变慢时，队列会堆积。后进来的请求排在队尾，等待时间从毫秒级变成秒级甚至分钟级。P50 是队列通畅时的体验，P99 是队列积压时的体验。
6. **少数大对象处理很慢。** 大部分请求处理的是小数据，几 KB 的 JSON 很快就序列化完了。但偶尔有请求要处理大文件、长列表、复杂嵌套结构，序列化/反序列化和内存分配的开销急剧膨胀。100KB 和 1MB 的对象，处理时间可能差 10 倍以上。

初学者可以这样记：

```text
平均值看大概
P95 看体验
P99 看风险
```

> 怎么理解"99% 请求比它快"？假设你有 1000 个请求，按耗时从小到大排列，第 990 个请求的耗时就是 P99。也就是说，只有 10 个请求（1%）比这个值更慢。

容量评估中，P99 往往比平均值更重要。

### TTFT、TPOT 是 AI 系统里的延迟指标

AI 应用里，普通 HTTP 延迟不够用了。因为 LLM 请求不是一次返回完整结果，而是持续生成 token。

| 指标 | 全称 | 白话解释 |
| --- | --- | --- |
| TTFT | Time To First Token | 用户多久看到第一个字 |
| TPOT | Time Per Output Token | 后面每个 token 生成多快 |
| Tokens/s | Tokens Per Second | 每秒生成多少 token |

**TPOT 怎么算：**

```text
TPOT = (总生成时间 - TTFT) ÷ 生成的 token 数
```

举个例子：用户发了一个请求，1 秒后看到第一个 token（TTFT = 1s），之后又花了 9 秒生成了 100 个 token，那么：

```text
TPOT = (10 - 1) ÷ 100 = 0.09s = 90ms/token
```

TPOT 和 Tokens/s 互为倒数：TPOT 是 90ms/token，换算成 Tokens/s 就是约 11 tokens/s。两个指标本质说的是同一件事，只是角度不同——TPOT 关注”每个 token 多慢”，Tokens/s 关注”每秒能出多少”。

**TPOT 多少算合理：**

| 级别 | TPOT | Tokens/s | 用户体感 |
| --- | --- | --- | --- |
| 优秀 | < 50ms | > 20 | 飞快，接近实时阅读 |
| 良好 | 50-100ms | 10-20 | 流畅，接近正常阅读速度 |
| 及格 | 100-200ms | 5-10 | 能用，但能感觉在”等” |
| 差 | > 200ms | < 5 | 明显”一个字一个字蹦” |

人的阅读速度大约是 5-8 tokens/s（中文约 3-5 字/秒），所以 Tokens/s 低于 8 时用户体感就开始变差。实际生产中，多数 LLM API 的 TPOT 在 30-100ms 之间，自部署小模型可能在 100-300ms，而流式输出的语音场景要求更苛刻，TPOT 需要控制在 50ms 以内才能保证语音的自然感。

**TTFT 和 TPOT 的关系：**

TTFT 决定用户觉得系统有没有反应。TPOT 决定用户觉得输出是否流畅。

一个 AI 产品如果 TTFT 是 5 秒，即使后面生成很快，用户也会觉得卡。一个产品 TTFT 只有 500ms，但 TPOT 很慢，用户会觉得它”一个字一个字蹦”。所以 AI 容量评估必须单独看这些指标。

## 3. CPU 和操作系统术语

### CPU 使用率和 CPU Load 不一样

CPU 使用率表示 CPU 有多少时间在忙。CPU Load 表示有多少任务正在运行或等待运行。

可以用饭店类比。

CPU 使用率像厨师有多忙。CPU Load 像厨房门口排了多少单。厨师忙不忙重要，排队多不多也重要。如果厨师一直 80% 忙但没有排队，系统可能还健康；如果厨师 80% 忙但门口排了很多单，说明请求已经开始堆积。

在 Linux 中，Load Average 表示过去 1 分钟、5 分钟、15 分钟内处于运行或等待状态的平均任务数。如果一台机器有 4 个 CPU 核心，Load 长期接近 4，通常说明 CPU 刚好比较忙；如果长期超过 8（核心数的 2 倍），说明有大量任务在排队等待。

一个简单的判断公式：

```text
Load / CPU 核心数 = 负载率
```

| 负载率 | 状态 | 说明 |
| --- | --- | --- |
| < 0.7 | 健康 | 有充足余量处理突发流量 |
| 0.7 - 1.0 | 较忙 | 正常运行但余量不多 |
| > 1.0 | 过载 | 任务开始排队，延迟上升 |
| > 2.0 | 危险 | 严重排队，需要扩容或优化 |

**不同生产场景的 Load 参考值（假设 8 核机器，Load 以 1 分钟均值为准）：**

| 场景 | 正常 Load | 告警阈值 | 说明 |
| --- | --- | --- | --- |
| Web API 服务 | 1 - 4 | > 6 | 请求型负载，来一个处理一个，Load 应保持较低。如果经常接近核心数，说明 QPS 接近瓶颈。 |
| 消息队列消费者 | 4 - 7 | > 10 | 批量消费型负载，天然会把 CPU 跑满。Load 接近甚至略超核心数是正常的，但如果持续超过核心数 1.5 倍，说明消费速度跟不上生产速度。 |
| 数据库（MySQL/PG） | 2 - 5 | > 8 | 混合负载，既有查询也有 IO。由于大量磁盘 IO，Load 容易偏高。但如果超过核心数的 1.5 倍且 IO Wait 也高，通常意味着查询需要优化或需要加内存做缓存。 |
| 定时任务/批处理 | 6 - 8 | > 12 | 任务型负载，跑起来就应该把 CPU 用满。白天在线低峰时跑批处理，Load 高不代表有问题，关键是别影响在线服务。通常用 cgroup 或 nice 值做隔离。 |
| AI 推理服务 | 5 - 8 | > 10 | GPU 推理场景下 CPU Load 通常不高，主要是调度和数据预处理。如果 CPU Load 高，说明瓶颈在 CPU 侧（数据预处理、序列化），而不是 GPU 计算本身。 |

举个实际的例子：你有一台 8 核的 Web 服务器，日常 Load 在 1.5 左右，某天突然飙到 7。先别急着加机器——查一下是 CPU 高还是 IO Wait 高。如果 IO Wait 从 5% 涨到 40%，问题可能出在一个慢 SQL 把磁盘打满了；如果 User CPU 高，可能是某个请求触发了昂贵的计算（比如大列表排序）。找到根因再决定是优化代码还是加资源。

但 Load 也要结合场景看。IO 等待（D 状态进程）也会让 Load 升高，因此看到 Load 高不能立刻说 CPU 不够，还要看 IO Wait 和进程状态。

### User CPU、System CPU、IO Wait 怎么看

CPU 使用率不是铁板一块，Linux 把它拆成了几个部分：

| 指标 | 白话解释 | 常见原因 | 排查方向 |
| --- | --- | --- | --- |
| User CPU（us） | 业务代码在消耗 CPU | 计算、序列化、压缩、加密、正则匹配 | 看业务代码和算法，用 perf/top 定位热点函数 |
| System CPU（sy） | 内核在消耗 CPU | 网络包处理、系统调用、上下文切换、锁竞争 | 看网络、系统调用频率、线程数是否过多 |
| IO Wait（wa） | CPU 在等磁盘或网络 IO | 慢磁盘、大量读写、数据库压力、NFS 挂载 | 加 CPU 没用，要看磁盘、数据库和文件系统 |
| Steal（st） | 虚拟机被宿主机"抢走"的 CPU | 超卖的云主机、宿主机过载 | 换宿主机或升级规格，代码层面无解 |
| Idle（id） | CPU 空闲 | 正常余量 | 低于 20% 时需要关注，低于 10% 时可能已经过载 |

**怎么查这些指标：**

```bash
# 最快的方式：top，看第 3 行
# %Cpu(s): 15.2 us,  8.3 sy,  0.0 ni, 72.1 id,  3.8 wa,  0.0 hi,  0.6 si,  0.0 st
top

# 更精确的方式：mpstat，每秒采样一次
mpstat -P ALL 1

# 看单个进程的 CPU 分布
pidstat -u 1 -p <pid>
```

`top` 输出的第 3 行就是 CPU 的拆分，字段顺序是 us / sy / ni / id / wa / hi / si / st，一眼就能看出是业务代码的问题还是内核的问题。

**生产环境中这些值意味着什么：**

| 指标 | 健康范围 | 需要关注 | 需要介入 |
| --- | --- | --- | --- |
| User CPU | < 60% | 60-80% | > 80% |
| System CPU | < 10% | 10-20% | > 20% |
| IO Wait | < 5% | 5-20% | > 20% |
| Steal | < 1% | 1-5% | > 5% |

这些不是绝对标准，要结合场景看。一个批处理任务 User CPU 跑到 90% 是正常的；但一个 Web API 服务 User CPU 持续 80%，说明快到瓶颈了。

**System CPU 特别值得关注。** 正常业务系统里，System CPU 应该远低于 User CPU。如果你发现 System CPU 占比超过 User CPU 的 50%，或者 System CPU 持续高于 20%，通常意味着以下几种问题之一：

- **上下文切换过多**：线程池设得太大，或者锁竞争激烈，CPU 花大量时间在线程切换上而不是干活。用 `vmstat 1` 看 `cs` 列（每秒上下文切换次数），后面会详细讲。
- **系统调用过于频繁**：每次 `read()`、`write()`、`send()` 都是系统调用，都会从用户态切换到内核态。如果每次只读写很少的数据，系统调用的开销占比就会很高。解决方法是用缓冲 IO 或批量操作。
- **网络中断处理**：高 QPS 场景下，网络包的收发和协议栈处理本身就很消耗 CPU。可以用 `sar -n DEV 1` 看网卡的 packets/s，如果非常高（百万级），考虑启用网卡多队列或 RPS/RFS。

**IO Wait 高时的排查路径：**

```bash
# 先确认是哪个设备慢
iostat -xz 1

# 关注这几个字段：
# %util   — 磁盘有多忙，接近 100% 说明磁盘饱和
# await   — IO 平均等待时间（ms），SSD 应该 < 1ms，HDD 可能在 5-20ms
# r/s w/s — 每秒读写次数

# 再看是哪个进程在大量读写
iotop
```

IO Wait 高且 `%util` 接近 100%，说明磁盘已经是瓶颈。常见原因：数据库没命中索引做了全表扫描、日志同步写（没有用异步）、大量小文件 IO。解法不是加 CPU，而是优化查询、用异步写、或者换更快的磁盘（HDD → SSD → NVMe）。

**一个真实的排查案例：** 一台 8 核 Web 服务器，用户反馈接口变慢。`top` 看到 CPU 总使用率 75%，看起来好像还好。但细看：us=20%，sy=15%，wa=38%。User CPU 不高，System CPU 偏高，IO Wait 非常高。`iostat` 发现 `/dev/sda` 的 `%util` 是 98%，`await` 从正常的 2ms 飙到了 80ms。`iotop` 发现 MySQL 进程在疯狂读盘。最后定位到一个慢查询没走索引，全表扫描 200 万行，磁盘被它打满。加了索引后，IO Wait 回到 3%，接口延迟恢复正常。——如果只看 CPU 总使用率 75%，根本发现不了问题。

### 上下文切换是什么

CPU 一次只能执行有限数量的任务。线程太多时，操作系统要不断把 CPU 从一个线程切到另一个线程，这就是上下文切换（Context Switch）。

每次切换，操作系统要保存当前线程的寄存器、栈指针、程序计数器，再恢复下一个线程的这些状态。这本身就要消耗几百到几千个 CPU 周期。更隐蔽的成本是 CPU 缓存失效——切换后 L1/L2 缓存里都是上一个线程的数据，新线程一开始几乎全是缓存未命中（Cache Miss），这比切换本身更慢。

**怎么查上下文切换：**

```bash
# 看系统总体上下文切换次数
vmstat 1
# 关注 cs 列：每秒上下文切换次数

# 看每个进程的上下文切换
pidstat -w 1
# cswch/s  — 自愿切换（通常是等 IO）
# nvcswch/s — 非自愿切换（通常是被调度器抢走 CPU）
```

**生产环境中的参考值：**

| 场景 | 正常范围 | 需要关注 | 需要介入 |
| --- | --- | --- | --- |
| Web API 服务（8 核） | < 5000 次/s | 5000-20000 次/s | > 20000 次/s |
| 数据库服务 | < 10000 次/s | 10000-50000 次/s | > 50000 次/s |
| 高并发网关（8 核） | < 20000 次/s | 20000-50000 次/s | > 50000 次/s |

这些值和业务强相关，不能孤立地看数字。一个 8 核机器跑 200 个线程，每秒几千次切换很正常；但如果只跑了 4 个线程却有几万次切换，就说明有问题。

**上下文切换高通常意味着三种情况：**

**第一，线程池设得太大。** 这是最常见的原因。很多人觉得线程多=并发高=性能好，事实恰恰相反。一个 8 核机器开了 200 个线程，操作系统要在 200 个线程之间来回切换，大量 CPU 时间花在了切换上而不是干活。经验值：CPU 密集型任务，线程数 = CPU 核心数；IO 密集型任务，线程数 = CPU 核心数 × (1 + IO 等待时间/CPU 计算时间)。

**第二，锁竞争激烈。** 多个线程抢同一把锁时，没抢到的线程会被挂起，等锁释放后再被唤醒。每次挂起和唤醒就是一次上下文切换。锁竞争越激烈，切换越频繁。`pidstat -w 1` 中如果 `nvcswch/s`（非自愿切换）特别高，多半是锁的问题。解决方法：减少锁的粒度、用无锁数据结构、或者减少共享状态。

**第三，短任务过多。** 如果大量任务每个只需要几微秒就完成了，操作系统会不断做"创建→执行→销毁"或"唤醒→执行→挂起"的循环，切换开销占比就非常高。常见于大量短 HTTP 请求、频繁的定时器回调、或者不合理的批处理粒度。解决方法是合并短任务、用批量处理代替逐条处理。

**一个排查案例：** 某 Java 服务上线后延迟翻倍，CPU 使用率却只有 30%。`vmstat 1` 显示 `cs` 列从正常的 3000 飙到了 25000。`pidstat -w 1` 发现这个 Java 进程的 `nvcswch/s` 高达 18000。排查代码发现线程池从 8 被改成了 200，理由是"提高并发"。改回 16（8 核 × 2）后，上下文切换降到 4000，延迟恢复正常。——CPU 使用率低不代表系统空闲，有可能是 CPU 在忙着切换线程。


### 文件描述符（FD）为什么默认只有 1024

很多初学者第一次做长连接压测时会遇到一个问题：连接数刚到几百就报错了。原因往往是 Linux 默认的文件描述符上限只有 1024。

这个数字看起来很小，但它不是因为 Linux 能力不够，而是一个"历史兼容性 + 系统保护"下的保守默认值。理解它的来龙去脉，对做容量评估很有帮助。

#### 什么是文件描述符

Linux 有一个核心设计哲学：**一切皆文件（Everything is a file）** 。不只是磁盘上的文件，网络连接、管道、设备，在内核看来都是"文件"，都需要一个文件描述符（File Descriptor，简称 FD）来标识。

| 对象 | 是否占用 FD |
| --- | --- |
| 普通文件 | ✅ |
| TCP 连接 | ✅ |
| WebSocket 连接 | ✅ |
| Unix Socket | ✅ |
| Pipe 管道 | ✅ |
| epoll 实例 | ✅ |
| stdin/stdout/stderr | ✅ |

一个 WebSocket 服务，每个客户端连接至少占用 1 个 FD。如果默认上限是 1024，扣掉系统自身占用的几十个，实际只能接受几百个连接。对现代系统来说，这显然太低了。

#### 为什么历史默认值这么低

原因有五个，每个都值得理解。

**第一，早期系统并发很低。** 早期 Unix 和 Linux 的时代，服务器规模很小，没有 WebSocket、长连接、微服务、Kafka、Redis Cluster 这些东西。当时一台机器同时打开 1024 个文件已经算很多了，几十个并发连接就是高负载。

**第二，FD 不只是一个数字，它背后是内核资源。** 很多人误以为 FD 只是一个整数编号，开多少都无所谓。实际上每一个 FD 背后都有内核对象：socket buffer、inode、file struct、dentry、page cache、TCP 状态机。如果不加限制，10 万个连接可能直接吃掉几个 GB 内存，100 万个连接可能吃掉几十 GB。

**第三，防止程序 Bug 把系统打死。** 这是非常关键的一点。一个经典 Bug 是 FD 泄漏：程序不断打开文件或连接，却忘记关闭。如果没有上限保护，一个有 Bug 的进程可能打开几十万个 FD，吃光系统资源，导致整台机器上所有服务都无法正常工作。1024 这个默认值本质上是一个安全保护网。

**第四，早期 select() 系统调用的硬限制。** 这是最核心的历史原因之一。早期网络编程大量使用 `select()` 来监听多个连接。而 `select()` 内部使用固定大小的位图（bitmap），编译时就确定了上限：

```text
FD_SETSIZE = 1024
```

这意味着 `select()` 最多只能监听 1024 个文件描述符。大量系统软件（早期 Apache、各种 Unix 服务）都围绕这个限制设计。后来才出现了更好的替代方案：

| 技术 | 改进 | 适用系统 |
| --- | --- | --- |
| poll | 不再有 1024 硬限制，但仍是 O(n) 遍历 | Linux/Unix |
| epoll | O(1) 事件通知，适合高并发 | Linux |
| kqueue | 类似 epoll 的高效方案 | macOS/BSD |
| io_uring | 新一代异步 IO，更高性能 | Linux 5.1+ |

> 初学者提示：如果你用 Go、Java、Node.js 等高级语言写网络服务，底层的 epoll/kqueue 通常由运行时或框架自动处理，你不需要直接操作它们。但理解它们的存在和原理，有助于你理解为什么现代服务器能处理几十万并发连接。

**第五，兼容低配设备。** Linux 必须能运行在各种硬件上：小 VPS、嵌入式设备、树莓派、老旧服务器。如果默认就开放 100 万 FD，很多低配机器启动时就会预分配大量内核资源，白白浪费内存。

#### 现代系统为什么需要调大

现代系统大量使用长连接，FD 消耗远超早期设计预期：

| 技术 | FD 消耗特点 |
| --- | --- |
| WebSocket | 每个客户端一个长连接，持续占用 |
| gRPC | 多路复用但仍需连接 |
| Redis 连接池 | 每个应用实例维持多个连接 |
| Kafka | Broker 维护 client、replica、controller 多种连接 |
| 微服务 | 服务间大量 HTTP/gRPC 连接 |
| AI 流式推理 | 长时间占用连接直到生成完成 |

一个实时 AI 语音产品，单个用户可能同时占用多个 FD：WebSocket 连接、到 ASR 服务的连接、到 LLM 服务的连接、日志文件等。

#### 怎么调整 FD 上限

Linux 的 FD 限制有多层，必须逐层检查：

| 层级 | 查看方式 | 修改方式 |
| --- | --- | --- |
| 进程级（soft/hard limit） | `ulimit -n` | `/etc/security/limits.conf` 或 `ulimit -n 65535` |
| 系统级 | `cat /proc/sys/fs/file-max` | `sysctl fs.file-max=2000000` |
| systemd 服务级 | 服务配置文件 | `LimitNOFILE=65535` |
| 容器级（Docker/K8s） | `docker inspect` 或 Pod spec | `--ulimit nofile=65535:65535` |

常见的推荐值：

| 场景 | 建议 FD 上限 |
| --- | --- |
| 普通 Web 服务 | 65535 |
| 高并发网关（Nginx、Envoy） | 500000+ |
| 超大规模长连接服务 | 1000000+ |

#### 调大 FD 不是终点

真正高级的工程师不会只改一个 `ulimit` 就觉得万事大吉。还要关注：

1. **FD 泄漏**。程序打开连接或文件后忘记关闭，FD 数量持续增长。Go 里忘写 `defer file.Close()`、Java 里忘关 InputStream，都是常见原因。
2. **TIME_WAIT 堆积**。大量短连接关闭后进入 TIME_WAIT 状态，虽然不再活跃，但仍占用 FD 和端口。高频短连接场景要特别注意。
3. **epoll 是否正确使用**。如果事件循环写得有问题，FD 注册了却没有正确移除，会导致 FD 泄漏和 CPU 飙升。
4. **单机连接模型要整体评估**。10 万个 WebSocket 连接不只是 10 万个 FD，还意味着 10 万份 TCP buffer、10 万个内核 socket 对象、对应的 epoll 事件、应用层的 goroutine 或线程。只改 FD 上限而不评估内存、CPU 和网络，系统照样会崩。

可以这样记：

```text
FD 上限决定你"能不能"打开这么多连接
内存和 CPU 决定你"撑不撑得住"这么多连接
```

这也是为什么容量评估不能只看单一指标。FD 只是连接容量的第一道门槛，过了这道门槛，后面还有内存、CPU、带宽和应用层调度等一系列约束。

## 4. 内存和 GC 术语

### 内存相关的常用术语

做容量评估，首先要分清操作系统层面和应用层面各自在说什么。Linux 内存管理和 Java/Go 运行时内存管理是两个世界，它们用不同的名字描述同一块物理内存的不同"视角"。

| 术语 | 层级 | 白话解释 |
| --- | --- | --- |
| RSS（Resident Set Size） | 操作系统 | 进程实际占用的物理内存大小，包含代码段、数据段、共享库和堆。操作系统用它来判断一个进程吃了多少物理 RAM |
| VSZ（Virtual Memory Size） | 操作系统 | 进程的虚拟内存总量，包含还没有分配物理内存的部分。通常比 RSS 大很多，单独看没什么意义 |
| Heap | 应用运行时 | 程序运行时动态分配对象的地方。Java 的 `new`、Go 的 `make` 都从这里拿内存。Heap 膨胀是内存问题最常见的原因 |
| Stack | 应用运行时 | 每个线程/goroutine 的调用栈。存局部变量和函数调用链。通常很小（线程默认 1MB，goroutine 默认几 KB），但如果递归太深会栈溢出 |
| Page Cache | 操作系统 | Linux 用空闲内存缓存磁盘文件内容。读文件时先查 Page Cache，命中了就不走磁盘。它会随使用自动增长，内存紧张时自动释放 |
| Swap | 操作系统 | 把不活跃的内存页写到磁盘上，腾出物理内存给活跃进程。Swap 一旦被大量使用，性能会断崖式下跌，因为磁盘比内存慢几个数量级 |
| Off-Heap / Direct Memory | 应用运行时 | Java 中 NIO、Netty 等框架绕过 JVM 直接从操作系统分配的内存。不在 GC 管辖范围内，但同样会消耗物理内存。用多了会导致 RSS 远高于 Heap |
| Shared Memory | 操作系统 | 多个进程共享的内存区域。`/dev/shm`、mmap、共享库都用到它。RSS 包含了共享内存，所以多进程的 RSS 加起来会超过实际物理内存占用 |
| Memory-Mapped File（mmap） | 操作系统 | 把文件映射到内存地址空间。读写文件就像读写内存一样。JVM 的类加载、Kafka 的日志段都大量使用 mmap |
| OOM（Out of Memory） | 操作系统 | 内存耗尽。Linux 的 OOM Killer 会挑一个占用内存最多的进程杀掉，保护系统整体存活 |

初学者常犯的错误，是看到 Linux 内存使用很高就以为泄漏。实际上 Linux 会尽量利用空闲内存做 Page Cache，这是正常的。真正需要担心的是 RSS 持续上涨且不回落、Swap 开始被大量使用、或 OOM Killer 出手。

一个直观的关系：

```text
物理内存总量
├── 内核自身占用（不可压缩）
├── 各进程 RSS 之和（用户空间实际使用）
│   ├── Heap（应用动态分配的对象）
│   ├── Stack（调用栈）
│   ├── mmap（文件映射、共享库）
│   └── Off-Heap（直接内存、NIO Buffer 等）
├── Page Cache（文件缓存，可回收）
└── 空闲内存（free）
```

> 初学者提示：`free -h` 看到 `available` 列比较低才需要担心。`used` 列高不代表内存不够，因为 Page Cache 被算在 `used` 里。`available` 才是系统实际还能分给新进程的内存量。

### 怎么查看内存使用情况

| 命令 | 看什么 | 适用场景 |
| --- | --- | --- |
| `free -h` | 系统总体内存分配 | 第一眼看系统是否健康 |
| `top` / `htop` | 各进程 RSS 排序 | 找哪个进程吃内存最多 |
| `cat /proc/<pid>/smaps_rollup` | 进程内存细项拆分 | 精确定位 RSS 由哪些部分组成 |
| `jmap -heap <pid>` | JVM Heap 使用详情 | Java 进程看堆内存分布 |
| `jstat -gc <pid>` | JVM GC 统计 | 实时观察 GC 频率和耗时 |
| `go tool pprof -memprofile` | Go 堆内存分配热点 | Go 进程定位谁在分配内存 |
| `pmap -x <pid>` | 进程内存映射详情 | 看内存分布在哪些段 |
| `vmstat 1` | 系统级别 si/so（swap in/out） | 判断是否开始用 Swap |

```bash
# 最快的系统级检查：free -h
# 关注 available 列和 swap used 列
$ free -h
              total        used        free      shared  buff/cache   available
Mem:           15Gi       8.2Gi       1.1Gi       256Mi       6.1Gi       6.5Gi
Swap:         2.0Gi       0.0Gi       2.0Gi

# 看进程级内存：按 RSS 排序
$ ps aux --sort=-%mem | head -10

# 看 Java 进程的堆内存详情
$ jmap -heap <pid>

# 看 GC 活动：每秒采样一次
$ jstat -gcutil <pid> 1000
# S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
# 0.00  45.21  67.33  32.15  95.42  91.20   1234    5.678     3    0.890    6.568
```

### 生产环境内存指标参考值

| 指标 | 健康范围 | 需要关注 | 需要介入 |
| --- | --- | --- | --- |
| 系统可用内存（available） | > 总内存 20% | 总内存 10%-20% | < 总内存 10% |
| Swap 使用量 | 0 或极小 | 持续 > 0 | 持续增长 |
| 进程 RSS 增长趋势 | 稳定或随流量比例波动 | 缓慢持续上涨 | 快速上涨或不回落 |
| JVM Heap 使用率（常态） | < 70% | 70%-85% | > 85%（GC 压力大） |
| Off-Heap（Direct Memory） | < Heap 大小 | 接近 Heap 大小 | 超过 Heap 大小 |

> 注意：这些阈值不是铁律。一个批处理任务 Heap 用到 90% 可能完全正常，因为它处理完就释放。关键看趋势和业务特征。

### 如何判断内存相关指标是否异常

判断内存问题，不能只看某一刻的快照，要看趋势。一个实用的四步判断法：

**第一步：看趋势。** RSS 是否持续上涨、不回落？如果 RSS 随流量波动（白天高、晚上低），通常是正常的。如果 RSS 只涨不跌，就像一个一直充气的气球，大概率是泄漏。

```bash
# 用 pidstat 每 10 秒采样一次进程内存
$ pidstat -r 10 -p <pid>
# 关注 minflt/s（缺页次数）和 VSZ、RSS 的变化趋势
```

**第二步：看 Swap。** 如果 Swap 开始被使用，说明物理内存已经不够了。Swap 使用量持续增长是紧急信号——进程会因为等磁盘 IO 而变得极慢。

```bash
# 快速检查 Swap 使用
$ free -h | grep Swap
# 或者看 vmstat 的 si/so 列（每秒 swap in/out 的 KB 数）
$ vmstat 1
# 如果 si 或 so 持续非零，说明在用 Swap
```

**第三步：看 GC。** 内存增长是否伴随 GC 次数增加、GC 暂停时间变长？GC 压力上升是 Heap 内存紧张的直接信号（下一节详细展开）。

**第四步：看 OOM。** 是否出现 OOM Killer？Linux 的 OOM Killer 会在内存耗尽时杀掉一个进程。如果 `dmesg` 里出现了 `Out of memory: Killed process`，说明物理内存已经被耗尽。

```bash
# 检查是否有 OOM 记录
$ dmesg | grep -i "out of memory"
# 或者检查系统日志
$ journalctl -k | grep -i oom
```

一个可以记住的判断口诀：

```text
涨而不退是泄漏
Swap 动了是紧张
GC 频繁是堆满
OOM 出手是崩溃
```

### GC 相关术语和基本原理

GC（Garbage Collection）是垃圾回收，Java、Go、.NET 等语言会自动回收不再被引用的对象。自动回收很方便，但不是免费的。

**GC 做了什么：** GC 要找到哪些对象已经没有人引用了，然后回收它们占用的内存。找的过程需要扫描和标记，这要消耗 CPU 和时间。某些 GC 算法还需要暂停所有业务线程（Stop-The-World，简称 STW），暂停期间任何请求都不会被处理。

**常见的 GC 算法和它们的特点：**

| GC 算法 | 使用者 | 原理 | 优缺点 |
| --- | --- | --- | --- |
| 分代 GC（Young/Old） | Java（传统 GC）、.NET | 新对象在 Young 区，存活够久就晋升到 Old 区。Young 区频繁回收，Old 区较少回收 | 适合大量短生命周期对象，但 Full GC 暂停时间长 |
| G1 GC | Java（Java 9+ 默认） | 把堆分成很多小 Region，优先回收垃圾最多的 Region | 暂停时间可控，但需要额外 CPU 开销来维护 Region 信息 |
| ZGC / Shenandoah | Java（低延迟场景） | 几乎所有工作都并发执行，STW 暂停时间在亚毫秒级 | 暂停时间极短，但吞吐量略低，需要更多 CPU |
| 三色标记 + 并发清除 | Go（从 1.5 开始） | 并发标记和清扫，STW 暂停通常在微秒级 | 暂停时间极短，但内存占用可能比 Java 更高（因为少了分代压缩） |
| 引用计数 | Python、PHP（辅助机制） | 每个对象维护一个引用计数，计数归零就回收 | 无法处理循环引用，需要辅助的循环检测器 |

**GC 的关键指标：**

| 指标 | 白话解释 | 怎么看 |
| --- | --- | --- |
| Minor GC / Young GC | 回收年轻代（新创建的对象） | Java：`jstat -gcutil` 的 YGC/YGCT 列 |
| Major GC / Full GC | 回收老年代甚至整个堆 | Java：`jstat -gcutil` 的 FGC/FGCT 列 |
| GC 暂停时间（STW） | 所有业务线程被暂停的时间 | Java：GC 日志中的 `Pause` 时间；Go：`GODEBUG=gctrace=1` |
| GC 频率 | 多久触发一次 GC | 每秒 GC 次数超过 1-2 次就需要关注 |
| GC 后堆存活量 | GC 回收后堆里还有多少活对象 | 反映真正的内存需求量 |
| 分配速率 | 每秒分配多少内存 | 速率越高，GC 越频繁。Go：`go tool pprof` 的 `alloc_space` |

### GC 为什么会影响容量

如果一次请求创建大量临时对象，流量上来后对象创建速度会增加，GC 压力就会变大。GC 一旦频繁或暂停时间变长，P99 延迟会明显变差。

一个常见事故路径是：

```text
流量增加
→ 对象创建增加
→ GC 变频繁
→ 请求变慢
→ 请求堆积
→ 内存继续上涨
→ OOM 或服务重启
```

GC 影响容量的机制有两层：

**第一层：STW 暂停直接增加延迟。** GC 暂停期间，所有在途请求都停住了。如果暂停 200ms，恰好有一批请求撞上，这批请求的延迟就凭空多了 200ms。P99 经常就是被这些 GC 暂停请求拉起来的。

**第二层：GC 线程抢 CPU。** 即使 GC 本身不暂停业务线程（并发 GC），GC 线程也要消耗 CPU。如果 GC 线程占了 30% CPU，留给业务的 CPU 就少了 30%。原来 80% CPU 就能处理的流量，现在需要 110%，直接过载。

所以容量评估要关注单请求对象分配量，而不是只看 CPU。一个请求如果只分配 1KB 对象，1000 QPS 每秒也就分配 1MB，GC 压力很小。但如果一个请求分配 100KB 对象，1000 QPS 每秒分配 100MB，GC 就会忙个不停。

### GC 问题的排查方法

排查 GC 问题，不同语言有不同工具，但思路是一样的：先看 GC 频率和暂停时间是否异常，再定位是哪个对象分配过多导致的。

**Java GC 排查：**

```bash
# 1. 实时看 GC 统计：每秒采样一次
$ jstat -gcutil <pid> 1000
#   S0     S1     E      O      M     CCS    YGC   YGCT  FGC  FGCT   GCT
#   0.00  45.21  67.33  32.15  95.42  91.20  1234  5.678   3   0.890  6.568
#
# 关注这几个字段：
# YGC/YGCT   — Young GC 次数和总耗时。YGCT/YGC = 平均每次暂停时间
# FGC/FGCT   — Full GC 次数和总耗时。Full GC 次数 > 0 就要警惕
# O           — Old 区使用率。持续 > 80% 说明对象晋升太快
# E           — Eden 区使用率。涨到 100% 就触发 Young GC

# 2. 开启 GC 日志（JDK 9+）
$ java -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=50m -jar app.jar

# 3. 堆内存分配热点（需要先 dump）
$ jmap -dump:live,format=b,file=heap.hprof <pid>
# 然后用 MAT（Eclipse Memory Analyzer）或 JVisualVM 分析

# 4. 实时看分配热点（不暂停，推荐）
$ jcmd <pid> GC.class_stats | sort -k 3 -n -r | head -20
```

**Go GC 排查：**

```bash
# 1. 启动时开启 GC trace
$ GODEBUG=gctrace=1 ./your-app
# gc 1 @0.012s 2%: 0.026+1.2+0.019 ms clock, 0.21+0.34/1.0/0.42+0.15 ms cpu, 4->6->2 MB, 5 MB goal, 0 MB stacks, 0 MB globals, 8 P
# 关注：
# gc N      — 第几次 GC
# 2%        — GC 占总 CPU 的比例（> 5% 需要关注）
# 4->6->2 MB — GC 前堆大小->GC 中峰值->GC 后存活量
# 8 P       — 并行度

# 2. 通过 HTTP pprof 看内存分配热点
$ go tool pprof http://localhost:6060/debug/pprof/heap
# 或者看累积分配量（找分配热点更有效）
$ go tool pprof http://localhost:6060/debug/pprof/allocs

# 3. 在 pprof 交互模式下
$ (pprof) top 20       # 看分配最多的函数
$ (pprof) web           # 生成调用图（需要安装 graphviz）
```

**通用排查思路：**

```text
第一步：确认是不是 GC 问题
  → 看 GC 日志/统计，暂停时间是否异常，频率是否过高

第二步：确认 GC 为什么频繁
  → 看堆内存分配速率（每秒分配多少）
  → 看 GC 后存活对象量（回收不掉说明有引用泄漏）

第三步：定位分配热点
  → dump 堆内存分析大对象
  → pprof 分析分配调用栈

第四步：对症下药
  → 对象池/缓存复用（减少分配）
  → 减少不必要的大对象创建
  → 调整 GC 参数（最后手段）
```

### 如何识别、排查和解决 GC 相关的问题

GC 问题通常表现为以下几种症状。每种症状背后有不同的根因和解法：

**症状一：P99 周期性飙高。** 延迟平时很好，每隔几秒或几十秒就出现一次尖刺。

```text
典型原因：Young GC 暂停时间过长
排查方法：
  1. jstat -gcutil 看 YGC 次数，计算 YGCT/YGC = 平均暂停时间
  2. 如果每次暂停 > 50ms，看 Young 区是否太大（大 Young 区每次要扫描更多对象）
  3. 如果暂停时间合理但频率太高，说明分配速率过高
解决思路：
  - 减少短生命周期对象创建（对象池、StringBuilder 拼接替代 String 拼接）
  - 减少 Young 区大小以降低单次暂停时间（但会增加 GC 频率，需权衡）
  - 升级到 ZGC 或 Shenandoah（如果 Java 版本允许）
```

**症状二：Full GC 频繁出现。** Old 区使用率持续上涨，Full GC 每隔几分钟就来一次，每次暂停几百毫秒甚至几秒。

```text
典型原因：内存泄漏或老年代过早填满
排查方法：
  1. jstat -gcutil 看 O 列（Old 区使用率）是否持续 > 80%
  2. FGC（Full GC 次数）是否持续增加
  3. jmap -dump:live 导出堆，用 MAT 分析 Retained Heap 最大的对象
解决思路：
  - 找到泄漏的对象（没被释放的集合、缓存没有淘汰策略、注册了监听器没有注销）
  - 增大堆内存（治标不治本，泄漏会把增大的内存也吃掉）
  - 检查是否有大对象直接分配到 Old 区（-XX:PretenureSizeThreshold）
```

**症状三：GC 占 CPU 过高。** 系统 CPU 使用率高，但业务吞吐量没增加。

```text
典型原因：分配速率过高，GC 线程忙不过来
排查方法：
  1. top 看 CPU 使用率，如果 User CPU 高但业务 QPS 没涨，可能 CPU 花在 GC 上
  2. Java：GC 日志中 GC 线程的 CPU 时间
  3. Go：GODEBUG=gctrace=1 看 GC 占 CPU 百分比（正常 < 5%）
解决思路：
  - 用 pprof 或 jmap 定位分配热点函数
  - 减少 JSON 序列化/反序列化时的临时对象（使用 Jsonb/Protobuf 等高效序列化）
  - 复用 buffer 和对象池
```

**症状四：Go 服务内存持续上涨但不 OOM。** RSS 长期上涨，但 `GODEBUG=gctrace=1` 显示 GC 后存活量并不大。

```text
典型原因：Go 的内存归还策略——Go 默认不会立刻把释放的内存归还操作系统
排查方法：
  1. 对比 GC 后存活量和 RSS，如果差距很大，说明内存被 Go 运行时缓存了
  2. GOMEMLIMIT 环境变量或 runtime/debug.SetMemoryLimit 看是否设置了内存限制
解决思路：
  - Go 1.19+ 设置 GOMEMLIMIT 让 GC 更主动地回收
  - 设置 GOGC 降低 GC 触发阈值（默认 100，设为 50 会更频繁 GC 但内存更少）
  - 极端情况调用 debug.FreeOSMemory() 强制归还（仅用于排查，不要用在生产路径上）
```

### 生产环境中典型的内存与 GC 问题场景

**场景一：JSON 序列化引发的 GC 风暴**

```text
现象：一个 API 网关，平时 P99 延迟 20ms，流量翻倍后 P99 飙到 500ms。
排查过程：
  1. jstat 看到 YGC 从每秒 2 次涨到每秒 15 次
  2. GC 日志显示每次 Young GC 暂停 30ms，加上频率高，每秒有 450ms 在做 GC
  3. pprof 定位到分配热点是 JSON 序列化——每处理一个请求，Gson 创建大量临时 Token 对象
根因：
  每个请求序列化一个大 JSON 响应体（包含 500 个商品详情），Gson 每次创建 2000+ 个临时对象。
  流量翻倍后对象分配速率达 400MB/s，GC 完全跟不上。
解决方案：
  1. 换用 Jackson 流式序列化，对象分配量降低 80%
  2. 对响应体做缓存——相同参数的请求在 TTL 内直接返回缓存结果
  3. 最终 P99 回到 30ms，GC 频率降到每秒 3 次
```

**场景二：缓存无限增长导致 OOM**

```text
现象：一个推荐服务，启动后运行稳定，但 3-5 天后必定 OOM 重启。
排查过程：
  1. jstat 看到 O 列（Old 区使用率）从启动时的 20% 缓慢涨到 95%
  2. 每次 Full GC 回收不掉多少对象——大量对象被永久持有
  3. MAT 分析 heap dump，发现一个 ConcurrentHashMap 存了 300 万个用户推荐结果，每个 2KB，总计 6GB
根因：
  开发者为"提高性能"把推荐结果全部缓存在本地 Map 里，没有过期策略，没有大小限制。
  用户量增长后，缓存越来越大，最终吃光堆内存。
解决方案：
  1. 用 Caffeine/Guava Cache 替代裸 HashMap，设置最大条目数和过期时间
  2. 设置缓存淘汰策略（LRU 或 W-TinyLFU）
  3. 内存占用稳定在 2GB 以内，不再 OOM
```

**场景三：日志框架引发的 Off-Heap 泄漏**

```text
现象：一个 Java 服务 RSS 持续增长，但 jstat 显示 Heap 使用率稳定在 50%。
排查过程：
  1. cat /proc/<pid>/smaps_rollup 发现大量匿名内存（Anonymous）
  2. pmap -x <pid> 发现多段 64MB 的匿名映射
  3. 排查发现 Log4j2 的 AsyncAppender 内部 RingBuffer 队列设得过大（100 万个槽位），
     每个日志事件占 4KB，队列满时就是 4GB Off-Heap 内存
根因：
  日志队列配置不合理。日志写入速度跟不上产生速度时，队列不断扩容，内存持续增长。
  因为是 Off-Heap，GC 管不到。
解决方案：
  1. 减小 RingBuffer 大小为 4096（默认值）
  2. 设置 DiscardThreshold，队列满时丢弃低级别日志（DEBUG/INFO），保留 ERROR
  3. RSS 稳定在 1.5GB 左右
```

**场景四：Go 服务延迟毛刺**

```text
现象：Go 微服务 P99 每隔 1-2 分钟出现一次 100ms 的延迟毛刺，P50 始终正常。
排查过程：
  1. GODEBUG=gctrace=1 看到 GC 间隔约 60 秒，每次 STW 暂停约 0.3ms
     → Go 的 GC 暂停不是原因
  2. 仔细看 gctrace 输出：gc 后堆 400MB，但 RSS 是 2GB
     → Go 运行时持有大量缓存内存
  3. 进一步发现，每次 GC 触发前后有短暂的 CPU 飙升（标记阶段占 15% CPU）
     → GC 标记阶段的 CPU 竞争导致业务 goroutine 被调度延迟
根因：
  服务在处理请求时大量使用 bytes.Buffer 拼接字符串，分配速率达 200MB/s。
  GC 标记阶段 CPU 开销高，在高流量时段与业务线程争抢 CPU。
解决方案：
  1. 引入 sync.Pool 复用 bytes.Buffer，分配速率降到 20MB/s
  2. 设置 GOMEMLIMIT=1536MB 让 GC 更积极回收，避免 RSS 无限膨胀
  3. GC 频率不变但 CPU 开销降低到 3%，P99 毛刺消失
```

**场景五：连接池与线程池叠加导致的内存爆炸**

```text
现象：一个电商服务大促时多个实例同时 OOM，重启后几分钟内再次 OOM。
排查过程：
  1. dmesg 看到 OOM Killer 杀掉了 Java 进程
  2. jstat 看到 Heap 满了，Full GC 间隔从正常的 10 分钟缩短到 30 秒
  3. MAT 分析发现：
     - 200 个 HTTP 连接 × 每个连接 2MB buffer = 400MB
     - 200 个数据库连接 × 每个连接的 ResultSet 缓存 5MB = 1GB
     - 1000 个线程 × 每个线程栈 1MB = 1GB
     总计 2.4GB，而堆只配了 2GB
根因：
  大促期间运维把线程池从 200 调到 1000"以防万一"，数据库连接池也从 50 调到 200。
  但每个连接和线程都要占内存，叠加后超出堆容量。
解决方案：
  1. 线程池恢复为 CPU 核心数 × 2，用异步处理来应对并发，而不是开更多线程
  2. 数据库连接池设为核心数的 2-3 倍（连接数不是越多越好，超过磁盘 IO 能力后加连接反而更慢）
  3. 堆内存从 2GB 调到 4GB（容器规格同步升级）
  4. 监控加上 Heap 使用率告警（> 80% 持续 5 分钟触发）
```

### 内存问题排查实用技巧汇总

排查内存问题时，可以按以下顺序快速定位。不同阶段关注点不同：

**快速定位阶段（5 分钟内）：**

```bash
# 1. 系统级：free -h 看 available 和 swap
# 2. 进程级：top 按内存排序（Shift+M），找 RSS 最大的进程
# 3. 趋势：pidstat -r 10 -p <pid>，看 RSS 是涨是稳
# 4. GC：jstat -gcutil <pid> 1000（Java）或 GODEBUG=gctrace=1（Go）
```

**深入分析阶段（15-30 分钟）：**

```bash
# 1. 堆 dump（Java，会暂停几十毫秒到几秒）
$ jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>

# 2. Go heap profile（不暂停）
$ curl http://localhost:6060/debug/pprof/heap > /tmp/heap.pb.gz
$ go tool pprof -http=:8080 /tmp/heap.pb.gz

# 3. 看 RSS 的详细组成
$ cat /proc/<pid>/smaps_rollup
# 关注 Anonymous（堆+栈）、Mapped（mmap 文件）、Shared（共享内存）

# 4. 检查是否有 FD 泄漏导致的内存增长
$ ls /proc/<pid>/fd | wc -l
# FD 数量持续增长通常意味着连接或文件泄漏
```

**生产环境排查的安全注意事项：**

```text
jmap -dump:live  会触发 Full GC，会在暂停期间产生大 IO，高峰期慎用
kill -3 <pid>    向 Java 进程发送 SIGQUIT 会打印线程 dump，但不暂停业务
strace -p <pid>  会严重拖慢进程，只在隔离环境中使用
perf record      对性能影响小（< 3%），可以在生产环境安全使用
```

一个可以记住的排查顺序：

```text
free 看全局 → top 找进程 → pidstat 看趋势
→ jstat/pprof 看 GC → dump 堆分析对象 → 定位代码修复
```

## 5. 数据库术语

### B+ 树索引是什么

MySQL InnoDB 常用 B+ 树索引。你可以把它理解成一本有目录的书。

没有索引时，数据库查一条记录可能要从头翻到尾。数据越多，越慢。有索引时，数据库先查目录，再跳到目标页，速度快很多。

但是索引不是越多越好。每个索引都要占磁盘，每次写入还要维护索引。读多写少的表可以多一些索引，写入很频繁的表要谨慎。

### Buffer Pool 是什么

Buffer Pool 是 MySQL InnoDB 在内存里缓存数据页和索引页的地方。

数据库快不快，很大程度取决于热数据能不能放进 Buffer Pool。热数据在内存里，查询就快；热数据放不下，就要频繁读磁盘，延迟会变差。

初学者可以这样记：

```text
索引决定能不能快速找到数据
Buffer Pool 决定找到数据时是否需要读磁盘
```

### 主从延迟是什么

很多系统使用主库写、从库读。主库写入后，通过 binlog 同步到从库。如果写入量太大，或者从库处理不过来，从库数据就会落后，这叫主从延迟。

主从延迟会带来一个常见问题：用户刚写完数据，立刻去读，从库还没同步到，于是用户看不到刚才的修改。

解决方案包括：

1. 写后短时间读主库。
2. 对关键查询使用强一致路径。
3. 监控复制延迟，延迟过高时降级。
4. 减少大事务和批量写入。

## 6. Redis 术语

### 热 Key 和大 Key

热 Key 是访问特别频繁的 Key。大 Key 是 Value 特别大的 Key。

热 Key 的问题是压力集中。Redis Cluster 有很多节点，但某个 Key 只在一个节点上，访问都打到这个节点，其他节点帮不上忙。

大 Key 的问题是操作慢。Redis 很多命令在单线程里执行，一个大 Key 的读取、删除、序列化可能阻塞其他请求。

常见解决方案：

| 问题 | 解决思路 |
| --- | --- |
| 热 Key | 本地缓存、Key 拆分、多级缓存 |
| 大 Key | 拆小、分页、异步删除、限制 Value 大小 |

### 缓存穿透、击穿、雪崩

| 问题 | 白话解释 | 解决方案 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，缓存没有，数据库也没有 | 缓存空值、布隆过滤器 |
| 击穿 | 一个热点 Key 过期，大量请求打到数据库 | 互斥锁、逻辑过期、提前刷新 |
| 雪崩 | 大量 Key 同时过期，数据库被打爆 | TTL 加随机值、分批刷新 |

这三个词初学者很容易混。可以这样记：

```text
穿透：查空气
击穿：打穿一个热点
雪崩：一大片同时塌
```

## 7. Kafka 和队列术语

### Topic、Partition、Consumer Group

| 术语 | 白话解释 |
| --- | --- |
| Topic | 一类消息的名字 |
| Partition | Topic 的分片 |
| Consumer Group | 一组消费者共同消费消息 |

Kafka 的并发能力和 Partition 强相关。一个 Consumer Group 中，同一个 Partition 同时只能被一个消费者消费。因此，如果 Topic 只有 3 个 Partition，同一个消费组最多有效并发 3 个消费者，再加消费者也没用。

### Lag 是什么

Lag 是消息积压量。它表示生产者写入的消息和消费者已经处理的消息之间差了多少。

Lag 增加说明消费速度低于生产速度：

```text
积压增长速度 = 生产速度 - 消费速度
```

如果每秒生产 10 万条，消费 7 万条，每秒就积压 3 万条。一小时就是 1.08 亿条。积压不是“等一下就好”，它是一个时间函数。

## 8. AI 推理术语

### Token 是什么

Token 可以粗略理解为模型处理文本的基本单位。不同模型的分词方式（tokenizer）不同，但有一些经验规则可以帮助估算：

- 中文：大约 1-2 个汉字对应 1 个 token（取决于模型和分词器，例如 GPT-4 通常 1 个汉字约 1 token，而早期模型可能 1 个汉字 2-3 个 token）
- 英文：大约 1 个单词对应 1-1.5 个 token，常见短词 1 个 token，长词可能被拆成多个子词

例如，"你好世界" 在 GPT-4 中大约是 4 个 token；"Hello world" 通常是 2 个 token。

> 提示：你可以使用 OpenAI 的 [Tokenizer 工具](https://platform.openai.com/tokenizer) 或 Hugging Face 的 tokenizer 库来精确计算特定文本的 token 数。在做容量评估时，建议用真实数据抽样统计，而不是只靠经验规则。

AI 成本通常按 token 计费，推理性能也按 token 吞吐衡量。因此 AI 容量评估不能只看请求数，还要看每次请求消耗多少 token。

### KV Cache 是什么

LLM 生成文本时，需要记住前面上下文的信息。KV Cache 就是把这些中间计算结果缓存起来，避免每生成一个 token 都从头计算。

它的好处是加速生成。代价是占用显存。上下文越长，并发越高，KV Cache 占用越大。

可以这样理解：

```text
模型权重占固定显存
KV Cache 随上下文长度和并发增长
batch 占用随同时处理请求增长
```

所以长上下文不是免费的。一个 128k context 的请求，可能比一个 4k context 的请求贵得多，也更容易挤爆显存。

### Batch 和 Continuous Batching

Batch 是把多个请求合在一起处理，提高 GPU 利用率。传统 batch 要等一批请求凑齐，可能增加等待时间。Continuous Batching 会在生成过程中动态加入和移除请求，更适合 LLM 推理。

吞吐和延迟之间有权衡：

```text
batch 大 → GPU 利用率高，吞吐高，但单个请求可能等更久
batch 小 → 响应快，但 GPU 可能吃不满
```

AI 推理容量的难点就在这里：你不能只追求吞吐，也不能只追求单请求低延迟，还要考虑成本。

## 9. 稳定性术语

### SLA、SLO、SLI、Error Budget

| 术语 | 白话解释 |
| --- | --- |
| SLI | 实际测量指标，比如成功率、P99 |
| SLO | 内部目标，比如 99.9% 可用 |
| SLA | 对客户承诺，通常带赔付 |
| Error Budget | 在目标内允许失败的额度 |

比如 SLO 是 99.9% 月可用性，一个月按 30 天计算有 30 × 24 × 60 = 43200 分钟，允许不可用时间大约是：

```text
43200 × (1 - 99.9%) = 43200 × 0.001 = 43.2 分钟
```

也就是说，一个月最多允许系统不可用约 43 分钟。这 43.2 分钟就是错误预算的一种表达。错误预算不是鼓励失败，而是让团队理性权衡稳定性和迭代速度：预算充足时可以大胆发布新功能，预算快用完时应该暂停高风险变更。

## 10. 一张记忆表

| 你看到的词 | 你应该想到的问题 |
| --- | --- |
| QPS/RPS | 每个请求背后消耗什么资源 |
| DAU | 高峰时到底有多少并发 |
| P99 | 哪些用户和路径正在变慢 |
| CPU Load | 是否有任务排队 |
| FD 上限 | 连接数是否会撞到文件描述符限制 |
| RSS / Heap / Page Cache | 进程真实内存、应用堆内存和文件缓存分别占多少 |
| Swap | 物理内存是否已经不够，开始用磁盘了 |
| Off-Heap / Direct Memory | GC 管不到的内存是否在偷偷增长 |
| GC 频率和暂停时间 | 对象分配速率是否过高，STW 是否在拉高 P99 |
| Full GC | 老年代是否被填满，是否有内存泄漏 |
| 分配速率（Allocation Rate） | 每秒创建多少对象，GC 能不能跟上 |
| Buffer Pool | 热数据是否放得进内存 |
| 主从延迟 | 写完能不能立刻读到 |
| 热 Key | 压力是否集中在一个节点 |
| Kafka Lag | 消费速度是否追得上生产 |
| TTFT | 用户多久看到 AI 第一个输出 |
| KV Cache | 长上下文和并发是否吃掉显存 |
| SLO | 稳定性目标到底是多少 |

学术语的目的不是背定义，而是形成条件反射。看到一个指标，就能想到它背后的资源、风险和处理方法。容量评估真正训练的，正是这种条件反射。
