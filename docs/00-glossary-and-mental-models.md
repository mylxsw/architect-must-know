# 预备章 先把容量评估里的专业词讲清楚

初学容量评估，最难的不是公式，而是术语。很多文章一上来就说 QPS、P99、CPU Load、Buffer Pool、GC、KV Cache、Error Budget，初学者看似读懂了，真正做事时却不知道这些词和自己的系统有什么关系。

所谓专业能力，本质上是能把抽象词汇还原成真实世界里的现象。你看到 P99，不只是知道它叫 99 分位延迟，而是能想到：是不是有一批用户正在变慢，线程池是不是被占住，下游是不是偶发抖动。你看到 Buffer Pool，不只是知道它是 MySQL 的缓存，而是能想到：热数据是否放得下，查询是不是开始读磁盘。

这一章先把常用词讲清楚。后面的章节再谈方法，就不会悬在空中。

---

## 1. 流量类术语

### QPS、RPS、TPS 到底有什么区别

这三个词经常混用，但它们的侧重点不同。

| 术语 | 全称 | 白话解释 | 常见场景 |
| --- | --- | --- | --- |
| QPS | Queries Per Second | 每秒查询数 | 搜索、读接口、数据库查询 |
| RPS | Requests Per Second | 每秒请求数 | HTTP API、网关 |
| TPS | Transactions Per Second | 每秒事务数 | 下单、支付、数据库事务 |

如果一个接口只是查商品详情，通常说 QPS 或 RPS 都可以。如果一个接口会创建订单、扣库存、写交易记录，叫 TPS 更贴切，因为它强调"事务"。

初学者可以先这样记：

```text
RPS 看入口请求
QPS 看查询压力
TPS 看业务事务
```

真正做容量评估时，不要纠结名字，而要问：这个数字背后会落到哪些资源上。比如 1000 RPS 的登录接口，可能每秒产生 1000 次密码校验、1000 次 Redis 查询、1000 次数据库读、1000 条登录日志。入口只有一个数字，资源消耗却是一串。

### DAU、MAU、CCU 为什么不能混用

| 术语 | 白话解释 | 关键点 |
| --- | --- | --- |
| DAU | 一天来过多少用户 | 不是同时在线 |
| MAU | 一个月来过多少用户 | 更偏产品规模 |
| CCU | 同时在线用户数 | 更接近容量压力 |

很多初学者会把"100 万 DAU"理解成"100 万并发"。这是严重误解。

一个有 100 万 DAU 的产品，可能晚高峰只有 5 万人同时活跃；也可能因为活动推送，短时间有 30 万人涌入。**容量评估要关心的是流量如何在时间上分布。**

一个常用估算是：

```text
峰值并发 ≈ DAU × 高峰活跃比例 × 平均使用时长(分钟) ÷ 高峰窗口时长(分钟)
```

假设 100 万 DAU，20% 用户在晚高峰活跃，平均每次使用 10 分钟，高峰窗口 2 小时（120 分钟）：

```text
峰值并发 ≈ 1000000 × 20% × 10 ÷ 120 ≈ 16667
```

这个数字不精确，但比拍脑袋可靠。**工程上很多事情不需要一开始就精确，需要先有量级判断。**

## 2. 延迟类术语

### 平均延迟为什么会骗人

假设有 100 个请求：99 个耗时 20ms，1 个耗时 8000ms。平均延迟 99.8ms，看起来不到 100ms。但那个 8 秒的请求对用户来说已经很糟糕，而且它可能占住连接、线程和内存，进一步拖慢系统。

### P50、P95、P99 怎么理解

| 指标 | 白话解释 | 你应该怎么用 |
| --- | --- | --- |
| P50 | 一半请求比它快 | 看普通用户体验 |
| P95 | 95% 请求比它快 | 看大多数用户是否稳定 |
| P99 | 99% 请求比它快 | 看尾部风险和系统抖动 |

> 怎么理解"99% 请求比它快"？假设你有 1000 个请求，按耗时从小到大排列，第 990 个请求的耗时就是 P99。也就是说，只有 10 个请求（1%）比这个值更慢。

如果 P50 很好，P99 很差，说明系统不是整体慢，而是有一部分请求特别慢。常见原因包括：

1. **某些请求参数导致慢 SQL。** 大多数查询走索引，但少数查询命中了全表扫描。
2. **缓存偶尔未命中。** 缓存命中时 1ms 返回，未命中时要回源查数据库 200ms。
3. **GC 偶尔暂停。** 堆内存压力大时，一次 Full GC 可能暂停几百毫秒甚至秒级。
4. **下游服务偶发抖动。** 微服务调用链越长，任何一个节点抖动都会传导到上游。
5. **队列里有任务积压。** 流量突增时，后进来的请求排在队尾，等待时间从毫秒级变成秒级。
6. **少数大对象处理很慢。** 100KB 和 1MB 的对象，处理时间可能差 10 倍以上。

初学者可以这样记：

```text
平均值看大概
P95 看体验
P99 看风险
```

容量评估中，P99 往往比平均值更重要。

### TTFT、TPOT 是 AI 系统里的延迟指标

AI 应用里，普通 HTTP 延迟不够用了。因为 LLM 请求不是一次返回完整结果，而是持续生成 token。

| 指标 | 全称 | 白话解释 |
| --- | --- | --- |
| TTFT | Time To First Token | 用户多久看到第一个字 |
| TPOT | Time Per Output Token | 后面每个 token 生成多快 |
| Tokens/s | Tokens Per Second | 每秒生成多少 token |

**TPOT 怎么算：**

```text
TPOT = (总生成时间 - TTFT) ÷ 生成的 token 数
```

举个例子：用户发了一个请求，1 秒后看到第一个 token（TTFT = 1s），之后又花了 9 秒生成了 100 个 token，那么 TPOT = 9 ÷ 100 = 90ms/token，换算成约 11 tokens/s。

**TPOT 多少算合理：**

| 级别 | TPOT | Tokens/s | 用户体感 |
| --- | --- | --- | --- |
| 优秀 | < 50ms | > 20 | 飞快，接近实时阅读 |
| 良好 | 50-100ms | 10-20 | 流畅，接近正常阅读速度 |
| 及格 | 100-200ms | 5-10 | 能用，但能感觉在"等" |
| 差 | > 200ms | < 5 | 明显"一个字一个字蹦" |

TTFT 决定用户觉得系统有没有反应。TPOT 决定用户觉得输出是否流畅。AI 容量评估必须单独看这些指标。

## 3. CPU 和操作系统术语

### CPU 使用率和 CPU Load 不一样

CPU 使用率表示 CPU 有多少时间在忙。CPU Load 表示有多少任务正在运行或等待运行。

可以用饭店类比：CPU 使用率像厨师有多忙，CPU Load 像厨房门口排了多少单。厨师忙不忙重要，排队多不多也重要。

在 Linux 中，Load Average 表示过去 1/5/15 分钟内处于运行或等待状态的平均任务数。判断公式：

```text
Load / CPU 核心数 = 负载率
```

| 负载率 | 状态 | 说明 |
| --- | --- | --- |
| < 0.7 | 健康 | 有充足余量处理突发流量 |
| 0.7 - 1.0 | 较忙 | 正常运行但余量不多 |
| > 1.0 | 过载 | 任务开始排队，延迟上升 |
| > 2.0 | 危险 | 严重排队，需要扩容或优化 |

但 Load 也要结合场景看。IO 等待（D 状态进程）也会让 Load 升高，看到 Load 高不能立刻说 CPU 不够，还要看 IO Wait 和进程状态。

### User CPU、System CPU、IO Wait 怎么看

| 指标 | 白话解释 | 常见原因 |
| --- | --- | --- |
| User CPU（us） | 业务代码在消耗 CPU | 计算、序列化、压缩、加密 |
| System CPU（sy） | 内核在消耗 CPU | 网络包处理、系统调用、上下文切换 |
| IO Wait（wa） | CPU 在等磁盘或网络 IO | 慢磁盘、大量读写、数据库压力 |
| Steal（st） | 虚拟机被宿主机"抢走"的 CPU | 超卖的云主机 |

```bash
# 最快的方式：top，看第 3 行
top
# 更精确的方式：mpstat，每秒采样一次
mpstat -P ALL 1
```

**生产环境健康范围：**

| 指标 | 健康 | 需要关注 | 需要介入 |
| --- | --- | --- | --- |
| User CPU | < 60% | 60-80% | > 80% |
| System CPU | < 10% | 10-20% | > 20% |
| IO Wait | < 5% | 5-20% | > 20% |
| Steal | < 1% | 1-5% | > 5% |

**一个真实的排查案例：** 一台 8 核 Web 服务器，用户反馈接口变慢。`top` 看到 CPU 总使用率 75%，看起来好像还好。但细看：us=20%，sy=15%，wa=38%。`iostat` 发现磁盘 `%util` 是 98%。最后定位到一个慢查询没走索引，全表扫描 200 万行。加了索引后，IO Wait 回到 3%。——如果只看 CPU 总使用率，根本发现不了问题。

### 上下文切换是什么

CPU 一次只能执行有限数量的任务。线程太多时，操作系统要不断把 CPU 从一个线程切到另一个线程，这就是上下文切换（Context Switch）。每次切换要保存和恢复线程状态，消耗几百到几千个 CPU 周期，还会导致 CPU 缓存失效。

上下文切换高通常意味着：线程池设得太大、锁竞争激烈、或短任务过多。

```bash
# 查看系统上下文切换
vmstat 1    # 关注 cs 列
```

> 📖 深入了解上下文切换的排查方法和案例，请阅读 [扩展：上下文切换深度解析](extensions/context-switch-deep-dive.md)

### 文件描述符（FD）为什么默认只有 1024

Linux 的"一切皆文件"设计意味着每个网络连接、管道、文件都需要一个 FD。默认上限 1024 是历史兼容性和系统保护的保守值。

对现代长连接服务来说，这个值太低了。一个 WebSocket 服务，每个客户端至少占 1 个 FD，默认上限只能接受几百个连接。

关键要记住：

```text
FD 上限决定你"能不能"打开这么多连接
内存和 CPU 决定你"撑不撑得住"这么多连接
```

## 4. 内存和 GC 术语

### 内存相关的常用术语

| 术语 | 层级 | 白话解释 |
| --- | --- | --- |
| RSS | 操作系统 | 进程实际占用的物理内存大小 |
| Heap | 应用运行时 | 程序动态分配对象的地方，膨胀是内存问题最常见的原因 |
| Page Cache | 操作系统 | Linux 用空闲内存缓存磁盘文件，内存紧张时自动释放 |
| Swap | 操作系统 | 把不活跃内存写到磁盘，一旦大量使用性能断崖式下跌 |
| Off-Heap | 应用运行时 | 绕过 GC 直接从操作系统分配的内存，不在 GC 管辖范围 |
| OOM | 操作系统 | 内存耗尽，OOM Killer 会杀掉占用最多的进程 |

> 初学者提示：`free -h` 看到 `available` 列比较低才需要担心。`used` 列高不代表内存不够，因为 Page Cache 被算在 `used` 里。

**判断内存是否异常的口诀：**

```text
涨而不退是泄漏
Swap 动了是紧张
GC 频繁是堆满
OOM 出手是崩溃
```

### GC 基本原理

GC（Garbage Collection）是垃圾回收，Java、Go、.NET 等语言会自动回收不再被引用的对象。自动回收很方便，但不是免费的——GC 要扫描和标记对象，消耗 CPU 和时间，某些算法还需要暂停所有业务线程（Stop-The-World）。

**常见 GC 算法：**

| GC 算法 | 使用者 | 特点 |
| --- | --- | --- |
| G1 GC | Java（9+ 默认） | 暂停时间可控，适合大多数场景 |
| ZGC / Shenandoah | Java（低延迟） | STW 亚毫秒级，但吞吐量略低 |
| 三色标记 + 并发清除 | Go | STW 微秒级，内存占用可能更高 |
| 引用计数 | Python、PHP | 无法处理循环引用 |

**GC 的关键指标：**

| 指标 | 白话解释 |
| --- | --- |
| Young GC 频率 | 多久回收一次年轻代 |
| Full GC 次数 | 回收整个堆的次数，出现就要警惕 |
| GC 暂停时间（STW） | 业务线程被暂停多久 |
| 分配速率 | 每秒分配多少内存，越高 GC 越频繁 |

### GC 为什么会影响容量

一个常见事故路径：

```text
流量增加 → 对象创建增加 → GC 变频繁 → 请求变慢 → 请求堆积 → OOM
```

GC 影响容量的两层机制：
- **STW 暂停直接增加延迟**：暂停期间所有在途请求都停住了，P99 经常被 GC 暂停拉起来。
- **GC 线程抢 CPU**：即使并发 GC 不暂停业务线程，GC 线程也要消耗 CPU，留给业务的就少了。

所以容量评估要关注单请求对象分配量。一个请求分配 1KB，1000 QPS 每秒分配 1MB，GC 压力很小。一个请求分配 100KB，1000 QPS 每秒分配 100MB，GC 就会忙个不停。

## 5. 数据库术语

### B+ 树索引是什么

MySQL InnoDB 常用 B+ 树索引。你可以把它理解成一本有目录的书。

没有索引时，数据库查一条记录可能要从头翻到尾。有索引时，先查目录再跳到目标页，速度快很多。

但索引不是越多越好。每个索引都要占磁盘，每次写入还要维护索引。读多写少的表可以多一些索引，写入很频繁的表要谨慎。

### Buffer Pool 是什么

Buffer Pool 是 MySQL InnoDB 在内存里缓存数据页和索引页的地方。

数据库快不快，很大程度取决于热数据能不能放进 Buffer Pool。热数据在内存里，查询就快；热数据放不下，就要频繁读磁盘，延迟会变差。

```text
索引决定能不能快速找到数据
Buffer Pool 决定找到数据时是否需要读磁盘
```

### 主从延迟是什么

很多系统使用主库写、从库读。主库写入后，通过 binlog 同步到从库。如果写入量太大或从库处理不过来，从库数据就会落后，这叫主从延迟。

主从延迟会带来一个常见问题：用户刚写完数据，立刻去读，从库还没同步到，于是看不到刚才的修改。

解决方案：写后短时间读主库、关键查询走强一致路径、监控复制延迟、减少大事务。

## 6. Redis 术语

### 热 Key 和大 Key

热 Key 是访问特别频繁的 Key。大 Key 是 Value 特别大的 Key。

热 Key 的问题是压力集中——Redis Cluster 有很多节点，但某个 Key 只在一个节点上，访问都打到这个节点。

大 Key 的问题是操作慢——Redis 单线程执行，一个大 Key 的读取、删除、序列化可能阻塞其他请求。

| 问题 | 解决思路 |
| --- | --- |
| 热 Key | 本地缓存、Key 拆分、多级缓存 |
| 大 Key | 拆小、分页、异步删除、限制 Value 大小 |

### 缓存穿透、击穿、雪崩

| 问题 | 白话解释 | 解决方案 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，缓存和数据库都没有 | 缓存空值、布隆过滤器 |
| 击穿 | 一个热点 Key 过期，大量请求打到数据库 | 互斥锁、逻辑过期、提前刷新 |
| 雪崩 | 大量 Key 同时过期，数据库被打爆 | TTL 加随机值、分批刷新 |

记忆口诀：

```text
穿透：查空气
击穿：打穿一个热点
雪崩：一大片同时塌
```

## 7. Kafka 和队列术语

### Topic、Partition、Consumer Group

| 术语 | 白话解释 |
| --- | --- |
| Topic | 一类消息的名字 |
| Partition | Topic 的分片 |
| Consumer Group | 一组消费者共同消费消息 |

Kafka 的并发能力和 Partition 强相关。同一个 Consumer Group 中，同一个 Partition 同时只能被一个消费者消费。因此，如果 Topic 只有 3 个 Partition，同一个消费组最多有效并发 3 个消费者，再加也没用。

### Lag 是什么

Lag 是消息积压量，表示生产者写入的消息和消费者已处理的消息之间差了多少。

```text
积压增长速度 = 生产速度 - 消费速度
```

如果每秒生产 10 万条，消费 7 万条，每秒就积压 3 万条。一小时就是 1.08 亿条。积压不是"等一下就好"，它是一个时间函数。

## 8. AI 推理术语

### Token 是什么

Token 是模型处理文本的基本单位。经验规则：

- 中文：大约 1-2 个汉字对应 1 个 token
- 英文：大约 1 个单词对应 1-1.5 个 token

> 提示：可以使用 OpenAI 的 [Tokenizer 工具](https://platform.openai.com/tokenizer) 精确计算。做容量评估时，建议用真实数据抽样统计。

AI 成本通常按 token 计费，推理性能也按 token 吞吐衡量。因此 AI 容量评估不能只看请求数，还要看每次请求消耗多少 token。

### KV Cache 是什么

LLM 生成文本时，需要记住前面上下文的信息。KV Cache 就是把这些中间计算结果缓存起来，避免每生成一个 token 都从头计算。

```text
模型权重占固定显存
KV Cache 随上下文长度和并发增长
batch 占用随同时处理请求增长
```

长上下文不是免费的。一个 128k context 的请求，可能比一个 4k context 的请求贵得多，也更容易挤爆显存。

### Batch 和 Continuous Batching

Batch 是把多个请求合在一起处理，提高 GPU 利用率。Continuous Batching 会在生成过程中动态加入和移除请求，更适合 LLM 推理。

```text
batch 大 → GPU 利用率高，吞吐高，但单个请求可能等更久
batch 小 → 响应快，但 GPU 可能吃不满
```

AI 推理容量的难点：不能只追求吞吐，也不能只追求低延迟，还要考虑成本。

## 9. 稳定性术语

### SLA、SLO、SLI、Error Budget

| 术语 | 白话解释 |
| --- | --- |
| SLI | 实际测量指标，比如成功率、P99 |
| SLO | 内部目标，比如 99.9% 可用 |
| SLA | 对客户承诺，通常带赔付 |
| Error Budget | 在目标内允许失败的额度 |

比如 SLO 是 99.9% 月可用性，一个月 43200 分钟，允许不可用时间：

```text
43200 × (1 - 99.9%) = 43.2 分钟
```

这 43.2 分钟就是错误预算。错误预算不是鼓励失败，而是让团队理性权衡稳定性和迭代速度：预算充足时可以大胆发布新功能，预算快用完时应该暂停高风险变更。

| --- | --- |
| QPS/RPS | 每个请求背后消耗什么资源 |
| DAU | 高峰时到底有多少并发 |
| P99 | 哪些用户和路径正在变慢 |
| CPU Load | 是否有任务排队 |
| FD 上限 | 连接数是否会撞到文件描述符限制 |
| RSS / Heap / Swap | 进程真实内存、堆内存、是否开始用磁盘 |
| GC 频率和暂停时间 | 对象分配速率是否过高，STW 是否在拉高 P99 |
| Buffer Pool | 热数据是否放得进内存 |
| 主从延迟 | 写完能不能立刻读到 |
| 热 Key | 压力是否集中在一个节点 |
| Kafka Lag | 消费速度是否追得上生产 |
| TTFT | 用户多久看到 AI 第一个输出 |
| KV Cache | 长上下文和并发是否吃掉显存 |
| SLO | 稳定性目标到底是多少 |

学术语的目的不是背定义，而是形成条件反射。看到一个指标，就能想到它背后的资源、风险和处理方法。容量评估真正训练的，正是这种条件反射。
