# 第一章 什么是容量评估

所谓容量评估，本质上不是问“系统能扛多少 QPS”，而是问一个更根本的问题：这个系统在未来某个规模下，是否还能以可接受的成本、可接受的稳定性、可接受的用户体验继续运行。

很多工程师在职业早期不太关心这个问题。原因很简单：系统规模小的时候，机器性能会替我们掩盖很多错误。代码写得粗糙一点，SQL 慢一点，Redis Key 设计随意一点，日志多打一倍，通常都不会立刻出事故。可是当一个系统从几千用户走向几十万用户、几百万用户，事情就变了。你会发现软件系统不是一个只存在于代码里的逻辑世界，它最终要落在 CPU、内存、磁盘、网络、数据库连接、GPU 显存、第三方 API 配额和云账单这些非常具体的东西上。

这就是容量评估的意义。它不是玄学，也不是资深工程师靠经验拍脑袋。归根结底，它是一套工程方法论：先建立用户行为模型，再推导资源消耗，再找到瓶颈，再设计扩容、降级和成本控制方案。

## 1. 容量评估到底在评估什么

容量评估，英文叫 Capacity Planning。简单讲，就是预测系统未来的资源消耗，并提前设计系统的承载能力。

这里有三个关键词。

第一，预测。容量评估不是系统已经崩了以后再去救火，而是在系统还没有达到那个规模之前，就大致知道它会在哪里出问题。

第二，资源消耗。一个系统消耗的不是单一资源，而是一组资源：CPU、内存、磁盘、网络、数据库、缓存、消息队列、对象存储、GPU、第三方 API 调用次数，以及云成本。

第三，承载能力。容量不是越大越好。一个系统当然可以通过多买机器提高承载能力，但如果每增长一倍用户，成本就增长三倍，这个系统在商业上也是不可持续的。

因此，容量评估的核心目标可以概括为六个字：不崩，不浪费。

| 目标 | 含义 | 初学者应该问的问题 |
| --- | --- | --- |
| 不崩 | 流量上涨时系统不会直接不可用 | 峰值流量来时，哪个资源会最先到上限 |
| 不浪费 | 不盲目购买机器和云资源 | 现在的资源利用率是否合理 |
| 可扩展 | 后续可以平滑扩容 | 横向加机器是否真的有效 |
| 可预测 | 知道什么时候会出现风险 | 按当前增长速度，多久后会撞墙 |
| 可量化 | 用数据而不是感觉做决策 | 我们的 QPS、P99、内存、成本分别是多少 |
| 可预算 | 能提前估算成本和毛利空间 | 每多一个活跃用户，要多花多少钱 |

很多公司早期靠“先上线再说”活下来，到了中后期却会被“先扩容再说”拖垮。前者是速度问题，后者是工程成熟度问题。

## 2. 为什么容量评估不能只看 QPS

这里有一个常见误解：很多人以为容量评估就是算 TPS 或 QPS。

这是不够的。

QPS 只是系统容量的入口指标，就像体温只是健康指标之一。一个人发烧可能是感冒，也可能是感染；一个系统 QPS 高，真正的瓶颈可能在数据库、Redis、网络带宽、磁盘 IO、线程池、GC，甚至云厂商的出网费用。

我在技术史中反复看到一个规律：真正决定系统规模的，往往不是最显眼的那个指标，而是最容易被忽略的底层约束。

早期互联网公司做搜索，看起来竞争的是搜索算法，实际上背后还要竞争网页抓取能力、索引构建能力、分布式存储能力、数据中心能力和成本控制能力。Google 之所以能把搜索做成全球级系统，并不只是因为 PageRank 这个算法，而是因为它把大规模计算、大规模存储和工程成本控制变成了一整套体系。

今天我们做 Web 系统、实时语音系统、AI 应用，也是同样的道理。表面上看是产品功能，底层看是资源模型。

容量评估，就是把这个资源模型看清楚。

## 3. 一个最小可用的容量模型

初学者不要一开始就追求复杂模型。一个能真正落地的容量模型，通常从四个问题开始。

1. 用户是谁：日活、月活、付费用户、免费用户、内部用户分别有多少。
2. 用户怎么用：高峰时段、核心路径、请求频率、单次行为持续时间是什么。
3. 每次使用消耗什么：CPU、内存、数据库读写、Redis、带宽、Token、对象存储分别消耗多少。
4. 增长以后谁先扛不住：哪一个资源最接近上限，扩容成本是多少。

可以把它写成一条链路：

```text
用户规模
→ 用户行为
→ 请求链路
→ 资源消耗
→ 系统瓶颈
→ 扩容方案
→ 成本模型
```

这个链路比“我们现在有多少 QPS”重要得多。因为 QPS 是结果，用户行为才是原因。

举一个简单例子。一个产品有 100 万 DAU，其中 20% 会在晚高峰活跃。每个活跃用户平均每分钟发起 5 次请求，那么峰值 QPS 大约是：

```text
QPS = 1000000 × 20% × 5 ÷ 60
    ≈ 16666
```

这个数字当然粗糙，但它已经比“100 万用户就要按 100 万并发设计”可靠得多。更重要的是，它告诉你可以从哪里修正模型：高峰活跃比例是不是 20%，每分钟请求数是不是 5，是否存在突发活动，是否有爬虫和异常流量。

## 4. 容量评估的实现原理

容量评估背后的原理其实很朴素：系统资源是有限的，用户行为会把压力转化成资源消耗，某个资源最先到达上限时，系统就会出现拐点。

这个拐点通常有三个特征。

第一，延迟先上升。系统不是突然不可用，而是 P95、P99 先变差。用户觉得“偶尔卡一下”，实际上资源已经接近饱和。

第二，错误率随后上升。超时、连接失败、队列积压、数据库死锁、Redis 超时开始出现。

第三，故障会传播。一个服务慢了，上游请求堆积；上游重试，又进一步压垮下游；某个节点重启，流量打到剩余节点，剩余节点也开始抖动。

因此，容量评估不是静态地算一个数字，而是研究系统在压力增加时如何变化。

生产环境里常见的容量曲线是这样的：

```text
低负载区：延迟稳定，资源有余量
健康增长区：QPS 增加，资源利用率近似线性上升
拐点区：延迟开始非线性上升，P99 抖动
失稳区：错误率上升，队列积压，重试风暴
崩溃区：服务不可用，依赖被拖垮
```

一个好的容量评估，就是要在拐点区之前给出预警，而不是等系统进入崩溃区。

## 5. 生产中如何使用容量评估

容量评估在生产中至少有五种典型用法。

第一，版本上线前评估。一个新功能会增加多少请求、多少存储、多少下游调用、多少 token 消耗。上线评审不能只问“功能测过了吗”，还要问“容量模型变了吗”。

第二，大促或活动前评估。活动会把流量集中到短时间窗口，平均流量没有意义，峰值和突发流量才有意义。

第三，增长规划。产品预计三个月增长 5 倍，工程团队要提前知道数据库、缓存、网关、队列和云成本分别什么时候需要扩容。

第四，成本治理。容量评估不是只服务稳定性，也服务成本。资源利用率长期只有 5%，说明浪费；资源利用率长期 90%，说明风险高。

第五，架构演进。什么时候需要分库分表，什么时候需要引入 Kafka，什么时候需要从同步链路改成异步链路，什么时候需要模型路由，都应该由容量模型推动，而不是由技术热情推动。

## 6. 初学者最容易踩的坑

第一个坑，是把 DAU 当并发。DAU 是一天内来过多少人，并发是同一时刻有多少人在线。两者之间要经过高峰比例、使用时长和请求频率的换算。

第二个坑，是只看平均值。平均响应 100ms 不代表系统健康。真正决定用户体验和系统风险的是 P95、P99，以及它们在高峰时段的变化。

第三个坑，是只算业务库，不算日志和监控。很多系统最先涨爆的不是 MySQL，而是日志、链路追踪和对象存储。

第四个坑，是以为扩容一定线性有效。应用服务可以横向扩容，但数据库连接、热点 Key、单分区 Kafka、GPU KV Cache 可能不会跟着线性扩展。

第五个坑，是不把成本纳入容量评估。特别是 AI 产品，每一次调用都可能产生真实的 token 或 GPU 成本。没有成本模型的增长，可能越增长越亏。

## 7. 本章检查清单

你可以用下面这份清单检查一个系统是否具备基本容量意识。

| 问题 | 是否有答案 |
| --- | --- |
| 当前峰值 QPS、P95、P99 是多少 |  |
| 高峰活跃用户比例是多少 |  |
| 单个核心用户路径会调用哪些服务 |  |
| 每次请求平均消耗多少数据库查询 |  |
| Redis 内存和命中率是多少 |  |
| 日志每天增长多少 GB |  |
| 哪个资源最接近上限 |  |
| 扩容一倍需要增加多少成本 |  |
| 系统拐点在哪里 |  |
| 出现过载时如何限流和降级 |  |

如果这些问题都答不上来，说明系统还没有真正做过容量评估。它也许今天能跑，但你还不知道它为什么能跑，也不知道它什么时候不能跑。

容量评估的价值就在这里：它把运气变成方法，把感觉变成数据，把救火变成设计。
