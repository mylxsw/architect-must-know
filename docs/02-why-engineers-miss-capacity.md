# 第二章 为什么很多工程师不懂容量评估

很多工程师不懂容量评估，并不是因为他们不聪明，而是因为他们长期处在一个被小规模系统保护的环境里。用户少、数据少、流量低，系统里的许多问题都会被机器性能掩盖。一个慢 SQL、一个不合理的缓存、一个没有上限的队列，在小规模时都像是无伤大雅的小问题。

但是工程系统有一个特点：规模会改变问题的性质。

在几百 QPS 时，慢一点只是慢一点；在几万 QPS 时，慢一点可能导致线程池耗尽、请求堆积、重试风暴和连锁故障。在几 GB 数据时，表设计不合理只是查询慢；在几 TB 数据时，它可能让归档、备份、迁移和统计都变成灾难。

## 1. 第一个误解：容量评估就是 QPS

很多人以为容量评估就是算 QPS 或 TPS。

QPS 只是系统容量的一个入口指标。一个系统 QPS 高，真正的瓶颈可能在数据库、Redis、网络带宽、磁盘 IO、线程池、GC，甚至云厂商的出网成本。

举一个例子。两个系统都是 1 万 QPS，但容量压力可能完全不同。

| 系统 | 请求特征 | 真实压力 |
| --- | --- | --- |
| 静态内容系统 | 大量 CDN 命中，源站少量回源 | 主要压力在 CDN 和带宽 |
| 订单系统 | 每次请求写库、扣库存、发消息 | 压力在数据库事务、锁和队列 |
| AI 生成系统 | 每次请求生成 1000 token | 压力在 GPU、token 成本和排队 |
| 实时语音系统 | 长连接持续上传音频 | 压力在连接数、带宽、ASR 和流式返回 |

所以，QPS 只是入口。真正的容量评估要问：每个请求背后到底消耗了什么。

## 2. 第二个误解：机器多就能解决问题

很多团队遇到容量问题，第一反应是加机器。这个做法有时有效，但不能当成通用答案。

应用服务通常比较容易横向扩容，因为它们大多是无状态的。可是系统里有很多东西不是简单加机器就能线性扩展。

| 资源 | 为什么不能简单加机器 |
| --- | --- |
| MySQL 单库 | 写入、锁、事务和主从复制可能成为瓶颈 |
| Redis 热 Key | 热点集中在一个节点，其他节点帮不上忙 |
| Kafka 单分区 | 分区决定同一消费组的并发上限 |
| GPU 推理 | 显存、KV Cache 和 batch 调度限制吞吐 |
| 外部 API | 第三方配额和限速不由你控制 |
| 带宽 | 云厂商和机房出口有上限，也有成本 |

历史上很多大系统的演进都说明了这一点。搜索引擎不是靠简单堆机器成功的。抓取、索引、排序、存储、数据分片、容错和成本控制必须形成体系。单点扩容解决不了系统性问题。

生产中的正确做法是：先确认瓶颈，再决定扩容方式。

```text
应用 CPU 满 → 可能加应用机器
数据库连接满 → 可能要连接池治理或读写拆分
Redis 热 Key → 可能要 Key 拆分或本地缓存
Kafka 积压 → 可能要增加分区、优化消费者或降级生产
GPU 排队 → 可能要 batch、模型路由、限流或加卡
```

扩容不是目的，解决瓶颈才是目的。

## 3. 第三个误解：平均指标代表系统健康

很多工程师习惯看平均响应时间。平均值当然有用，但它很容易掩盖尾部问题。

比如一个接口平均响应 100ms，可能有两种情况：

```text
情况 A：所有请求都在 80ms 到 120ms 之间（标准差小，分布集中）
情况 B：99% 请求是 20ms，1% 请求是 8000ms（标准差大，有严重尾部）
```

两种情况的平均值都接近 100ms 左右：
- 情况 A：平均 ≈ 100ms
- 情况 B：平均 = 99% × 20 + 1% × 8000 = 19.8 + 80 = 99.8ms

平均值几乎一样，但用户体验和系统风险完全不同。情况 B 的慢请求可能占住线程、占住连接、触发重试，然后把问题放大。

容量评估要看分布：

1. P50 代表普通请求体验。
2. P95 代表大多数用户的尾部体验。
3. P99 代表系统风险。
4. Max 往往代表异常路径。

在生产中，很多容量问题最早不是表现为错误率，而是 P99 开始抖动。这个阶段如果能发现并处理，成本很低；等错误率上升、队列积压、服务重启，系统已经进入失稳区。

## 4. 第四个误解：只关注业务代码

很多工程师把系统理解为自己写的业务代码。实际上，生产系统远比代码复杂。

一次请求可能经过：

```text
DNS
→ CDN
→ 负载均衡
→ 网关
→ 应用服务
→ Redis
→ MySQL
→ Kafka
→ 第三方 API
→ 日志系统
→ 监控系统
```

任何一个环节都可能成为容量瓶颈。

比如日志系统。新手常常觉得日志只是“记录一下”，不会影响主流程。可是高峰时每秒几万请求，每个请求打印几 KB 日志，一天就可能产生 TB 级数据。日志采集、传输、索引和查询都会消耗资源。如果日志写入阻塞主线程，甚至会直接拖慢业务接口。

再比如监控和链路追踪。它们是系统的眼睛，但也不是免费的。如果采样率、字段和保留周期设计不好，观测系统本身也会变成成本和容量问题。

工程师必须意识到：生产系统里的每一个“顺手加一下”，乘以规模以后都可能变成大问题。

## 5. 第五个误解：容量问题是运维的事

容量评估不是运维一个人的事。

开发者写的代码决定了资源消耗模型。一个接口查几次数据库，一个任务一次处理多少数据，一个缓存 Key 是否有 TTL，一个重试策略是否有上限，这些都在代码和设计里。

SRE 可以建立监控、告警、扩容和演练机制，但如果业务代码没有容量意识，SRE 只能不断救火。

正确的分工应该是：

| 角色 | 责任 |
| --- | --- |
| 产品 | 说明用户规模、使用场景和业务优先级 |
| 开发 | 设计资源消耗可控的实现 |
| 架构师 | 建立系统级容量模型和演进路线 |
| SRE | 建立监控、告警、扩缩容和演练 |
| 财务/业务 | 提供成本边界和商业约束 |

容量评估是团队协作，不是某个岗位的孤立任务。

## 6. 为什么初学者特别容易忽略容量

初学者容易忽略容量，通常有几个原因。

第一，学习材料偏功能实现。很多教程教你如何写接口、连数据库、用 Redis，却很少告诉你这些东西在高并发和大数据量下会怎样失效。

第二，测试环境太小。测试库只有几百行数据，接口当然很快；真实库有几千万行，问题才会出现。

第三，反馈周期太长。容量问题往往在用户增长后才暴露，而不是写完代码立刻暴露。

第四，缺少指标。没有监控、没有压测、没有链路追踪，就只能凭感觉。

第五，团队文化只奖励交付功能，不奖励提前发现风险。结果是功能越做越多，系统边界越来越模糊。

解决方法也很朴素：把容量问题前置。

1. 需求评审时问容量影响。
2. 设计评审时画资源链路。
3. 上线前做关键路径压测。
4. 上线后观察指标趋势。
5. 事故后修正容量模型。

## 7. 从技术史看容量意识

我喜欢从技术史看问题，因为很多今天看似新的问题，历史上都发生过。

早期互联网系统从单机走向集群，本质上就是容量问题。搜索引擎从小规模网页检索走向全网搜索，也是容量问题。移动互联网时代，春节红包、秒杀、大促把系统推向极端峰值，还是容量问题。今天 AI 产品面临 token、GPU、长上下文和成本约束，仍然是容量问题，只是资源形式变了。

每一次技术浪潮都会带来新的瓶颈。

| 时代 | 典型瓶颈 |
| --- | --- |
| 早期 Web | 单机 CPU、数据库连接 |
| 移动互联网 | 高峰流量、缓存、消息队列 |
| 云原生 | 调度、弹性、服务治理 |
| 实时音视频 | 带宽、连接、延迟 |
| AI 应用 | GPU、token、KV Cache、成本 |

所以容量评估不是过时的运维技能，而是随着技术发展不断更新的工程基本功。

## 8. 一个典型事故：重试把系统压垮

很多容量事故不是因为用户突然多了十倍，而是因为系统内部把压力放大了。重试就是最典型的例子。

假设一个订单服务调用库存服务。平时订单服务每秒 1000 次请求库存服务。某一刻库存服务变慢，成功率下降。订单服务为了提高成功率，设置了最多重试 3 次。

表面上看，重试是一个好设计。实际上，如果没有退避和熔断，它会把下游压力放大：

```text
原始请求：1000 次/秒
每次最多重试 3 次（即失败后最多再试 3 次）
最坏请求量：1000 × (1 + 3) = 4000 次/秒
（1 次原始请求 + 3 次重试 = 每个请求最多产生 4 次调用）
```

库存服务本来已经慢了，现在又被打了 4 倍流量，结果更慢。订单服务等待库存服务返回，线程池被占满；用户端看不到结果，又刷新或重新提交；网关流量继续上涨。最后看起来像是“库存服务故障”，本质上是容量保护机制缺失。

生产中的正确做法包括：

1. 重试必须有上限。
2. 重试必须有指数退避和随机抖动。
3. 对不可重试错误不要重试，比如参数错误（HTTP 4xx）。
4. 对非幂等操作（如支付、扣款）要特别谨慎，重试可能导致重复执行。
5. 对下游错误率高的服务要熔断（短时间内直接返回失败，不再尝试调用）。
6. 重试要计入容量模型——如果平均重试率是 10%，容量规划就要多留 10% 余量。

一个简单的退避伪代码如下：

```python
import random
import time

def call_with_retry(fn, max_retries=3):
    for attempt in range(max_retries + 1):
        try:
            return fn()
        except TimeoutError:
            if attempt == max_retries:
                raise
            # 指数退避：第1次等0.1s，第2次等0.2s，第3次等0.4s
            base = 0.1 * (2 ** attempt)
            # 随机抖动：避免所有客户端在同一时刻重试
            jitter = random.uniform(0, base)
            time.sleep(base + jitter)
```

这段代码的重点不是 Python，而是两个思想：

1. **指数退避**（Exponential Backoff）：每次重试等待时间翻倍，给下游更多恢复时间。
2. **随机抖动**（Jitter）：让不同客户端的重试时间错开，避免"重试风暴"——所有客户端在同一时刻再次冲上去。

## 9. 如何让团队开始具备容量意识

容量意识不是靠一次培训形成的，而是靠流程不断强化。

我建议把下面几个问题写进技术方案模板：

1. 这个功能的高峰调用量预计是多少。
2. 每次调用会访问哪些下游。
3. 是否新增数据库写入、Redis Key、Kafka 消息或对象存储。
4. 是否有批量任务，批量大小上限是多少。
5. 失败后是否重试，重试会放大多少流量。
6. 是否有超时、限流、熔断和降级。
7. 是否有数据清理策略。
8. 是否有上线后的观测指标。

这些问题看似繁琐，其实是在帮助初学者建立工程条件反射。很多事故不是因为工程师不会写代码，而是写代码时没有问这些问题。

## 10. 本章检查清单

| 误解 | 正确认识 |
| --- | --- |
| 容量就是 QPS | QPS 只是入口，资源消耗才是核心 |
| 加机器就能解决 | 先找瓶颈，很多资源不能线性扩容 |
| 平均值代表健康 | 必须看 P95、P99 和错误率 |
| 只关注业务代码 | 网关、数据库、缓存、队列、日志都会成为瓶颈 |
| 容量是运维的事 | 产品、开发、架构、SRE 和业务都要参与 |
| 小流量没问题就安全 | 规模会改变问题性质 |

很多工程师不是不会做容量评估，而是还没有被训练去这样思考。一旦你开始从用户行为、资源消耗、瓶颈和成本看系统，你会发现容量评估并不神秘。它只是把真实世界的约束重新带回软件设计里。
