# 第三章 容量评估到底评估什么

所谓“评估容量”，不能只评估一个入口数字。一个成熟系统的容量评估，至少要看流量、存储、计算、内存、网络、数据库、缓存、消息队列和 AI 推理九类容量。

我认为这九类容量像一张地图。初学者容易只盯着地图上最显眼的城市，也就是 QPS；架构师要看到道路、桥梁、仓库、能源和成本。系统真正出问题时，常常不是大门进来的人太多，而是仓库满了、道路堵了、账单撑不住了。

## 1. 流量容量：系统入口有多大

流量容量是容量评估的起点，但不是终点。

常见指标包括：

| 指标 | 含义 |
| --- | --- |
| QPS | 每秒查询数 |
| TPS | 每秒事务数 |
| RPS | 每秒请求数 |
| DAU | 日活用户 |
| MAU | 月活用户 |
| CCU | 同时在线人数 |
| Peak Traffic | 峰值流量 |
| Average Traffic | 平均流量 |
| Burst Traffic | 突发流量 |

新手最容易犯的错误，是把 DAU 直接当并发量。一个产品有 100 万 DAU，并不表示有 100 万人同时在线。真正要看的是高峰时段有多少用户活跃，以及每个用户在这个时段会产生多少请求。

比较可靠的估算方式是：

```text
峰值 QPS = DAU × 高峰活跃比例 × 单活跃用户每分钟请求数 ÷ 60 × 峰值放大系数
```

峰值放大系数很重要。工作日和周末不同，普通日和大促不同，产品刚发版和稳定运行不同。很多事故不是平均流量太高，而是突发流量太集中。

生产建议：

1. 入口网关要区分正常用户、爬虫、内部任务和恶意流量。
2. 指标要分接口看，不要只看全站 QPS。
3. 对写接口、支付接口、登录接口单独建容量模型。
4. 保留突发冗余，通常不能把机器长期跑在 90% 以上。
5. 限流策略要提前做，而不是事故时临时加。

常见坑是压测只压一个读接口，然后宣布系统能扛 5 万 QPS。真实业务通常是混合流量，有读、有写、有慢查询、有外部依赖、有缓存未命中。只压一个接口，测到的常常不是系统容量，而是某个局部路径的最好情况。

## 2. 存储容量：数据会不会把系统拖垮

很多系统不是被流量打死的，而是被数据量拖死的。流量问题来得急，容易被发现；存储问题来得慢，容易被忽视。等到数据库磁盘满了、Redis 内存爆了、Kafka Topic 堆积了、ClickHouse Merge 跑不动了，团队才意识到自己从来没有认真算过数据增长。

存储容量需要评估这些维度：

| 维度 | 例子 |
| --- | --- |
| 每日新增数据 | 订单、消息、日志、文件 |
| 总存储量 | GB、TB、PB |
| 热数据 | 最近 7 天、30 天高频访问数据 |
| 冷数据 | 历史归档数据 |
| 索引大小 | MySQL 二级索引、全文索引 |
| 日志容量 | ELK（Elasticsearch, Logstash, Kibana）、ClickHouse、对象存储日志 |
| 对象存储 | 图片、音频、视频、附件 |
| 备份容量 | 全量备份、增量备份 |
| 副本数量 | 主从、三副本、跨机房复制 |

一个实用公式是：

```text
总容量 = 每条数据大小 × 每日新增条数 × 保留天数 × 副本系数 × 索引膨胀系数
```

比如，一条日志平均 2KB，每天 10 亿条，保留 30 天，三副本，索引和压缩后按 1.5 倍计算：

```text
2KB × 10亿 × 30 × 3 × 1.5 ≈ 270TB
```

这时你会发现，日志不是免费的。很多公司云账单里增长最快的部分，不是业务数据库，而是日志、监控和链路追踪数据。

生产建议：

1. 任何持续增长的数据都必须有保留周期。
2. 热数据和冷数据要分层，不能都放在昂贵存储里。
3. 日志采样、字段裁剪和索引策略要尽早设计。
4. 备份容量也要算，尤其是跨区域备份。
5. 删除策略要可执行，不能只写在文档里。

初学者要养成一个习惯：凡是会持续增长的东西，都要问三件事：每天增长多少，保留多久，谁来清理。没有清理策略的数据，迟早会变成事故。

## 3. 计算容量：CPU 和 GPU 到底够不够

计算容量主要看 CPU 或 GPU 是否足够处理业务逻辑。

不同系统的计算特征不同：

| 类型 | 例子 |
| --- | --- |
| CPU 密集型 | 视频编码、加密、压缩、复杂计算 |
| IO 密集型 | 数据库读写、文件读写 |
| 内存密集型 | Redis、实时分析 |
| GPU 密集型 | AI 推理、模型训练 |
| 网络密集型 | 网关、代理、音视频传输 |

很多初学者看 CPU，只看利用率。例如 CPU 使用率 80%，就认为 CPU 快满了。事实上，CPU 分析要细得多。

你至少需要理解：

| 指标 | 含义 |
| --- | --- |
| CPU Load | 运行队列压力，不等于 CPU 使用率 |
| User CPU | 用户态代码消耗 |
| System CPU | 内核态消耗 |
| Context Switch | 上下文切换次数 |
| Run Queue | 等待运行的线程队列 |
| Cache Miss | CPU 缓存未命中 |
| GC Stop The World | 垃圾回收暂停 |
| Thread Pool Saturation | 线程池饱和 |

一个 Java 服务 CPU 高，可能不是业务计算真的复杂，而是对象创建太多导致 GC 频繁。一个 Go 服务延迟上升，可能不是 CPU 不够，而是 goroutine 太多、锁竞争严重或者网络调用阻塞。

生产建议：

1. CPU 高时先分清 user、system、iowait、steal。
2. 用火焰图看热点函数，不要凭感觉优化。
3. 对 CPU 密集任务使用独立线程池或独立服务隔离。
4. 对加密、压缩、序列化等公共开销做基准测试。
5. AI 推理要用 token 吞吐和显存模型，而不是只看 HTTP QPS。

容量评估不是看到 CPU 高就加机器，而是要知道 CPU 为什么高。这就是高级工程师和普通工程师的差别。

## 4. 内存容量：最容易被忽视的风险

很多系统崩溃，不是 CPU 不够，而是内存出了问题。

内存问题通常有几种：

| 问题 | 表现 |
| --- | --- |
| 内存泄漏 | 内存持续上涨，不回落 |
| GC 压力 | 延迟抖动，P99 飙升 |
| Cache 失控 | 缓存越积越大 |
| 大对象 | 一次请求占用大量内存 |
| Swap | 系统变慢，延迟不可控 |
| OOM Killer | 进程被 Linux 杀掉 |
| 内存碎片 | 看似有内存，实际不可用 |

对 Java 程序，要理解 JVM Heap、Young GC、Old GC、Full GC。对 Go 程序，要理解 Go Heap、GC Pace、对象逃逸。对 Linux 进程，要看 RSS，而不是只看语言运行时内部的内存统计。

很多线上事故路径非常相似：

```text
流量上涨
→ 对象创建增加
→ GC 压力增大
→ 请求变慢
→ 请求堆积
→ 内存继续上涨
→ OOM
→ 服务重启
→ 流量打到剩余节点
→ 连锁故障
```

生产建议：

1. 对每个服务设置合理的内存 request 和 limit。
2. 禁止无限队列、无限缓存、无限批量。
3. 大对象上传、下载、解析必须做流式处理。
4. 定期做堆分析，观察对象增长趋势。
5. 在压测中加入长时间稳定性测试，专门观察泄漏。

内存容量不是“机器还有多少内存”这么简单。真正要看的，是一次请求会产生多少临时对象，峰值并发会把多少对象同时留在内存里，以及 GC 是否还能在可接受时间内完成回收。

## 5. 网络容量：开发者最容易低估的瓶颈

很多开发者习惯把网络当成透明的东西，好像请求发出去自然会回来。到了大规模系统里，网络本身就是核心资源。

你需要理解：

| 内容 | 含义 |
| --- | --- |
| 带宽 | Mbps、Gbps |
| RTT（Round-Trip Time） | 网络往返延迟 |
| TCP 连接数 | 长连接和短连接压力 |
| WebSocket | 长连接容量 |
| Connection Pool | 连接池大小 |
| SYN（Synchronize） Flood | 半连接攻击或异常流量 |
| NIC（Network Interface Card） 吞吐 | 网卡能力 |
| CDN（Content Delivery Network） 回源 | 源站压力 |
| Egress Cost | 云厂商出网费用 |

特别是 AI 系统和实时语音系统，网络容量往往比传统 Web 更重要。

比如语音流式系统，每个用户不是发一个 HTTP 请求就结束，而是持续上传音频流，同时接收识别结果或模型输出。这里要评估的不只是 QPS，而是同时连接数、单连接带宽、心跳频率、断线重连、backpressure 和网关连接状态管理。

一个简单估算是：

```text
总带宽 = 同时在线连接数 × 单连接平均带宽
```

如果 5 万个用户同时进行语音流式输入，每个连接平均上行 32kbps，那么仅上行带宽就是：

```text
50000 × 32kbps = 1.6Gbps
```

这还没有算协议开销、下行数据、TLS（Transport Layer Security）、重传和峰值波动。

生产建议：

1. 网关层要监控连接数、带宽、连接建立速率和连接失败率。
2. 长连接系统必须设计心跳和超时回收。
3. 客户端要做指数退避重连，避免故障时重连风暴。
4. 出网费用要纳入成本模型。
5. 对大文件、音视频和模型输出优先考虑 CDN 或分片传输。

实时系统的容量评估不能只看请求数，要看连接数和持续流量。

## 6. 数据库、缓存和队列：状态系统的容量

数据库容量是架构师绕不开的能力。需要评估单表容量、索引容量、Buffer Pool、连接数、慢查询、主从延迟、WAL（Write-Ahead Log）/Redo Log、Binlog、热点数据和分库分表。

一个常见错误是只看表里的数据大小，不看索引大小。很多 MySQL 表，索引占用空间比数据本身还大。查询性能也不是由“表有多大”单独决定，而是由查询模式、索引设计、Buffer Pool 命中率、磁盘 IO 和锁冲突共同决定。

数据库容量评估至少要回答：

1. 单表数据一年后有多少行。
2. 主要查询是否都能走索引。
3. 热数据能否放进 Buffer Pool。
4. 写入峰值会不会拖慢主从复制。
5. 如果单库撑不住，按什么维度拆分。
6. 拆分以后，跨分片查询怎么办。

Redis 容量评估则要关注 Key 数量、Value 大小、热 Key、大 Key、命中率、淘汰策略、内存碎片率、持久化开销和网络 IO。

```text
Redis 内存 ≈ Key 数量 × (平均 Key 大小 + 平均 Value 大小 + 对象元数据开销) × 碎片系数
```

其中对象元数据开销包括 Redis 内部数据结构（dictEntry、redisObject 等），通常每个 Key 额外占用 50-100 字节。碎片系数通常在 1.2-2.0 之间。

> 初学者提示：不同数据结构的内存开销差异很大。String 类型最简单，Hash/Set/ZSet 在元素少时会使用紧凑编码（ziplist/listpack），元素多时切换为标准结构，内存会突然增长。可以用 `MEMORY USAGE key` 命令查看单个 Key 的实际内存占用。

Kafka、RabbitMQ 这类消息队列要关注 Topic 分区数、生产速度、消费速度、积压容量、Retention、副本数、Broker 容量和磁盘吞吐。

```text
积压增长速度 = 生产速度 - 消费速度
```

如果生产速度是每秒 10 万条，消费速度是每秒 7 万条，那么每秒积压 3 万条。持续一小时，就是 1.08 亿条。队列积压不是暂时现象，而是一个时间函数。

### 6.1 MySQL 为什么会慢：从一条查询说起

初学者理解 MySQL 容量，最好不要一开始就背参数。先看一条查询在数据库里发生了什么。

假设有一条 SQL：

```sql
select * from orders
where user_id = 10001
  and status = 'paid'
order by created_at desc
limit 20;
```

这条 SQL 快不快，取决于几个问题。

第一，有没有合适的索引。如果只有 `user_id` 索引，数据库能快速找到这个用户的订单，但还要在这个用户的订单里筛选 `status`，再按 `created_at` 排序。如果用户订单很多，就会慢。

第二，索引顺序是否匹配查询。如果有联合索引：

```text
(user_id, status, created_at)
```

数据库就可以先按用户定位，再按状态过滤，最后直接按时间顺序取前 20 条。这比扫描后排序快得多。

第三，热数据是否在 Buffer Pool 里。如果索引页和数据页在内存里，查询就快；如果频繁读磁盘，P99 会明显变差。

第四，是否有锁冲突。如果同一批订单正在被大量更新，查询可能受到事务和锁的影响。

所以 MySQL 容量不是“表有多少行”这么简单，而是：

```text
数据量
× 查询模式
× 索引设计
× 热数据命中率
× 写入压力
× 锁和事务
```

生产中，你可以按这个顺序排查慢查询：

1. 用慢查询日志找到 SQL。
2. 用 `EXPLAIN` 看是否走索引（`EXPLAIN` 会显示 MySQL 的查询执行计划，告诉你它打算怎么找数据）。
3. 看扫描行数是否远大于返回行数（如果扫描 100 万行只返回 20 行，说明索引可能有问题）。
4. 看是否出现 filesort、temporary（这意味着 MySQL 需要额外的排序或临时表操作，通常比较慢）。
5. 看 Buffer Pool 命中率和磁盘 IO。
6. 看是否有锁等待。
7. 看同一时间是否有批量任务或大事务。

一个常见误区是：慢了就加索引。索引能提高读性能，但会增加写入成本和存储成本。订单表每增加一个二级索引，每次写入订单、更新状态都要维护它。读多写少的表可以多索引，写入高峰明显的表要谨慎。

### 6.2 Redis 为什么会抖：单线程和内存模型

Redis 快，是因为它主要在内存里工作，并且用高效的数据结构和事件循环处理请求。但 Redis 快不等于不会出问题。

> 注意：Redis 6.0 以后引入了多线程 IO（用于网络读写），但命令执行仍然是单线程的。这意味着一个慢命令（如操作大 Key、执行 `KEYS *`）仍然会阻塞其他所有请求的执行。Redis 7.0 进一步优化了多线程能力，但核心的单线程命令执行模型没有改变。

Redis 的容量风险主要来自四件事。

第一，内存不是只等于 Value 大小。一个 Key 除了 Value，还有对象头、字典、过期时间、内存分配器碎片等开销。你以为 1000 万个 100B 的 Value 只占 1GB，实际可能远不止。

第二，大 Key 会阻塞。比如一个 List 有 100 万个元素，或者一个 String 有几十 MB，读取、删除、序列化都可能拖慢 Redis 主线程。

第三，热 Key 会让集群失衡。Redis Cluster 有很多节点，但一个 Key 只落在一个节点上。某个 Key 每秒被访问几十万次，这个节点会很忙，其他节点帮不上忙。

第四，持久化有成本。RDB（Redis Database Backup）快照、AOF（Append Only File） rewrite 都可能带来 CPU、内存和磁盘压力。

可以用一个例子理解 Redis 内存估算。假设系统有 500 万个用户配额 Key，每个 Key 平均：

```text
Key 名称：40 字节
Value（String 类型）：100 字节
Redis 对象元数据（dictEntry + redisObject + SDS 头等）：约 80-100 字节
```

单个 Key 实际占用（含碎片，按 1.5 倍估算）：

```text
(40 + 100 + 100) × 1.5 ≈ 360 字节
```

总内存：

```text
500万 × 360B ≈ 1.8GB
```

如果再加上副本、预留空间和增长余量，可能要准备 5GB 以上。这就是为什么 Redis 不能只按 Value 大小估算——对象元数据和内存碎片可能让实际占用翻倍。

生产中要建立几个习惯：

1. 所有临时 Key 必须有 TTL（Time To Live）。
2. 定期扫描 big key 和 hot key。
3. Value 大小要有上限。
4. 不在线上使用 `keys *`。
5. 删除大 Key 用异步删除或分批删除。
6. 热 Key 用本地缓存、Key 拆分或多级缓存。

Redis 的本质不是“快”，而是“用内存换时间”。既然用了内存，就必须认真算内存。

### 6.3 Kafka 为什么会积压：分区、消费和时间函数

Kafka 常被说成削峰填谷的工具。这个说法没错，但容易让初学者误解：好像只要加了 Kafka，峰值就自然消失了。

实际上，Kafka 只是把压力从同步链路转移到了异步链路。压力没有消失，只是换了形式。

Kafka 容量要看三件事。

第一，生产速度。每秒写入多少消息，每条消息多大。

第二，消费速度。消费者每秒能处理多少消息，处理一次要调用哪些下游。

第三，积压恢复时间。如果高峰积压了 1 亿条消息，低峰时多久能追平。

公式很简单：

```text
积压增长速度 = 生产速度 - 消费速度
恢复时间 = 积压总量 ÷ (消费速度 - 生产速度)
```

举例：

```text
高峰生产：100000 条/秒
高峰消费：70000 条/秒
积压速度：100000 - 70000 = 30000 条/秒
高峰持续：1 小时 = 3600 秒
积压总量：30000 × 3600 = 1.08 亿条
```

如果低峰生产降到 30000 条/秒，消费能力仍是 70000 条/秒，那么净恢复速度是：

```text
恢复速度 = 消费速度 - 生产速度 = 70000 - 30000 = 40000 条/秒
```

恢复时间：

```text
1.08亿 ÷ 40000 = 2700 秒 = 45 分钟
```

这就是一个完整的队列容量判断。只说“Kafka 积压了”没有意义，要知道积压增长速度和恢复时间。

Kafka 还有一个关键概念：Partition 决定消费并发上限。同一个 Consumer Group 中，一个 Partition 同时只能由一个消费者消费。如果 Topic 只有 6 个 Partition，那么同一消费组最多 6 个消费者有效。你加 20 个消费者，也只有 6 个在干活，剩下 14 个处于空闲状态。

> 为什么这样设计？因为 Kafka 保证同一 Partition 内消息的顺序性。如果多个消费者同时消费一个 Partition，就无法保证消息按顺序处理。这是 Kafka 在吞吐和顺序性之间的设计权衡。

生产建议：

1. Topic 分区数要按未来吞吐规划。
2. 消息体不要太大，大文件放对象存储，消息里放 URL 或 ID。
3. 消费者要幂等，因为消息可能重复消费。
4. 失败消息进入重试队列或死信队列。
5. 监控不仅看 lag，还要看 lag 恢复速度。
6. 高峰时允许低优先级 Topic 延迟，保护核心 Topic。

Kafka 不是免费的缓冲垫。它帮你争取时间，但你最终还是要把消息处理掉。

## 7. AI 系统容量：新的瓶颈模型

如果说传统 Web 系统的核心指标是 QPS，那么 AI 推理系统的核心指标就变成了 Token。

AI 系统和传统系统最大的不同是：请求之间差异巨大。一个普通 HTTP 请求可能几十毫秒结束，而一个 LLM（Large Language Model）请求可能持续几十秒；一个用户输入 200 个 token，另一个用户可能输入 10 万 token；有的请求只生成一句话，有的请求要生成几千字。

AI 系统容量要评估：

| 维度 | 说明 |
| --- | --- |
| Token 吞吐 | 每秒处理多少输入和输出 token |
| GPU 显存 | 模型权重、KV Cache、batch 占用 |
| Context 长度 | 8k、32k、128k 带来不同成本 |
| 并发生成数 | 同时有多少请求在生成 |
| Batch Size | 批处理大小影响吞吐和延迟 |
| KV Cache | 长上下文推理的重要成本 |
| TTFT | Time To First Token |
| TPOT | Time Per Output Token |

比如，一个模型在单卡上对单个请求的生成速度是 100 tokens/s。如果平均每个请求生成 500 tokens，那么单个请求需要 5 秒才能完成。如果没有 batching（批处理），单卡每秒只能完成 0.2 个请求。

实际上，通过 batching 可以同时处理多个请求，提高总吞吐。比如 batch size 为 8 时，虽然每个请求的生成速度可能从 100 tokens/s 降到 60 tokens/s，但总吞吐变成 8 × 60 = 480 tokens/s，远高于单请求的 100 tokens/s。这就是 AI 推理容量的核心权衡：吞吐和延迟之间的平衡。

生产建议：

1. 对不同模型建立 token 成本表。
2. 区分输入 token、输出 token、长上下文和工具调用成本。
3. 对免费用户设置配额和降级策略。
4. 用小模型优先、缓存、摘要压缩和模型路由控制成本。
5. 监控 TTFT、TPOT、Tokens/s 和 GPU 显存。

传统 SaaS 的边际成本可能很低，但 AI 产品每一次生成都在消耗真实 GPU 时间或 API token。用户越活跃，成本越高。如果没有配额、缓存、模型路由、batching 和降级策略，产品越成功，亏损可能越严重。

### 7.1 为什么 AI 系统不能用传统 QPS 思维

传统接口通常有比较稳定的处理时间。比如查询商品详情，可能 50ms 到 200ms 返回。AI 请求则不同。

同样是一次请求，差异可能非常大：

| 请求 | 输入 | 输出 | 特征 |
| --- | --- | --- | --- |
| 简短改写 | 100 token | 80 token | 很快，成本低 |
| 长文总结 | 8000 token | 1000 token | 输入长，KV Cache 大 |
| 代码生成 | 2000 token | 3000 token | 输出长，占用生成时间 |
| 多轮对话 | 16000 token | 500 token | 上下文成本高 |

HTTP 网关看到的都是 1 个请求，但推理层看到的资源消耗完全不同。因此 AI 容量至少要拆成四个指标：

```text
请求数
输入 token 数
输出 token 数
上下文长度
```

其中输出 token 通常更影响生成时间，因为模型要一个 token 一个 token 生成。输入 token 更影响预填充阶段和 KV Cache。上下文长度则会影响显存占用。

### 7.2 GPU 显存到底被什么占用了

初学者容易以为显存只放模型。实际上推理时显存大致被几类东西占用：

| 显存项 | 是否固定 | 说明 |
| --- | --- | --- |
| 模型权重 | 基本固定 | 模型越大，占用越高 |
| KV Cache | 随请求变化 | 上下文越长、并发越高，占用越高 |
| Batch 激活 | 随 batch 变化 | 同时处理请求越多，占用越高 |
| 框架和临时缓冲 | 部分变化 | 推理框架、CUDA buffer 等 |

可以用一个简化模型记住：

```text
总显存 ≈ 模型权重 + 并发数 × 上下文长度 × 每层每token的KV大小 × 层数 + 运行时开销
```

简化版：

```text
总显存 ≈ 模型权重（固定） + KV Cache（随并发和上下文增长） + 运行时开销
```

这个公式不用于精确计算，但能帮你理解为什么长上下文和高并发会很快吃掉显存。

比如你把 context 从 8k 提到 128k，不是“只是允许用户多输入一点”。它会显著增加 KV Cache，占用更多显存，降低并发，推高成本。

### 7.3 TTFT 和 TPOT 如何定位问题

AI 体验可以拆成两个阶段。

第一阶段是看到第一个 token 之前，这就是 TTFT。TTFT 高，常见原因包括：

1. 请求排队。
2. 输入上下文太长。
3. 模型冷启动。
4. batch 调度等待。
5. 上游 ASR（Automatic Speech Recognition） 或检索耗时。

第二阶段是持续生成过程，这主要看 TPOT。TPOT 高，常见原因包括：

1. 输出太长。
2. GPU 利用率不合理。
3. batch 过大导致单请求变慢。
4. 模型太大。
5. 推理框架效率低。

排查时可以这样做：

```text
TTFT 高，先看 queue time 和输入长度
TPOT 高，先看模型吞吐和 batch 设置
成本高，先看输出 token、模型选择和重复请求
显存高，先看上下文长度和并发
```

### 7.4 AI 容量优化的四个杠杆

AI 系统优化不只是“加 GPU”。常见杠杆有四类。

第一，减少不必要的 token。

1. 裁剪上下文。
2. 对历史对话做摘要。
3. 缩短系统提示词。
4. 限制输出长度。

第二，用合适的模型。

1. 简单分类用小模型。
2. 格式化任务用小模型。
3. 复杂推理才用大模型。
4. 高价值用户优先使用高质量模型。

第三，提高推理效率。

1. Continuous batching。
2. Prefix cache。
3. 量化。
4. 更高效的推理框架。

第四，控制产品策略。

1. 免费用户配额。
2. 高峰排队。
3. 异步处理非实时任务。
4. 对滥用行为限流。

这里最重要的认识是：AI 容量优化是产品、工程和商业一起做的事。工程团队单独优化 GPU，不如产品层面减少低价值 token 更有效。

## 8. 本章检查清单

| 类别 | 必须回答的问题 |
| --- | --- |
| 流量 | 峰值 QPS、突发倍数、接口比例是多少 |
| 存储 | 每天新增多少数据，保留多久，副本几份 |
| 计算 | CPU/GPU 瓶颈来自哪里，是否可横向扩容 |
| 内存 | 单请求内存、缓存、GC、泄漏风险如何 |
| 网络 | 带宽、连接数、出网费用是否可控 |
| 数据库 | 单表增长、索引、连接数、主从延迟如何 |
| Redis | Key 数量、热 Key、大 Key、淘汰策略如何 |
| Kafka | 生产消费速率、分区、积压恢复时间如何 |
| AI | token 吞吐、显存、TTFT、TPOT、成本如何 |

容量评估不是把这些指标背下来，而是知道它们如何互相影响。流量增加会带来计算增加，计算变慢会导致队列堆积，队列堆积会增加存储，存储膨胀会提高成本。系统是一个整体，容量评估也必须看整体。
