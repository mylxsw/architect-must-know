# 第四章 真正高级的容量评估能力

前两章讲的是“容量评估是什么”和“要评估哪些资源”。这一章要讲更关键的问题：怎么评估。

新手容易从组件出发：MySQL 怎么优化，Redis 怎么扩容，Kafka 怎么调参数。高级工程师会从用户行为出发。差别就在这里。组件只是结果，用户行为才是压力的源头；组件优化只是手段，系统目标才是判断标准。

## 1. 建立用户行为模型

容量评估的第一步，不是算机器，而是画出用户行为链路。

例如，一个实时语音 AI 产品，用户按下快捷键开始输入：

```text
按下 Fn
→ 建立 WebSocket 连接
→ 上传音频流
→ 实时 ASR
→ LLM 后处理
→ 流式返回结果
→ 客户端展示
→ 写入会话记录
```

每个环节都会消耗资源：

| 环节 | 资源消耗 |
| --- | --- |
| WebSocket | 长连接、内存、网关连接数 |
| 音频流 | 上行带宽、包处理 |
| ASR | CPU/GPU、推理延迟 |
| LLM | token、GPU 显存、KV Cache |
| 后处理 | CPU、规则引擎 |
| Redis Session | 内存、过期策略 |
| 数据库存储 | 写入、索引、归档 |
| 日志监控 | 存储、查询、成本 |

这才是容量评估的正确入口。用户不是抽象的 DAU，而是一组行为。行为不是抽象的请求，而是一条资源消耗链路。

一个可落地的用户行为模型通常包括：

1. 用户分层：免费用户、付费用户、企业用户、内部用户。
2. 行为路径：首页浏览、搜索、下单、上传、生成、导出。
3. 行为频率：每天几次，每次持续多久，高峰集中在哪里。
4. 请求比例：读写比例、缓存命中和未命中比例、同步和异步比例。
5. 数据规模：一次行为产生多少数据、日志、消息、文件或 token。
6. 异常行为：重试、刷新、重复提交、断线重连、爬虫和攻击流量。

生产中可以用埋点、日志和链路追踪来校准这个模型。模型一开始可以粗糙，但必须能被真实数据修正。容量评估最怕的是一直停留在会议室里的想象。

## 2. 找到真正的瓶颈

瓶颈定位是容量评估中最能拉开差距的能力。

普通工程师看到系统慢，会说：“CPU 高了，加机器吧。”

高级工程师会问：

1. CPU 高是用户态还是内核态。
2. 是业务计算、GC、序列化、加密，还是日志。
3. 是所有节点都高，还是某几个节点高。
4. 增加机器后，瓶颈是否会转移到数据库。
5. 如果 QPS 翻倍，哪个资源先到上限。
6. 扩容是否线性有效。

系统瓶颈通常遵循木桶原理。最短的木板可能是数据库连接数，也可能是 Redis 热 Key，也可能是 Kafka 分区数，也可能是 GPU KV Cache，也可能是云厂商带宽上限。

定位瓶颈可以按这个顺序做：

```text
用户体验指标
→ 入口流量指标
→ 应用资源指标
→ 下游依赖指标
→ 数据系统指标
→ 基础设施指标
→ 成本指标
```

举一个常见案例。某个接口 P99 从 200ms 涨到 2s，CPU 看起来只有 50%，很多人会以为机器还很空。进一步看链路追踪，发现 90% 时间耗在 MySQL 查询；再看 MySQL，Buffer Pool 命中率下降，磁盘读 IO 增加；再看 SQL，发现一个新功能增加了按状态和时间范围的查询，但索引顺序不匹配。这个问题的瓶颈不在应用 CPU，而在数据库查询路径。

生产建议：

1. 所有容量判断都要有指标证据。
2. 不要只看平均值，要看 P95、P99 和错误率。
3. 所有外部依赖都要有单独监控。
4. 先定位瓶颈，再决定扩容或优化。
5. 每次优化后都要复测，看瓶颈是否转移。

容量评估要做的，就是在事故发生之前找到那块短板。

## 3. 建立压测体系

没有压测的容量评估，大概率只是猜测。

常见压测工具包括：

| 工具 | 用途 | 语言/生态 |
| --- | --- | --- |
| wrk | HTTP 高性能压测 | C，适合极限吞吐测试 |
| k6 | 现代压测脚本，适合场景化测试 | Go + JS 脚本 |
| JMeter | 企业传统压测，GUI 操作 | Java |
| Locust | Python 用户行为模拟 | Python |
| vegeta | Go 生态常用压测，支持恒定速率 | Go |
| hey | 简单 HTTP 压测，适合快速验证 | Go |
| Gatling | 高性能场景化压测 | Scala/Java |

> 选择建议：初学者从 wrk（简单快速）或 k6（脚本灵活）开始。如果需要模拟复杂用户行为（登录→浏览→下单），k6 或 Locust 更合适。JMeter 功能全面但学习曲线较陡。

压测也有不同类型：

| 类型 | 目的 |
| --- | --- |
| 阶梯压测 | 逐步增加流量，找到拐点 |
| 峰值压测 | 验证系统能否扛住峰值 |
| 稳定性压测 | 长时间运行，观察泄漏和抖动 |
| 故障压测 | 模拟依赖异常 |
| 混沌工程 | 验证系统在故障下的韧性 |

一份好的压测报告，不应该只写“系统能扛 2 万 QPS”。它至少要包括：

1. 测试场景是什么。
2. 用户行为是否真实。
3. 请求比例是否接近线上。
4. P50、P95、P99 延迟是多少。
5. CPU、内存、网络、磁盘分别如何变化。
6. 数据库和缓存是否出现瓶颈。
7. 系统拐点在哪里。
8. 继续扩容是否线性有效。
9. 失败模式是什么。

很多压测看起来很专业，实际上价值不大。因为它只压了一个接口，而且请求数据完全一样，缓存命中率接近 100%。这类压测测到的不是系统能力，而是缓存能力。

生产中的压测要尽量接近真实环境：

1. 请求参数要有分布，不要全部相同。
2. 登录态、权限、限流、缓存都要尽量真实。
3. 下游依赖要么接真实测试环境，要么用可控 Mock 模拟延迟和错误。
4. 写入压测要有数据清理方案。
5. 压测前要设停止条件，避免压坏共享环境。

压测不是炫耀 QPS，而是找到拐点和失败模式。

## 4. 把成本纳入容量评估

高级架构师不只是让系统扛得住，还要让公司扛得起。

云时代有一个特点：扩容变得非常容易，浪费也变得非常容易。过去买服务器要走采购流程，今天点几下就能开几十台机器。方便本身没有错，但方便会让很多团队忘记成本约束。

你需要评估：

| 成本项 | 说明 |
| --- | --- |
| 计算成本 | ECS、容器、Kubernetes 节点 |
| GPU 成本 | AI 系统核心成本 |
| 存储成本 | 数据库、对象存储、快照 |
| 带宽成本 | 出网流量常常很贵 |
| CDN 成本 | 分发和回源 |
| Redis 成本 | 高规格内存实例昂贵 |
| ClickHouse 成本 | 日志和分析数据膨胀 |
| 第三方 API | 按调用或 token 收费 |
| 监控日志 | 容易被低估 |

AI 产品尤其如此。

比如你做一个 AI 写作或语音产品，每个用户每天消耗 5 万 token。如果有 10 万日活，就是每天 50 亿 token。哪怕每百万 token 成本很低，总量上来以后也是很大的支出。

因此 AI 产品从第一天起就要有成本模型：

```text
单用户日成本 = 输入 token 成本 + 输出 token 成本 + ASR 成本 + 存储成本 + 带宽成本
```

再进一步：

```text
毛利 = 用户收入 - 单用户资源成本 - 基础设施摊销 - 第三方服务成本
```

没有成本模型的 AI 产品，就像没有仪表盘的飞机，飞得越快，风险越大。

生产建议：

1. 所有核心路径都要能算单次请求成本。
2. 成本指标要按用户、租户、功能和模型拆分。
3. 免费用户和付费用户要有不同资源策略。
4. 对高成本操作设置配额、排队、降级或人工审批。
5. 资源利用率长期过低时，要做降配或合并。

工程不是只追求性能。真正的工程，是在性能、稳定性、成本和交付速度之间做理性选择。

## 5. 理解 SLA、SLO 和 Error Budget

现代系统不能只说“尽量稳定”。稳定性也要量化。

几个概念很重要：

| 概念 | 含义 |
| --- | --- |
| SLA | 对客户或用户的承诺 |
| SLO | 团队内部设定的稳定性目标 |
| SLI | 用来衡量目标的指标 |
| Error Budget | 可容忍的失败额度 |

比如，一个系统的 SLO 是 99.9% 可用性。一个月约 30 天，也就是 43200 分钟。99.9% 可用意味着每月最多不可用约 43.2 分钟。

常见 SLO 等级对应的允许停机时间：

| SLO | 每月允许不可用 | 每年允许不可用 |
| --- | --- | --- |
| 99% | 约 7.2 小时 | 约 3.65 天 |
| 99.9% | 约 43 分钟 | 约 8.76 小时 |
| 99.95% | 约 22 分钟 | 约 4.38 小时 |
| 99.99% | 约 4.3 分钟 | 约 52.6 分钟 |

这个 43.2 分钟就是错误预算的一部分。

它的意义在于：稳定性不是绝对的，也不是越高越好。99.999% 可用性当然很好，但成本可能极高（需要多机房、自动切换、极致冗余）。工程的本质就是在目标、成本和约束之间做选择。

错误预算的实际用法：当本月错误预算还剩很多时，团队可以大胆发布新功能；当错误预算快用完时，应该暂停高风险变更，优先修复稳定性问题。这让"稳定性 vs 迭代速度"的权衡变得可量化。

> 初学者提示：Error Budget 的概念来自 Google SRE 实践。它的核心洞察是——100% 可用性既不现实也不经济。与其追求不可能的完美，不如明确"允许多少失败"，然后围绕这个预算做决策。这比模糊的"尽量稳定"更有工程价值。

容量评估要和 SLO 结合起来。因为不同 SLO 对容量冗余的要求不同。一个内部报表系统可以接受分钟级抖动，一个支付系统就不能；一个免费 AI 试用功能可以排队，一个企业客户的实时语音服务就要保证低延迟。

生产建议：

1. 为核心用户路径定义 SLI，例如成功率、P99、TTFT。
2. 为不同业务等级定义不同 SLO。
3. 把错误预算和发布节奏绑定。
4. 错误预算消耗过快时，暂停高风险发布，优先稳定性。
5. 容量冗余要服务 SLO，而不是凭感觉设置。

## 6. 用指标链定位瓶颈：一个可复用流程

所谓瓶颈定位，本质上是建立证据链。证据链的作用，是避免团队陷入“我觉得是数据库”“我觉得是网络”“我觉得是代码”的争论。

一个可复用流程是：

```text
用户体验指标
→ 入口指标
→ 应用指标
→ 下游依赖指标
→ 数据系统指标
→ 基础设施指标
→ 成本指标
```

假设用户反馈“生成结果很慢”。不要马上优化模型，也不要马上加机器。先拆：

1. 是所有用户慢，还是部分用户慢。
2. 是 TTFT 慢，还是 TPOT 慢。
3. 是请求排队慢，还是模型生成慢。
4. 是 ASR 慢，还是 LLM 慢。
5. 是免费用户慢，还是付费用户也慢。
6. 是某个区域慢，还是全局慢。

对应的指标查询可以设计成这样（以 ClickHouse 为例）：

```sql
select
  model_name,
  user_plan,
  quantile(0.95)(queue_ms) as queue_p95,
  quantile(0.95)(ttft_ms) as ttft_p95,
  quantile(0.95)(tpot_ms) as tpot_p95,
  count() as requests
from llm_requests
where created_at >= now() - interval 1 hour
group by model_name, user_plan
order by ttft_p95 desc;
```

> 注意：`quantile()` 是 ClickHouse 的分位数函数。如果你用 MySQL，可以用窗口函数 `PERCENT_RANK()` 或 `NTILE()` 近似实现；如果用 PostgreSQL，可以用 `percentile_cont(0.95)`。

如果 `queue_p95` 高，说明请求在排队，可能是容量不够或调度策略有问题。如果 `queue_p95` 不高但 `tpot_p95` 高，说明生成阶段慢，可能是模型、batch、GPU 利用率或上下文长度问题。

这个例子说明，高级工程师不是更会猜，而是更会把问题拆成可观测的证据。

## 7. 压测报告怎么写才有决策价值

很多压测报告只有一句话：“系统能扛 2 万 QPS。”这句话的价值很低，因为它没有上下文。

一份有决策价值的压测报告至少要回答：

1. 这 2 万 QPS 是哪些接口组成的。
2. 请求参数是否真实。
3. 数据库里有多少数据。
4. 缓存命中率是多少。
5. P95 和 P99 是否满足 SLO。
6. 错误率是多少。
7. 哪个资源先到上限。
8. 加机器后是否线性提升。
9. 成本增加多少。
10. 下一次增长会卡在哪里。

可以用这个结论模板：

```text
在 8 台应用服务、1 个 MySQL 主库、3 个 Redis 节点的配置下，
按线上 7:2:1 的读写导出流量比例压测，
系统在 12000 RPS 以内 P99 小于 500ms，错误率小于 0.1%。
当流量提升到 15000 RPS 后，MySQL 连接池耗尽，P99 上升到 2.3s。
继续增加应用机器无明显收益，瓶颈已经转移到 MySQL。
建议上线前将导出接口异步化，并把读请求拆到从库或缓存。
```

这样的结论能指导决策。它不是炫耀数字，而是告诉团队下一步该做什么。

## 8. 高级容量评估的输出物

一次成熟的容量评估，最终不应该只是几页 PPT，而应该产出可执行的工程资产。

| 输出物 | 作用 |
| --- | --- |
| 用户行为模型 | 说明压力从哪里来 |
| 资源消耗模型 | 说明每条链路消耗什么 |
| 压测报告 | 说明当前容量和拐点 |
| 瓶颈清单 | 说明最先出问题的资源 |
| 扩容方案 | 说明如何增加容量 |
| 降级方案 | 说明过载时如何保护系统 |
| 成本模型 | 说明增长对应的费用 |
| 监控告警 | 说明如何提前发现风险 |
| 演练记录 | 说明方案是否真的有效 |

架构师的价值，不是把系统画得很复杂，而是让团队在复杂性到来之前有准备。
