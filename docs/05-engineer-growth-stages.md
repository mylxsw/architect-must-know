# 第五章 不同阶段的工程师应该达到什么水平

容量评估能力，实际上也是工程师成长层次的分水岭。

很多人以为工程师的成长是会更多框架、写更多代码、背更多中间件参数。那些当然有用，但并不是根本。真正的变化，是你能不能从“把功能做出来”走向“让系统长期可靠、可扩展、可承担成本地运行”。

这件事不能一步到位。不同阶段的工程师，对容量评估的要求不同。

## 1. 初级工程师：先建立资源意识

初级工程师主要关注功能是否能跑通。这个阶段最重要的是写出正确代码，理解基本的 HTTP、数据库、缓存和日志。至于系统什么时候会崩，通常还没有直觉。

这并不丢人。每个人都要从这里开始。

但是，初级工程师不能一直停留在“接口返回 200 就结束”的层次。你至少要开始理解：一次请求不是魔法，它会消耗资源。

一次典型 Web 请求大致会经过：

```text
客户端发起请求
→ 网关接收连接
→ 应用线程处理
→ 查询 Redis 或数据库
→ 调用下游服务
→ 写日志和监控
→ 返回响应
```

每一步都可能成为容量问题。

初级工程师应该掌握：

1. 会看接口 QPS、响应时间和错误率。
2. 会看服务 CPU、内存、磁盘和网络。
3. 知道慢 SQL 会拖慢系统。
4. 知道 Redis 不是无限内存。
5. 知道日志太多会产生成本和 IO 压力。
6. 知道重试可能放大故障。
7. 知道任何外部调用都要设置超时。

初级阶段最常见的坑，是写代码时只考虑正常路径。比如调用第三方 API 时不设超时，批量查询时一次拉十万条数据，日志里打印完整请求体，循环里查数据库。这些在测试环境看不出问题，到了生产高峰就会变成事故。

举一个具体例子：

```text
// 危险写法：循环中查数据库（N+1 问题）
for user in users:           // 假设 users 有 1000 个
    orders = db.query("SELECT * FROM orders WHERE user_id = ?", user.id)
    // 测试环境 users 只有 10 个，看不出问题
    // 生产环境 users 有 10000 个，就是 10000 次数据库查询

// 正确写法：批量查询
user_ids = [user.id for user in users]
orders = db.query("SELECT * FROM orders WHERE user_id IN (?)", user_ids)
```

给初级工程师的实践建议：

1. 每写一个接口，都问自己它会查几次数据库。
2. 每加一条日志，都问自己高峰时每分钟会产生多少。
3. 每做一个循环，都问自己数据量从 100 变成 100 万会怎样。
4. 每调用一个下游，都设置超时、重试上限和失败处理。
5. 每次线上问题复盘，都记录一个容量相关教训。

这一阶段的目标不是独立做容量规划，而是建立资源直觉。

## 2. 中级工程师：能做局部容量判断

中级工程师开始知道一些系统风险：

1. Redis 可能会爆内存。
2. MySQL 查询可能会变慢。
3. 接口可能会超时。
4. 服务需要限流和重试。
5. 慢查询需要加索引。
6. 队列消费速度可能跟不上生产速度。
7. 大对象会导致内存抖动。

这个阶段能做局部优化，但通常还缺少全局容量模型。

中级工程师应该能回答一个模块级问题：如果这个功能的使用量增长 10 倍，我负责的这一段会不会出问题？

例如你负责订单列表接口，就要知道：

1. 当前每天新增多少订单。
2. 单用户最多有多少订单。
3. 查询条件有哪些。
4. 索引是否覆盖主要查询。
5. 分页是否会扫大量数据。
6. 高峰 QPS 是多少。
7. 缓存命中率是多少。
8. 日志和埋点会增加多少写入。

中级工程师要开始使用工具，而不是凭感觉判断：

| 工具 | 用途 |
| --- | --- |
| 慢查询日志 | 找数据库瓶颈 |
| explain | 理解 SQL 执行计划 |
| Redis memory | 看 Key 和内存占用 |
| APM | 看接口耗时分布 |
| Grafana | 看资源趋势 |
| k6/wrk | 做基本压测 |
| pprof/flame graph | 找 CPU 和内存热点 |

生产中，中级工程师经常承担“局部系统负责人”的角色。你不一定设计全公司架构，但你要对自己模块的容量负责。

常见坑包括：

1. 只优化平均响应时间，不看 P99。
2. 只看接口耗时，不看下游依赖。
3. 只给 SQL 加索引，不评估索引写入成本。
4. 只做缓存，不考虑缓存雪崩、穿透和一致性。
5. 只增加消费者，不看 Kafka 分区数是否限制并发。

中级工程师的关键跃迁，是从“我会修一个慢接口”走向“我能解释这个接口为什么慢、什么时候会更慢、怎么避免它变慢”。


> 初级到中级的标志：从"能让功能跑起来"到"能让功能稳定跑"。
> 中级到高级的标志：从"能修一个问题"到"能预测和预防问题"。
## 3. 高级开发者：能做基本容量模型

高级开发者必须能做基本估算。

他应该能回答：

1. 一个功能上线后大概带来多少 QPS。
2. Redis 需要多少内存。
3. MySQL 表一年后有多大。
4. 日志一天会产生多少。
5. 带宽峰值是多少。
6. P99 延迟为什么上升。
7. 压测结果是否可信。
8. 扩容是否线性有效。

高级开发者还要能定位瓶颈，而不是只会加机器。

举一个生产中的例子。某个服务 QPS 从 3000 增长到 8000 后，P99 从 150ms 涨到 1.5s。初级工程师可能认为“机器不够”，中级工程师可能去优化某个 SQL，高级开发者应该先画链路：

```text
入口网关
→ 应用服务
→ Redis
→ MySQL
→ Kafka
→ 日志系统
```

然后逐项看指标：网关连接数是否正常，应用线程池是否饱和，Redis 是否有热 Key，MySQL 是否有锁等待，Kafka 是否积压，日志写入是否阻塞。只有证据指向 CPU 时，才应该加应用机器。

高级开发者应该建立三类能力。

第一，估算能力。知道如何从用户数推 QPS，从 QPS 推数据库查询，从日志条数推存储成本。

第二，实验能力。能设计压测场景，找到系统拐点，而不是只跑一个命令。

第三，复盘能力。线上事故后能提炼出容量模型的缺口，而不是只修一个补丁。

高级开发者的产出物应该包括：

1. 模块容量评估文档。
2. 压测报告。
3. 核心指标看板。
4. 限流降级方案。
5. 数据增长和清理策略。
6. 成本估算。

高级开发者的价值，不在于写更多代码，而在于让一个模块在增长中不失控。

## 4. 架构师：看 1 到 3 年的系统演进

架构师要看得更远。

他要能做未来 1 到 3 年容量规划，设计多机房架构，规划成本，设计扩容方案、降级方案和灾难恢复方案。

架构师关心的不只是“今天系统能不能跑”，而是“系统增长十倍后，架构还是否成立”。

架构师做容量评估时，至少要看五个层面：

1. 产品增长：用户规模、使用频率、核心路径是否会变化。
2. 技术架构：当前单体、微服务、数据库、缓存、队列是否能支撑增长。
3. 数据架构：数据如何分层、归档、分析和治理。
4. 运维体系：监控、告警、扩缩容、演练是否成熟。
5. 成本结构：资源成本是否随着收入合理增长。

架构师要提前做一些艰难决定。

比如数据库是否要按租户分片。如果太早做，会增加复杂度；如果太晚做，迁移成本巨大。什么时候引入 Kafka 也是类似。太早引入，会让系统复杂；太晚引入，同步链路可能已经被长任务拖垮。

这就是架构判断的难点。它不是背一个“最佳实践”就能解决，而是要在业务增长、团队能力、成本约束和技术风险之间做取舍。

架构师应该输出：

1. 未来容量预测。
2. 架构演进路线。
3. 关键资源扩容策略。
4. 降级和灾备设计。
5. 成本模型和预算。
6. 技术债清单。
7. 容量风险优先级。

好的架构师不会追求一次性设计一个完美系统。他会设计一个可演进的系统，让每个阶段都有足够能力，又不提前背上过重复杂度。

## 5. SRE 和运维负责人：让系统长期可靠地活着

SRE 更关注系统运行状态和自动化能力。

他需要建立监控体系、告警体系、自动扩缩容体系、容量预测体系和故障演练机制。在 Kubernetes 环境下，还要理解节点资源调度、Pod request/limit、HPA、VPA、Cluster Autoscaler 等能力。

开发者负责把系统造出来，SRE 负责让系统长期可靠地活着。两者不是对立关系，而是分工不同。

SRE 在容量评估中关心：

1. 资源利用率趋势。
2. 容量水位和预警阈值。
3. 自动扩缩容是否有效。
4. 故障是否会跨服务传播。
5. 告警是否准确，不误报也不漏报。
6. 变更是否会引发容量风险。
7. 灾备切换是否真的演练过。

SRE 最怕两类系统。

第一类是没有指标的系统。它可能已经很危险，但没人知道。

第二类是指标很多但没有结论的系统。看板几十个，事故来了却不知道哪个指标最重要。

生产建议：

1. 每个核心服务至少要有黄金指标：流量、错误率、延迟、饱和度。
2. 告警要基于用户影响和 SLO，而不是基于单点噪声。
3. 容量阈值要分级，不能只有“已经爆了”这一档。
4. 自动扩容要做冷启动和扩容速度评估。
5. 故障演练要覆盖依赖超时、节点故障、网络抖动和流量突增。

SRE 的成熟度，决定了系统能不能从“靠人盯着”变成“靠机制运行”。

## 6. 能力成长路线

可以把容量评估能力分成五级。

| 阶段 | 能力特征 | 典型问题 |
| --- | --- | --- |
| 初级 | 知道资源会被消耗 | 这个接口会不会查很多数据库 |
| 中级 | 能做局部优化 | 这个模块 QPS 翻倍会怎样 |
| 高级 | 能建模块容量模型 | 这个功能增长 10 倍瓶颈在哪 |
| 架构师 | 能做系统演进规划 | 未来 3 年架构是否成立 |
| SRE/负责人 | 能建立运行机制 | 如何让容量风险提前暴露 |

每一级都不是靠头衔定义的，而是靠你能回答的问题定义的。

## 7. 本章检查清单

| 角色 | 应该能交付什么 |
| --- | --- |
| 初级工程师 | 基本资源指标、慢 SQL 意识、超时和日志控制 |
| 中级工程师 | 模块级容量判断、局部压测、缓存和数据库优化 |
| 高级开发者 | 容量模型、压测报告、瓶颈定位、降级方案 |
| 架构师 | 1 到 3 年容量规划、架构演进、成本和灾备设计 |
| SRE | 监控告警、自动扩缩容、容量预测、故障演练 |

说到底，工程师成长不是从简单走向复杂，而是从局部走向整体，从功能走向系统，从代码走向成本和风险。容量评估正好训练这条路径。
