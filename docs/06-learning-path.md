# 第六章 推荐学习路线

容量评估不是一门孤立的课，它建立在计算机系统、网络、数据库、性能分析和分布式系统之上。

学习顺序很重要。很多人一上来就学 Kubernetes、Kafka、微服务，其实是倒过来了。底层资源都不理解，学再多框架也只是知道一些名词。一个工程师如果不知道 CPU Load 和 CPU 使用率的区别，不知道 TCP 连接为什么会耗资源，不知道 MySQL Buffer Pool 如何影响查询，就很难真正理解容量。

我建议按七个阶段学习。

## 1. 第一阶段：计算机资源基础

先学 Linux 和操作系统资源。

必须理解：

1. CPU Load。
2. Memory。
3. IO。
4. Network。
5. epoll。
6. 文件系统。
7. Page Cache。
8. mmap。
9. 零拷贝。
10. 进程、线程、上下文切换。

这一阶段的目标不是背命令，而是建立资源直觉。你要知道一个请求进入服务器后，经历了哪些内核和用户态过程。

比如，一个 HTTP 请求到达服务器，并不是直接进入你的业务函数。它先经过网卡、中断、内核协议栈、socket buffer、epoll、应用线程或协程调度，然后才到业务代码。业务代码查询数据库时，又会进入网络、磁盘、数据库 Buffer Pool 和锁管理。任何一个环节都可能成为瓶颈。

推荐练习：

1. 用 `top`、`htop`、`vmstat`、`iostat`、`sar` 观察系统资源。
2. 用 `strace` 看一个进程做了哪些系统调用。
3. 用 `perf` 或火焰图看 CPU 热点。
4. 写一个简单 HTTP 服务，逐步增加并发，观察 CPU、内存和连接数。
5. 构造大文件读写，观察 Page Cache 对性能的影响。

常见坑：

1. 把 CPU Load 当成 CPU 使用率。
2. 看到内存使用高就以为内存泄漏，不理解 Page Cache。
3. 不区分磁盘吞吐和 IOPS。
4. 不理解上下文切换过多会拖垮系统。
5. 在容器里只看宿主机指标，不看 cgroup 限制。

推荐读：

1. 《性能之巅》。
2. 《Systems Performance》。
3. 《深入理解 Linux 内核》。

## 2. 第二阶段：网络基础

网络是分布式系统的地基。

必须掌握：

1. TCP/IP。
2. HTTP/1.1、HTTP/2、HTTP/3。
3. 长连接。
4. WebSocket。
5. QUIC。
6. CDN。
7. DNS。
8. TLS。
9. 连接池。
10. 超时、重试、限流。

做实时语音和 AI 流式产品的人，尤其要重视 WebSocket、HTTP/2 streaming、网络抖动、backpressure 和断线重连。

网络容量的底层逻辑是：每一次通信都要占用连接、带宽、缓冲区和处理能力。短连接有建立成本，长连接有持有成本；重试能提高单次成功率，也可能放大故障；连接池能复用连接，也可能在下游变慢时积压请求。

推荐练习：

1. 用 `curl -w` 观察 DNS、连接、TLS、首包和总耗时。
2. 用 `ss` 或 `netstat` 观察连接状态。
3. 写一个 WebSocket 服务，测 1 万长连接的内存占用。
4. 模拟下游延迟，观察连接池如何耗尽。
5. 用 `tc` 模拟弱网、丢包和延迟。

常见坑：

1. 没有设置超时。
2. 重试没有上限。
3. 所有服务共用一个连接池。
4. WebSocket 心跳过于频繁，浪费带宽。
5. 客户端断线后立即全量重连，形成重连风暴。

网络问题最麻烦的地方在于，它常常表现为应用问题。接口慢了，看起来像代码慢；实际上可能是 DNS 慢、TLS 握手慢、连接池耗尽或者下游 RTT 增加。

## 3. 第三阶段：数据库容量

这一阶段重点学 MySQL、Redis 和 Kafka。

MySQL 要理解：

1. B+ 树索引。
2. Buffer Pool。
3. 事务隔离级别。
4. MVCC。
5. Redo Log。
6. Binlog。
7. 慢查询。
8. 主从复制。
9. 分库分表。

数据库容量的核心不是“表能放多少行”，而是“在目标查询模式下，表增长以后还能不能稳定返回结果”。同样是一亿行表，如果查询都能命中高选择性索引，热数据在 Buffer Pool 中，性能可以很好；如果查询条件混乱、索引设计差、排序和分页扫描大量数据，几百万行也可能很慢。

Redis 要理解：

1. 单线程模型。
2. 数据结构。
3. 内存开销。
4. 淘汰策略。
5. RDB/AOF。
6. Cluster。
7. 热 Key 和大 Key。

Kafka 要理解：

1. Topic。
2. Partition。
3. Consumer Group。
4. Offset。
5. Retention。
6. 副本。
7. 顺序写。
8. 消费积压。

推荐练习：

1. 建一张百万级、千万级 MySQL 表，比较不同索引下的查询计划。
2. 观察 Buffer Pool 命中率变化。
3. 构造 Redis 大 Key 和热 Key，观察延迟。
4. 用 Kafka 模拟生产速度大于消费速度，计算积压恢复时间。
5. 做一次小规模数据归档，把热数据和冷数据分开。

常见坑：

1. 只加索引，不看写入成本和索引空间。
2. 使用深分页，越翻越慢。
3. Redis Value 过大，单线程阻塞。
4. Kafka 分区数太少，消费者加不上去。
5. 没有数据保留和归档策略。

数据库容量是架构师的基本功。因为只要系统有状态，状态系统迟早会成为核心约束。

## 4. 第四阶段：性能分析

性能分析是把“感觉”变成“证据”的工具。

必须掌握：

1. flame graph。
2. pprof。
3. perf。
4. tracing。
5. eBPF。
6. APM。
7. 慢日志。
8. 系统指标关联分析。

看到延迟升高时，不要急着改代码。先把证据链建立起来：请求在哪个阶段耗时，哪个函数占 CPU，哪个依赖变慢，哪个资源接近上限。

一个好的性能分析流程通常是：

```text
确定用户影响
→ 找到受影响接口
→ 看延迟分布和错误率
→ 看链路追踪
→ 看服务资源
→ 看下游依赖
→ 看热点代码或慢查询
→ 做最小修复
→ 复测验证
```

推荐练习：

1. 给一个 Go 或 Java 服务接入 pprof 或 profiler。
2. 构造 CPU 热点，生成火焰图。
3. 构造内存泄漏，观察堆增长。
4. 给核心接口接入 tracing，看跨服务耗时。
5. 做一次“延迟升高”的故障演练。

常见坑：

1. 没有基线，不知道什么叫异常。
2. 只看单个指标，不看关联。
3. 没有区分 P50 和 P99。
4. 看到热点函数就改，不看业务路径是否真实。
5. 优化后不复测。

性能分析的本质，是建立证据链。没有证据链的优化，常常只是运气。

## 5. 第五阶段：压测体系

这一阶段学习如何设计真实压测。

工具可以从 k6 和 wrk 开始。k6 适合写用户场景，wrk 适合压 HTTP 极限。

你要学会写压测报告，而不只是跑一个命令。

好的压测报告应该告诉团队：系统当前容量是多少，瓶颈是什么，扩容方式是否有效，继续增长会在哪里出问题。

推荐练习：

1. 对一个真实 API 做阶梯压测。
2. 设计混合流量：登录、查询、写入、导出。
3. 记录 P50、P95、P99、错误率和资源利用率。
4. 找到系统拐点。
5. 增加一倍机器后复测，看扩容是否线性。
6. 做 2 到 4 小时稳定性压测，观察内存和延迟漂移。

常见坑：

1. 压测数据完全一样，缓存命中率过高。
2. 压测环境和生产环境差距太大。
3. 只看 QPS，不看失败率和 P99。
4. 不记录系统资源，压完不知道瓶颈在哪。
5. 不设停止条件，压坏共享环境。

压测的目标不是得到一个漂亮数字，而是让团队知道系统边界。

## 6. 第六阶段：分布式系统容量

当单机资源不够时，就进入分布式系统。

必须理解：

1. CAP。
2. 一致性。
3. 分片。
4. 复制。
5. 服务发现。
6. Service Mesh。
7. Kubernetes。
8. Elastic Scaling。
9. 限流降级。
10. 多机房灾备。

这一阶段最重要的认识是：分布式系统不是免费午餐。它解决单机容量问题，同时引入一致性、网络分区、运维复杂度和故障传播问题。

例如分库分表可以解决单库容量，但它会改变事务、排序、分页、统计和数据修复方式。Kubernetes 可以提高调度和弹性能力，但它也引入 request/limit、探针、滚动发布、节点资源碎片和网络插件等新问题。

推荐练习：

1. 将一个单体服务拆成两个服务，观察调用链和故障传播。
2. 对数据库按用户 ID 做简单分片。
3. 在 Kubernetes 中设置 request/limit，观察调度和 OOM。
4. 配置 HPA，测试扩容速度。
5. 做一次依赖故障演练，看降级是否生效。

常见坑：

1. 为了“先进”过早引入微服务。
2. 以为加 Kubernetes 就自动高可用。
3. 分片键选择错误，导致热点分片。
4. 限流只在入口做，下游仍被打爆。
5. 多机房只做部署，不做切流演练。

分布式系统的关键不是组件数量，而是边界管理。哪里同步，哪里异步；哪里强一致，哪里最终一致；哪里可降级，哪里必须保证。

## 7. 第七阶段：AI 系统容量

如果你现在做 AI 产品，这一阶段非常重要。

需要重点学习：

1. vLLM。
2. TensorRT-LLM。
3. Ollama。
4. KV Cache。
5. Continuous Batching。
6. Batch Scheduling。
7. CUDA 基础。
8. GPU 显存计算。
9. Tensor Parallel。
10. Pipeline Parallel。
11. TTFT、TPOT、Tokens/s。

AI 推理容量和传统 Web 容量不同。传统 Web 请求通常比较短，CPU 和数据库是主要瓶颈；LLM 请求可能持续几十秒，瓶颈常常在 GPU 显存、KV Cache、batch 调度和 token 生成速度。

推荐练习：

1. 用 Ollama 或 vLLM 部署一个开源模型。
2. 测不同 context length 下的显存占用。
3. 测不同并发下的 TTFT 和 TPOT。
4. 比较流式输出和非流式输出体验。
5. 测 batch size 对吞吐和延迟的影响。
6. 建立一次请求的 token 成本模型。

常见坑：

1. 用 HTTP QPS 衡量 LLM 容量。
2. 只看输出 token，不看输入 token 和长上下文。
3. 忽视 KV Cache 对显存的占用。
4. 没有模型路由，所有请求都走大模型。
5. 没有配额，免费用户也能产生高成本请求。

AI 推理容量将是未来几年非常值钱的工程能力。因为它同时涉及模型、系统、GPU、成本和用户体验。

## 8. 学习节奏建议

如果你是初学者，不要试图同时学完所有东西。可以按这个节奏推进：

| 时间 | 重点 |
| --- | --- |
| 第 1 个月 | Linux 资源、HTTP、基础监控 |
| 第 2 个月 | MySQL 索引、Redis 内存、慢查询 |
| 第 3 个月 | 压测工具、P99、瓶颈定位 |
| 第 4 个月 | Kafka、队列积压、异步架构 |
| 第 5 个月 | Kubernetes、限流降级、弹性扩容 |
| 第 6 个月 | AI 推理容量和成本模型 |

学习容量评估，最好的方法不是看更多概念，而是反复做实验。每做一次实验，你都会对系统边界多一分直觉。
