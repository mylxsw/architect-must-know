# 第七章 以 Typeflux 为案例：实时 AI 产品最该先学什么

Typeflux 是作者的一个开源项目。在这本小书里，我不把它当成一个需要读者参与开发的项目，而是把它当成一个教学案例：一个带有 macOS 客户端、语音流式输入、AI 推理和云端 API 的实时 AI 产品。

我认为，用这样的案例训练容量评估很合适。它既不像普通 CRUD 后台那样简单，也不像大型互联网平台那样离初学者太远。它把客户端、网络、长连接、ASR（Automatic Speech Recognition）、LLM（Large Language Model）、Redis、Kafka、数据库和成本放在一条链路上，正好能让读者看到现代应用的真实复杂性。

因此，本章要回答的问题不是给这个开源项目制定私有方案，而是：如果一个初学者想成为架构师，看到 Typeflux 这一类实时 AI 产品，应该优先学习哪些容量评估能力。

原因很简单。实时 AI 产品不是传统的表单系统，也不是普通 CRUD 后台。它的核心体验来自实时输入、实时识别、实时生成和低延迟反馈。用户感受到的不是“系统有没有返回 200”，而是第一句话多久出来、流式输出是否稳定、弱网下是否能恢复、成本是否能支撑长期使用。

## 1. 第一优先级：AI 推理容量

这是最核心的成本和体验来源。

你要知道：

1. 每个用户平均消耗多少 token。
2. 峰值时有多少并发生成。
3. TTFT 是否足够低。
4. TPOT 是否稳定。
5. GPU 利用率是否健康。
6. 长上下文是否导致 KV Cache 膨胀。
7. 哪些场景可以用小模型。
8. 哪些请求可以缓存。
9. 哪些用户需要配额。
10. 如何做模型路由。

AI 产品最怕的是技术上能跑，商业上跑不动。

一个最小成本模型可以这样写：

```text
单次请求成本 =
  输入 token 数 × 输入 token 单价
+ 输出 token 数 × 输出 token 单价
+ ASR 音频时长 × ASR 单价
+ 存储和带宽成本
+ 基础设施摊销
```

如果使用自建 GPU，还要换一种口径：

```text
单 token 成本 =
  GPU 小时成本 ÷ 单小时有效生成 token 数
```


例如：一张 A100 80GB 云租赁每小时成本约 $2-3（以 2024 年主流云厂商价格为参考，实际价格因厂商和地区而异），如果部署 7B-13B 参数模型并做好 batching 优化，有效输出可达 50-100 万 token/小时，则单 token 成本约 $0.002-0.006/千 token。与 API 调用价格对比，可以判断自建是否划算。

> 注意：这个数字高度依赖模型大小、量化方式和 batch 策略。70B 模型的吞吐会低很多，成本也会高很多。实际决策前必须用自己的模型和流量做基准测试。
这里“有效”两个字很重要。GPU 利用率低、batch 调度不好、请求排队过长、模型切换频繁，都会让理论成本和真实成本相差很大。

生产实践建议：

1. 建立 token 账本，按用户、功能、模型记录输入和输出 token。
2. 区分低价值请求和高价值请求，低价值请求优先小模型或缓存。
3. 对长上下文做摘要压缩和窗口裁剪。
4. 对重复指令、模板化任务做结果缓存。
5. 对免费用户设置每日 token 配额。
6. 对企业用户提供更高优先级和更稳定模型。
7. 用 TTFT 和 TPOT 监控体验，而不是只看成功率。

常见坑：

1. 所有请求都走同一个大模型。
2. 只统计请求次数，不统计 token。
3. 不限制上下文长度，导致 KV Cache 膨胀。
4. 没有流式输出，用户感知延迟很高。
5. 成本按月才发现，无法实时控制。

AI 推理容量的底层逻辑，是把用户体验和 GPU 资源连接起来。TTFT 决定用户是否觉得系统“有反应”，TPOT 决定用户是否觉得输出流畅，token 成本决定产品能不能赚钱。

## 2. 第二优先级：WebSocket 长连接容量

实时语音依赖长连接和流式传输。

你要重点关注：

1. 单机最大连接数。
2. 每个连接占用多少内存。
3. 心跳频率。
4. 断线重连策略。
5. backpressure。
6. 网关是否支持水平扩展。
7. 连接状态是否能迁移。
8. 流量突增时如何限流。
9. 客户端弱网环境如何处理。

长连接系统和普通 HTTP 系统不同。HTTP 请求结束后连接可以释放，而 WebSocket 会长时间占用服务器资源。

一个简单模型是：

```text
单机连接容量 =
  min(
    文件描述符上限,          // Linux 默认 1024，需要调大到 100000+（详见预备章 FD 部分）
    内存上限 ÷ 单连接内存,
    CPU 包处理能力,
    网络带宽 ÷ 单连接带宽,
    网关或负载均衡连接上限
  )
```

例如单连接平均占用 32KB 内存，单机可用于连接状态的内存是 8GB，理论内存上限约为：

```text
8GB ÷ 32KB ≈ 262144 连接
```

但这只是理论值。实际还要扣除应用对象、TLS、缓冲区、日志、心跳、GC、操作系统开销和安全余量。生产中不能按理论上限部署。

生产实践建议：

1. 单独监控连接数、连接建立速率、断开原因和重连次数。
2. 心跳间隔不要过短，避免无意义流量。
3. 客户端重连使用指数退避和随机抖动。
4. 服务端要有 backpressure，不能无限接收音频包。
5. 网关层要支持连接均衡和灰度发布。
6. 发布时要考虑长连接排水，而不是直接杀进程。
7. 对异常客户端做限速和封禁。

常见坑：

1. 用普通 HTTP 思维设计 WebSocket。
2. 服务端没有连接清理，僵尸连接越来越多。
3. 客户端断线后立刻疯狂重连。
4. 没有发送队列上限，慢客户端拖垮服务端内存。
5. 发布时直接重启，导致全量用户重连。

长连接容量的关键不是“最多能连多少”，而是“在故障、发布、弱网和流量突增时能不能稳定维持连接”。

### 2.1 长连接服务的最小保护代码

初学者写 WebSocket 服务时，最容易忘记三件事：连接上限、发送队列上限和慢客户端处理。

下面是一个伪代码，表达的是生产思路：

```go
type Conn struct {
    id        string
    userID    string
    sendQueue chan []byte
    closed    chan struct{}
}

const maxQueueSize = 256

func newConn(id, userID string) *Conn {
    return &Conn{
        id:        id,
        userID:    userID,
        sendQueue: make(chan []byte, maxQueueSize),
        closed:    make(chan struct{}),
    }
}

func (c *Conn) Send(msg []byte) bool {
    select {
    case c.sendQueue <- msg:
        return true
    default:
        // 慢客户端不能无限占用内存，队列满了就断开或降级。
        close(c.closed)
        return false
    }
}
```

这段代码想说明一个原则：凡是队列，都要有上限。没有上限的队列，本质上是在用内存掩盖容量问题。流量小的时候看不出来，流量一大就会变成 OOM。

### 2.2 发布时为什么要连接排水

普通 HTTP 服务发布时，旧实例停止接收新请求，等正在处理的请求结束即可。WebSocket 不一样，一个连接可能持续几十分钟甚至几小时。如果直接重启实例，所有连接会同时断开，客户端同时重连，形成重连风暴。

更合理的发布流程是：

```text
实例标记为 draining
→ 负载均衡不再分配新连接
→ 旧连接继续服务一段时间
→ 服务端通知客户端准备重连
→ 客户端随机延迟重连到新实例
→ 超时后关闭剩余连接
```

这类细节看起来不像“架构”，但它决定了系统在生产中是否稳定。

## 3. 第三优先级：Redis 和 Kafka

实时 AI 系统发展到一定阶段，通常会需要状态管理和异步处理。

Redis 可能用于：

1. Session 状态。
2. 用户配额。
3. 热数据缓存。
4. 分布式锁。
5. 临时上下文。
6. 速率限制。

Kafka 或其他消息队列可能用于：

1. 音频任务异步处理。
2. 日志采集。
3. 事件流。
4. 用户行为分析。
5. 模型调用记录。
6. 后台批处理。

这些组件一旦进入核心链路，就必须有容量规划。

Redis 的实现原理要抓住两点。第一，它主要在内存中工作，所以容量首先受内存约束。第二，很多操作在单线程事件循环中执行，所以大 Key、慢命令和网络阻塞都会影响整体延迟。

Redis 生产建议：

1. 所有 Key 都要有命名规范和过期策略。
2. 用户临时状态必须设置 TTL（Time To Live）。
3. 定期扫描 big key 和 hot key。
4. 配额、限流这类强依赖 Redis 的功能要有降级方案。
5. Redis Cluster 要关注槽位和热点分布。

Kafka 的实现原理也要抓住两点。第一，Partition 决定消费并发上限。第二，消息积压是生产速度和消费速度的差值随时间累积。

Kafka 生产建议：

1. Topic 分区数要根据未来消费并发规划。
2. 消息体不要过大，大文件放对象存储，消息里放引用。
3. 监控 consumer lag 和 lag 恢复速度。
4. 区分实时 Topic 和离线分析 Topic。
5. Retention 要按业务和成本设置。

常见坑：

1. Redis 被当数据库用，放了大量长期数据。
2. 分布式锁没有超时，锁泄漏导致业务停摆。
3. Kafka 分区太少，消费者再多也没用。
4. 消费失败没有死信队列。
5. 事件日志无限保留，存储成本失控。

Redis 和 Kafka 的价值在于解耦和削峰，但如果没有容量评估，它们也会从缓冲区变成事故放大器。

### 3.1 配额系统为什么适合 Redis

实时 AI 产品通常需要配额，例如免费用户每天最多使用 100 次，或每天最多消耗 5 万 token。Redis 适合做这件事，因为它支持原子递增和过期时间。

示例：

```text
quota:user:{user_id}:2026-05-13
```

每次请求后执行：

```redis
INCRBY quota:user:10001:2026-05-13 850
EXPIRE quota:user:10001:2026-05-13 172800
```

这里的 850 可以表示本次消耗 token 数。过期时间设置为 2 天，是为了覆盖时区、延迟上报和账单核对。

生产里要注意：

1. `INCRBY` 和 `EXPIRE` 最好用 Lua 脚本保证原子性（否则如果 INCRBY 成功但 EXPIRE 失败，Key 可能永不过期）。
2. Key 要按用户分散，避免所有请求打到少数 Key。
3. Redis 不可用时，要有保守策略，例如限制免费用户高成本请求。
4. 配额数据要异步落库，不能只存在 Redis（Redis 重启后数据可能丢失）。

Lua 脚本示例：

```lua
-- 原子性地增加配额并设置过期时间
local current = redis.call('INCRBY', KEYS[1], ARGV[1])
if current == tonumber(ARGV[1]) then
    -- 第一次写入时设置过期时间
    redis.call('EXPIRE', KEYS[1], ARGV[2])
end
return current
```

### 3.2 Kafka 事件应该怎么设计

很多团队把整个请求体都塞进 Kafka，这是一个常见坑。消息越大，网络、磁盘、复制和消费成本越高。

更好的事件设计是：

```json
{
  "event_id": "evt_123",
  "user_id": "u_10001",
  "request_id": "req_abc",
  "event_type": "llm.completed",
  "model": "small-model",
  "input_tokens": 950,
  "output_tokens": 400,
  "latency_ms": 3200,
  "created_at": "2026-05-13T10:00:00Z"
}
```

大文本、音频和完整上下文不要直接放消息里，可以放对象存储，消息里只放引用。这样 Kafka 负责事件流，存储系统负责大对象，各自做自己擅长的事。

## 4. 第四优先级：成本优化

AI 产品最难的不是把功能做出来，而是把单位经济模型做成立。

你需要建立：

```text
用户请求
→ token 消耗
→ GPU/API 成本
→ 存储和带宽成本
→ 用户收入
→ 毛利
```

然后围绕这个模型优化：

1. batching。
2. cache。
3. 小模型优先。
4. 模型路由。
5. 用户配额。
6. 上下文裁剪。
7. 摘要压缩。
8. 异步降级。
9. 免费用户限制。
10. 高级用户差异化。

这不是单纯的技术优化，而是产品、工程和商业的交汇点。

举一个简单例子。假设免费用户每天可以生成 50 次，每次平均 2000 token，10 万免费 DAU（Daily Active Users） 就是每天 100 亿 token。如果没有配额、缓存和模型分层，这个免费流量可能消耗掉非常可观的成本，而收入为零。

成本优化的原则不是一味减少成本，而是把昂贵资源用在高价值场景上。

生产实践建议：

1. 给每个功能标注成本等级。
2. 在产品层面限制高成本功能的滥用。
3. 对不同订阅等级设置不同模型、上下文和并发额度。
4. 用异步处理承接非实时任务。
5. 每周复盘成本 Top 用户、Top 功能和 Top 模型。
6. 对异常成本做告警，比如某用户 token 消耗突然增长 10 倍。

常见坑：

1. 工程团队只看技术指标，没人看毛利。
2. 成本归因不到用户和功能。
3. 免费功能没有边界。
4. 大模型承担了小模型能完成的任务。
5. 为了降低成本牺牲核心体验，没有区分关键路径和非关键路径。

### 4.1 成本账本要怎么落地

如果成本不能归因，就无法优化。一个最小成本账本可以这样设计：

```sql
create table ai_usage_events (
  id bigint primary key,
  user_id bigint not null,
  request_id varchar(128) not null,
  feature varchar(64) not null,
  model varchar(64) not null,
  input_tokens int not null,
  output_tokens int not null,
  audio_seconds int not null default 0,
  estimated_cost_usd decimal(12, 6) not null,
  created_at timestamp not null
);
```

每天聚合：

```sql
select
  feature,
  model,
  count(*) as requests,
  sum(input_tokens) as input_tokens,
  sum(output_tokens) as output_tokens,
  sum(estimated_cost_usd) as cost
from ai_usage_events
where created_at >= current_date
group by feature, model
order by cost desc;
```

这张表的意义不是做财务系统，而是让工程团队看到：钱花在什么功能、什么模型、什么用户上。没有这个账本，所谓成本优化只能凭感觉。

## 5. 以 Typeflux 为例的容量评估顺序

如果把 Typeflux 当作一个训练案例，从零做容量评估，可以按下面顺序展开。

第一，画出核心链路：

```text
macOS 客户端
→ 网关 / WebSocket
→ 音频上传
→ ASR
→ LLM 改写或生成
→ 流式返回
→ 会话存储
→ 日志和计费
```

第二，定义核心指标：

| 模块 | 指标 |
| --- | --- |
| 客户端 | 连接成功率、断线率、重连次数 |
| WebSocket | 连接数、带宽、消息延迟 |
| ASR | 音频秒数、识别延迟、错误率 |
| LLM | TTFT、TPOT、tokens/s、成本 |
| Redis | 内存、命中率、热 Key |
| Kafka | 生产速度、消费速度、lag |
| 数据库 | 写入 QPS、表增长、慢查询 |
| 成本 | 单用户日成本、毛利、异常消耗 |

第三，先做四个实验：

1. 1 万、5 万、10 万 WebSocket 连接实验。
2. 不同音频时长下的 ASR 延迟和成本实验。
3. 不同上下文长度和并发下的 LLM TTFT/TPOT 实验。
4. 免费用户、付费用户、重度用户的成本分布实验。

第四，设计降级策略：

1. ASR 压力过高时降低非核心用户优先级。
2. LLM 压力过高时切小模型或排队。
3. WebSocket 压力过高时限制新连接。
4. Redis 异常时保留核心功能，关闭非关键状态。
5. Kafka 积压时暂停低优先级后台任务。
