# 第八章 最有效的实践方式

容量评估不能只靠看书。你必须做实验。

很多技术知识，读的时候觉得明白，用的时候才发现自己没有真正理解。容量评估尤其如此。你只有亲手把系统压到拐点，观察 CPU、内存、网络、数据库、Redis、队列和延迟如何变化，才会对“系统边界”产生直觉。

我建议从四个项目开始：压测自己的 API、做 Redis 容量实验、做 WebSocket 长连接实验、做 AI 推理容量实验。

## 1. 项目一：压测自己的 API

选择一个真实接口，用 wrk 或 k6 做压测。

观察：

1. QPS。
2. P50、P95、P99。
3. CPU。
4. 内存。
5. 数据库连接。
6. Redis 命中率。
7. 错误率。

然后逐步增加并发，找到系统拐点。

### 实验目标

这个实验不是为了证明“我的接口很快”，而是为了回答三个问题：

1. 当前接口在真实场景下能承受多少流量。
2. 流量继续增加时，哪个资源最先出问题。
3. 这个接口的失败模式是什么。

### 推荐步骤

第一，准备一个接近真实的测试接口。不要选择健康检查接口，也不要选择只返回静态字符串的接口。最好选择一个有数据库、缓存或下游调用的核心接口。

第二，准备测试数据。请求参数要有分布，不能所有请求都查同一个用户、同一个商品、同一条记录。否则缓存命中率会异常高，结果没有参考价值。

第三，做基线测试。先用很低的并发运行 5 到 10 分钟，记录正常状态下的 P50、P95、P99 和资源消耗。

第四，做阶梯压测。比如并发从 10、50、100、200、500、1000 逐步上升。每个阶段至少持续几分钟，让系统进入稳定状态。

第五，记录拐点。当 P99 开始明显上升、错误率出现、CPU 或数据库连接接近上限时，说明系统接近容量边界。

第六，做复测。优化后再压一次，确认瓶颈是否真的被解决，以及新瓶颈在哪里。

### k6 示例

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },   // 2分钟内爬升到50并发
    { duration: '5m', target: 200 },   // 5分钟内爬升到200并发
    { duration: '5m', target: 500 },   // 5分钟内爬升到500并发
    { duration: '2m', target: 0 },     // 2分钟内降到0（冷却）
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],    // 错误率低于1%
    http_req_duration: ['p(95)<500'],  // P95延迟低于500ms
  },
};

export default function () {
  const id = Math.floor(Math.random() * 100000);
  const res = http.get(`https://example.com/api/items/${id}`);
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);  // 模拟用户思考时间，每个虚拟用户每秒发1个请求
}
```

### 压测报告模板

| 项目 | 内容 |
| --- | --- |
| 测试目标 | 验证哪个接口、哪个场景 |
| 环境配置 | 机器规格、实例数量、数据库规格 |
| 流量模型 | 请求比例、参数分布、并发用户 |
| 结果 | QPS、P50、P95、P99、错误率 |
| 资源 | CPU、内存、网络、磁盘、连接数 |
| 瓶颈 | 哪个资源先到上限 |
| 拐点 | 系统从哪个并发开始失稳 |
| 结论 | 当前容量和可承载峰值 |
| 建议 | 扩容、优化、限流或降级方案 |

### 常见坑

1. 只压一个接口，却宣称整个系统容量足够。
2. 测试数据完全相同，缓存命中率接近 100%。
3. 压测环境比生产环境小很多，却直接外推。
4. 只记录 QPS，不记录 P99 和错误率。
5. 不看数据库、Redis 和下游依赖。

压测最有价值的不是数字，而是它让你第一次看见系统如何失稳。

## 2. 项目二：做 Redis 容量实验

自己构造：

1. 100 万 Key。
2. 1000 万 Key。
3. 大 Key。
4. 热 Key。
5. 不同淘汰策略。
6. RDB/AOF 开启和关闭。

观察内存、延迟和阻塞情况。

### 实验目标

这个实验要让你理解三件事：

1. Redis 的内存开销远大于 Value 本身。
2. 大 Key 和热 Key 会破坏集群均衡。
3. 持久化和淘汰策略会影响延迟。

### 推荐步骤

第一，写入不同数量的小 Key。比如 10 万、100 万、1000 万，观察 used_memory、mem_fragmentation_ratio 和延迟。

第二，写入不同大小的 Value。比较 100B、1KB、10KB、100KB Value 对内存和网络的影响。

第三，构造大 Key。比如一个 List 或 Hash 里放几十万元素，然后执行读取、删除或遍历操作，观察 Redis 延迟。

> 提示：删除大 Key 时使用 `UNLINK` 命令（Redis 4.0+）而不是 `DEL`。`UNLINK` 会在后台异步释放内存，不会阻塞主线程。

第四，构造热 Key。让大量请求访问同一个 Key，观察单节点 CPU 和网络是否成为瓶颈。

第五，打开和关闭 RDB/AOF，比较写入延迟和磁盘 IO。

第六，设置不同 maxmemory-policy，观察内存满时系统行为。

### 关键指标

| 指标 | 含义 |
| --- | --- |
| used_memory | Redis 逻辑内存 |
| used_memory_rss | 操作系统看到的实际内存 |
| mem_fragmentation_ratio | 内存碎片率 |
| instantaneous_ops_per_sec | 当前操作速率 |
| connected_clients | 连接数 |
| blocked_clients | 阻塞客户端 |
| evicted_keys | 被淘汰的 Key 数量 |
| keyspace_hits/misses | 命中和未命中 |

### 常见坑

1. 只看 Value 大小，不看 Redis 对象开销。
2. 用 `keys *` 在线上扫描全量 Key。
3. 大 Key 删除时阻塞主线程。
4. 缓存没有 TTL，最终变成数据库。
5. 以为 Redis Cluster 可以自动解决热 Key。

这个实验做完，你对 Redis 的理解会比只看文档深很多。

## 3. 项目三：做 WebSocket 长连接实验

搭一个简单 WebSocket 服务，测试：

1. 1 万连接。
2. 5 万连接。
3. 心跳。
4. 弱网断开。
5. 重连。
6. 服务端广播。
7. 单连接内存占用。
8. 网关 CPU 和带宽。

### 实验目标

这个实验要回答：

1. 单机能维持多少稳定连接。
2. 单连接平均占多少内存和带宽。
3. 重连、心跳和广播会不会造成额外压力。
4. 发布或故障时连接如何平滑迁移。

### 推荐步骤

第一，搭一个最小 WebSocket 服务，只做连接、心跳和 echo。

第二，用压测客户端建立 1 万连接，观察内存、文件描述符、CPU 和网络。

第三，把连接数提升到 5 万、10 万，记录系统拐点。

第四，加入心跳。比较 5 秒、15 秒、30 秒、60 秒心跳对带宽和 CPU 的影响。

第五，模拟弱网和断线重连。观察客户端是否同时重连，服务端是否出现连接风暴。

第六，测试服务端广播。观察慢客户端是否拖垮发送队列。

第七，模拟发布。让服务端优雅关闭连接，观察客户端恢复时间。

### 关键指标

| 指标 | 含义 |
| --- | --- |
| active_connections | 当前连接数 |
| connection_rate | 新建连接速率 |
| disconnect_rate | 断开连接速率 |
| reconnect_rate | 重连速率 |
| memory_per_connection | 单连接内存 |
| inbound_bandwidth | 上行带宽 |
| outbound_bandwidth | 下行带宽 |
| send_queue_size | 发送队列积压 |
| event_loop_lag | 事件循环延迟 |

### 常见坑

1. 文件描述符上限太低（Linux 默认 1024，需要通过 `ulimit -n` 或 `/etc/security/limits.conf` 调大）。
2. 心跳太频繁，带宽被浪费。
3. 没有慢客户端保护。
4. 断线重连没有指数退避。
5. 发布时没有连接排水。

实时系统的很多问题，只有在长连接规模上来后才会暴露。

## 4. 项目四：做 AI 推理容量实验

选择 Qwen、Llama 或其他开源模型，用 vLLM 或 Ollama 做实验。

观察：

1. tokens/s。
2. TTFT。
3. TPOT。
4. GPU 显存。
5. batch size。
6. context length。
7. 并发请求。
8. 流式输出体验。

### 实验目标

这个实验要让你理解：AI 推理容量不是一个固定 QPS，而是一组变量之间的平衡。

影响容量的变量包括：

1. 模型大小。
2. 输入 token 数。
3. 输出 token 数。
4. context length。
5. 并发请求数。
6. batch 策略。
7. GPU 显存。
8. KV Cache。
9. 流式输出策略。

### 推荐步骤

第一，选择一个模型，固定 prompt 和输出长度，测单并发 tokens/s。

> 入门建议：用 Ollama 在本地 Mac 或 Linux 上部署 Qwen2.5-7B 或 Llama-3-8B 等小模型即可开始实验。不需要昂贵 GPU，Apple Silicon Mac 的统一内存也能跑 7B 模型。

第二，增加并发，观察 TTFT、TPOT 和吞吐变化。

第三，增加输入长度，从 1k、4k、16k、32k 逐步测试显存和延迟。

第四，比较流式和非流式输出的用户体验。

第五，改变 batch size 或使用 continuous batching，观察吞吐和延迟的权衡。

第六，建立成本模型，计算每 1000 次请求消耗多少 GPU 时间或 API 费用。

### 关键指标

| 指标 | 含义 |
| --- | --- |
| TTFT | 首 token 延迟 |
| TPOT | 每个输出 token 耗时 |
| tokens/s | token 吞吐 |
| GPU utilization | GPU 利用率 |
| GPU memory | 显存占用 |
| queue_time | 请求排队时间 |
| context_length | 上下文长度 |
| output_tokens | 输出长度 |

### 常见坑

1. 只测短 prompt，不测长上下文。
2. 只看平均速度，不看 TTFT。
3. 并发上来后排队时间被忽略。
4. 使用大模型处理所有任务。
5. 不把实验结果换算成成本。

你会发现，AI 推理系统的容量不是一个固定数字，而是体验、吞吐、显存和成本之间的平衡。

## 5. 实践项目如何形成闭环

每个实验都要形成闭环：

```text
提出问题
→ 建立假设
→ 设计实验
→ 收集指标
→ 找到瓶颈
→ 做出改动
→ 复测验证
→ 写成文档
```

不要只做实验不写结论。工程团队最宝贵的资产之一，就是这些实验报告。它们会告诉后来的人：系统曾经在哪里出过问题，哪些优化有效，哪些想法只是看起来有效。

## 6. 本章检查清单

| 实验 | 最低交付物 |
| --- | --- |
| API 压测 | 压测脚本、结果表、瓶颈结论、优化建议 |
| Redis 容量 | Key 数量、内存曲线、大 Key/热 Key 结论 |
| WebSocket | 连接数上限、单连接成本、重连策略结论 |
| AI 推理 | TTFT、TPOT、tokens/s、显存和成本模型 |

实践的价值，不是让你记住几个命令，而是训练一种工程直觉：系统不会无缘无故变慢，也不会无缘无故崩溃。只要你愿意做实验，它总会把自己的边界告诉你。
