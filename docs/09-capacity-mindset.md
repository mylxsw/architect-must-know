# 第九章 最终要形成的思维方式

真正高级的工程师，脑子里会自动形成一条链路：

```text
用户规模
→ 用户行为模型
→ 请求链路
→ 资源消耗
→ 系统瓶颈
→ 扩容方案
→ 成本模型
→ 风险模型
```

这条链路，就是架构能力的核心。

很多人以为架构师的能力是会画复杂的架构图，会说很多分布式系统名词。其实不是。架构师最重要的能力，是在系统还没有变复杂之前，就能看见它未来会在哪里变复杂；在事故还没有发生之前，就知道它大概率会以什么方式发生；在公司还没有花冤枉钱之前，就知道哪些资源值得买，哪些资源不值得买。

容量评估就是这种能力的训练场。

## 1. 从功能思维到系统思维

功能思维关注“这个需求怎么做出来”。系统思维关注“这个需求上线后，会怎样影响整个系统”。

一个简单的“导出报表”功能，在功能思维里可能只是：

```text
查询数据
→ 生成 Excel
→ 返回下载链接
```

在系统思维里，它至少包括：

1. 一次导出最多查多少数据。
2. 查询是否会拖慢主库。
3. 生成文件是否会占用大量内存。
4. 文件存在哪里，保留多久。
5. 同时有多少用户导出。
6. 是否需要异步任务。
7. 是否需要限流。
8. 是否会产生带宽和对象存储成本。
9. 失败后如何重试。
10. 用户是否能看到进度。

这就是差别。初学者看到的是功能路径，架构师看到的是资源路径。

生产建议：

1. 每个新功能评审都增加“容量影响”一项。
2. 对高成本功能默认异步化和限流。
3. 对可能增长的数据默认设计清理策略。
4. 对核心链路默认设计降级方案。
5. 对外部依赖默认设置超时和隔离。

## 2. 从平均值思维到分布思维

平均值会掩盖很多问题。

平均响应时间 100ms，可能是所有请求都稳定在 100ms，也可能是 99% 请求 20ms，1% 请求 8s。对用户和系统来说，这两种情况完全不同。

容量评估必须看分布：

1. P50 表示普通用户体验。
2. P95 表示大多数用户的尾部体验。
3. P99 表示系统风险和极端体验。
4. Max 往往反映异常请求、下游故障或队列积压。

尾延迟之所以重要，是因为现代系统是链式调用。一个用户请求可能调用十几个服务。即使每个服务只有 1% 慢请求，组合起来以后，整体慢请求比例也会显著增加。

这也是为什么 Google 早年在大规模系统中非常重视 tail latency。大规模系统的体验，不是由平均值决定，而是由尾部决定。

生产建议：

1. 所有核心接口都看 P50、P95、P99。
2. 告警不要只基于平均延迟。
3. 压测报告必须包含延迟分布。
4. 对慢请求采样保存完整链路。
5. 分析 P99 时同时看队列、锁、GC、下游依赖。

从平均值到分布，是工程师容量意识的一次重要升级。

## 3. 从静态数字到动态曲线

系统容量不是一个静态数字。

“系统能扛 2 万 QPS”这句话只有在上下文完整时才有意义：什么请求比例，什么数据量，什么缓存命中率，什么机器规格，什么错误率，什么延迟目标，持续多久，成本多少。

更重要的是，系统会随时间变化。

1. 用户增长会改变流量。
2. 数据增长会改变查询成本。
3. 功能增加会改变请求链路。
4. 日志增加会改变存储成本。
5. 模型升级会改变 AI 推理成本。
6. 业务活动会改变峰值流量。

因此，容量评估要看趋势，而不是只看某一天的截图。

生产建议：

1. 每周看资源水位趋势。
2. 每月做一次容量预测。
3. 重大版本上线前重新评估容量模型。
4. 大促或活动前做专项压测。
5. 数据增长超过预期时提前做归档或分片。

一个成熟团队应该知道：按当前增长速度，哪个资源会在什么时候先到上限。

## 4. 从局部优化到全局约束

局部优化不一定带来全局收益。

例如，把应用服务从 10 台扩到 30 台，如果数据库已经是瓶颈，整体 QPS 可能不会提升多少，反而会因为更多连接和并发查询把数据库压得更慢。

再比如，给接口加缓存可以降低数据库压力，但如果缓存 Key 设计不好，可能引入热 Key；如果 TTL 同时过期，可能造成缓存雪崩；如果一致性要求高，可能带来更复杂的失效逻辑。

工程系统像一张网。你拉动一个点，其他点也会变化。

生产建议：

1. 优化前先明确全局瓶颈。
2. 优化后复测端到端指标。
3. 关注瓶颈转移，而不是只看局部变快。
4. 对新引入组件评估运维成本。
5. 把复杂度也当成成本。

高级工程师做优化时，脑子里不是一个函数，而是一条链路。

## 5. 从稳定性到经济性

容量评估不能只问系统会不会崩，还要问公司会不会被成本拖垮。

在云和 AI 时代，这一点尤其重要。云资源让扩容很容易，AI 让每次请求都有直接成本。一个没有成本模型的系统，可能技术上很成功，商业上很危险。

你应该把容量问题和经济问题连起来：

```text
用户行为
→ 资源消耗
→ 单用户成本
→ 收入
→ 毛利
→ 可持续增长
```

生产建议：

1. 每个核心功能都要有单次成本估算。
2. 成本要能归因到用户、租户、功能和模型。
3. 免费功能要有明确资源边界。
4. 高成本功能要和付费权益绑定。
5. 容量规划要和财务预算同步。

技术系统最终要服务现实世界。现实世界有资源约束，也有商业约束。

## 6. 从救火到机制

很多团队早期靠人救火。哪里慢了，加机器；哪里爆了，清数据；哪里超时，重启服务。

这在小系统里可能有效，但在大系统里不可持续。

成熟团队要把救火经验变成机制：

| 救火行为 | 机制化做法 |
| --- | --- |
| 事故时看日志 | 建立核心指标和链路追踪 |
| 出问题再扩容 | 建立容量水位和预测 |
| 临时限流 | 设计分级限流和降级 |
| 手动清数据 | 建立数据生命周期管理 |
| 人肉盯成本 | 建立成本归因和告警 |
| 口头复盘 | 写事故复盘和改进任务 |

机制的意义，是让系统不依赖某个英雄。工程成熟度越高，越不应该靠个人记忆和临场发挥。

## 7. 一个架构师的容量评估问题清单

面对一个新系统，我通常会问这些问题：

1. 这个系统的核心用户路径是什么。
2. 当前 DAU、峰值并发和请求比例是多少。
3. 每条路径会访问哪些下游。
4. 每次请求消耗多少数据库、缓存、队列和外部 API。
5. 数据每天增长多少，保留多久。
6. 哪个资源最接近上限。
7. QPS 增长 3 倍、10 倍时，瓶颈在哪里。
8. 哪些资源可以线性扩容，哪些不可以。
9. 过载时保护谁、牺牲谁。
10. 当前成本结构是否支持业务增长。
11. 哪些指标能提前预警。
12. 最坏情况下如何恢复。

这些问题不复杂，但很少有团队一开始就能答全。答不全不要紧，容量评估的过程，就是把这些问题逐个变成数据和方案。

## 8. 最后的判断

说到底，容量评估不是一门“运维课”，而是一门“工程判断课”。它训练的不是某个工具的使用，而是你对系统边界、增长规律和资源约束的理解。

当你能从一个产品功能，推导出它的流量、存储、计算、网络、数据库、缓存、消息队列、AI 推理和成本模型时，你就不再只是一个写功能的开发者，而开始真正进入架构师的世界。

技术史反复告诉我们，一个系统、一个公司，甚至一个行业，真正的竞争力往往不在最表面的功能，而在底层能力。搜索引擎表面是一个输入框，背后是抓取、索引、排序、存储和数据中心。AI 产品表面是一个对话框，背后是模型、推理、调度、成本和体验。

容量评估，就是训练你看见这些背后的东西。

## 9. 本章检查清单

| 思维方式 | 自检问题 |
| --- | --- |
| 系统思维 | 我是否能从功能推导出资源链路 |
| 分布思维 | 我是否看 P95、P99，而不是只看平均值 |
| 趋势思维 | 我是否知道资源何时到上限 |
| 全局思维 | 我是否知道优化会把瓶颈转移到哪里 |
| 成本思维 | 我是否知道单用户和单请求成本 |
| 机制思维 | 我是否把经验沉淀成监控、告警和流程 |

如果这些问题能逐渐答上来，你的容量评估能力就已经开始成型。
