# 附录 容量评估模板与落地清单

前面的章节讲了概念、资源、方法、学习路线和实践项目。最后这一章给出一个可以直接使用的容量评估模板。

我一直认为，工程方法论如果不能落到表格、指标、实验和决策上，就容易变成漂亮话。容量评估也是如此。你不需要每次都写几十页文档，但至少要让团队能回答：评估对象是什么，流量从哪里来，资源消耗是多少，瓶颈在哪里，风险如何处理，成本是否合理。

## 1. 容量评估文档模板

> 使用建议：第一次做容量评估时，不需要填满所有字段。先填你能确定的数据，标记不确定的部分，然后通过压测和监控逐步补全。一份 80% 完整的容量评估，比没有评估好一百倍。

> 模板格式：这些模板可以用 Markdown、Notion、飞书文档或 Google Docs 承载。重要的不是工具，而是团队真的去填写和更新它。建议每季度至少更新一次。

### 1.1 背景和目标

先说明为什么要做这次容量评估。

示例：

```text
本次评估针对实时语音输入功能。
目标是在未来 3 个月 DAU（Daily Active Users） 从 5 万增长到 30 万时，
验证 WebSocket、ASR、LLM、Redis、数据库和成本是否能支撑业务增长。
```

需要写清楚：

1. 评估的业务范围。
2. 评估的时间窗口。
3. 目标用户规模。
4. 核心 SLO（Service Level Objective）。
5. 成本边界。

### 1.2 用户行为模型

用户行为模型是容量评估的起点。不要跳过这一步直接算资源——没有用户行为模型，资源估算就没有依据。

| 指标 | 当前值 | 目标值 | 说明 |
| --- | --- | --- | --- |
| DAU |  |  | 日活用户 |
| MAU |  |  | 月活用户 |
| 高峰活跃比例 |  |  | 晚高峰或活动高峰 |
| 人均每日使用次数 |  |  | 每个用户发起几次核心行为 |
| 单次使用时长 |  |  | 语音、会话或任务时长 |
| 请求峰值系数 |  |  | 突发流量放大 |
| 免费/付费比例 |  |  | 成本和优先级相关 |

计算示例：

```text
峰值并发 = DAU × 高峰活跃比例 × 单次使用时长 ÷ 高峰窗口时长
峰值 QPS = 峰值并发 × 单用户每秒请求数 × 峰值系数
```

### 1.3 核心链路

把用户行为拆成资源链路。

```text
客户端
→ 网关
→ 应用服务
→ Redis
→ MySQL
→ Kafka
→ 第三方 API / AI 模型
→ 日志与监控
```

每个环节要写：

1. 调用次数。
2. 平均耗时。
3. P95/P99。
4. 错误率。
5. 资源消耗。
6. 是否可降级。

风险等级可以简单分为：

| 等级 | 含义 |
| --- | --- |
| 低 | 目标用量低于上限 50%，扩容路径清晰 |

### 1.5 瓶颈和扩容方案

每个高风险资源都要写清楚：

1. 为什么它是瓶颈。
2. 当前证据是什么。
3. 扩容方式是什么。
4. 扩容成本是多少。
5. 扩容是否线性有效。
6. 扩容失败时如何降级。

示例：

```text
瓶颈：Redis 单节点热 Key 导致 P99 抖动。
证据：高峰时某 Key 每秒访问 8 万次，所在节点 CPU 90%，其他节点 30%。
方案：增加本地缓存和 Key 拆分，将单 Key 拆为 64 个分片 Key。
验证：压测中 P99 从 800ms 降至 120ms。
风险：本地缓存带来短时间不一致，可接受。
```

## 3. 降级和保护模板

容量评估不能只写扩容。扩容有时来不及，有时成本太高，有时瓶颈不支持线性扩容。必须有降级。

| 风险 | 保护策略 | 用户影响 | 恢复方式 |
| --- | --- | --- | --- |
| 应用 CPU 高 | 限流低优先级接口 | 部分功能变慢 | 自动恢复 |
| 数据库慢 | 读缓存、关闭复杂查询 | 数据可能短暂不新 | 缓存失效后恢复 |
| Redis 异常 | 本地缓存、关闭非核心状态 | 部分状态不准确 | Redis 恢复后刷新 |
| Kafka 积压 | 暂停低优先级生产者 | 后台任务延迟 | 消费追平 |
| LLM 过载 | 小模型、排队、限制长上下文 | 生成质量或速度下降 | 资源恢复后切回 |
| WebSocket 连接过多 | 拒绝新连接、延长心跳 | 新用户连接失败 | 水位下降后恢复 |

降级要遵循一个原则：保护核心路径，牺牲非核心体验。没有优先级的降级，最后往往什么都保不住。

具体来说，降级优先级通常是：
1. 先关闭日志、监控等观测类功能的非核心部分（如 debug 日志、全量链路采样）。
2. 再降级后台任务、报表、推荐等非实时功能。
3. 然后降级非核心用户体验（如关闭动画、降低刷新频率）。
4. 最后才考虑降级核心业务功能（如限制输入长度、排队、切小模型等）。

> 关键原则：降级方案必须提前设计和测试，不能等事故发生时临时决定。每个降级开关都应该有明确的触发条件和恢复条件。

## 4. 成本模型模板

成本模型至少要能回答单用户成本和单请求成本。

### 4.1 单请求成本

```text
单请求成本 =
  计算成本
+ 存储成本
+ 带宽成本
+ 第三方 API 成本
+ AI token 或 GPU 成本
+ 日志监控成本
```

### 4.2 单用户日成本

```text
单用户日成本 =
  人均请求数 × 单请求成本
+ 人均存储增长 × 存储单价
+ 人均日志增长 × 日志单价
```

### 4.3 毛利模型

```text
用户毛利 =
  用户收入
- 单用户资源成本
- 第三方服务成本
- 基础设施摊销
```

| 问题 | 回答 |

## 7. 一份填写后的示例

模板只有在填过一次之后，读者才知道怎么用。下面是一份简化示例。

### 7.1 背景和目标

```text
业务：AI 语音整理功能
目标：3 个月内支持 30 万 DAU
核心 SLO：LLM TTFT P95 < 1.5s，核心链路成功率 > 99.5%
成本边界：单免费用户日成本不超过 0.02 美元（即 30 万免费用户每天最多 6000 美元，月成本约 18 万美元）
```

### 7.2 用户行为模型

| 指标 | 当前值 | 目标值 | 说明 |
| --- | --- | --- | --- |
| DAU | 5 万 | 30 万 | 产品增长目标 |
| 高峰活跃比例 | 10% | 15% | 晚高峰 |
| 单用户日均使用次数 | 8 | 10 | 按埋点统计 |
| 单次语音时长 | 20 秒 | 25 秒 | P50 口径 |
| 单次输出 token | 300 | 400 | 抽样估算 |

### 7.3 风险结论

| 风险 | 证据 | 方案 |
| --- | --- | --- |
| LLM 成本过高 | 目标规模下月成本可能超过预算 | 小模型优先、配额、缓存 |
| WebSocket 重连风暴 | 客户端无退避策略 | 指数退避、随机抖动、连接排水 |
| Redis 临时上下文膨胀 | 上下文无大小限制 | TTL、大小上限、对象存储引用 |
| 事件表增长过快 | 每天 900 万事件 | Kafka + 分析库，主库只存核心状态 |

### 7.4 最终决策

```text
当前不做复杂多机房架构，先完成四项基础能力：
1. AI token 成本账本；
2. WebSocket 连接排水和重连退避；
3. Redis Key TTL 和 big key 扫描；
4. LLM/ASR/长连接三类压测。

理由：
这些能力直接对应当前最大风险，改造成本低，能显著提高系统可观测性和容量确定性。
```

这就是一份好容量评估的样子：不追求把所有问题一次解决，而是把风险排序，把证据写清楚，把下一步行动定下来。

## 8. 本章最终清单

如果你要把容量评估真正落地，至少要有这些东西：

1. 一份用户行为模型。
2. 一张核心链路图。
3. 一张资源容量表。
4. 一份压测计划和压测报告。
5. 一份瓶颈和扩容方案。
6. 一份降级和保护方案。
7. 一份成本模型。
8. 一组核心监控和告警。
9. 一份上线前容量评审清单。
10. 一套事故复盘模板。

这十样东西看起来朴素，但它们比许多复杂架构图更有价值。架构图告诉你系统长什么样，容量评估告诉你系统能活到多大。

容量评估的最高境界，不是每个数字都算得完全准确，而是让团队在增长之前先看到边界，在事故之前先看到风险，在花钱之前先看到成本。工程师的见识，就体现在这些地方。
