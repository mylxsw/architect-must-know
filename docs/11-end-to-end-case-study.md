# 实战案例 以 Typeflux 为案例：从零做一次容量评估

前面的章节讲了很多概念。现在我们把它们串起来，做一次完整的容量评估。

Typeflux 是作者的开源项目。这里使用它作为教学案例，而不是给某个具体项目做私有咨询。数字都是为了说明方法而设定的，不代表真实业务数据。重要的不是这些数字本身，而是推导过程。工程师真正要学会的，是如何从用户规模一步步推到系统资源、瓶颈、成本和方案。

> 阅读建议：跟着每一步计算走一遍，理解每个数字是怎么来的。然后把数字替换成你自己项目的真实数据，重新算一遍。这比只看结论有用得多。

## 1. 业务背景

假设我们要评估一个实时语音 AI 产品。用户在 macOS 客户端按下快捷键，说一段话，系统实时识别语音，然后调用 LLM（Large Language Model） 做整理、润色或结构化输出，最后把结果流式返回客户端。

核心链路是：

```text
macOS 客户端
→ WebSocket 网关
→ 音频流上传
→ ASR（Automatic Speech Recognition） 语音识别
→ LLM 文本处理
→ 流式返回结果
→ 会话存储
→ 计费和日志
```

这个产品和普通 Web 系统不同。它的容量压力来自四个地方：

1. WebSocket 长连接。
2. 持续音频流带宽。
3. ASR 和 LLM 推理。
4. token 和 GPU/API 成本。

如果只问“能扛多少 QPS”，这个评估从一开始就是错的。

## 2. 设定业务目标

假设未来三个月的目标是：

| 指标 | 当前 | 三个月目标 |
| --- | --- | --- |
| DAU（Daily Active Users） | 5 万 | 30 万 |
| 付费用户占比 | 5% | 8% |
| 高峰活跃比例 | 10% | 15% |
| 高峰窗口 | 2 小时 | 2 小时 |
| 单用户日均使用次数 | 8 次 | 10 次 |
| 单次平均语音时长 | 20 秒 | 25 秒 |
| 单次平均输出 | 300 token | 400 token |

目标 SLO（Service Level Objective）：

| 指标 | 目标 |
| --- | --- |
| 连接成功率 | 99.9% |
| ASR P95 | 2 秒内完成一句话识别 |
| LLM TTFT P95 | 1.5 秒以内 |
| LLM TPOT P95 | 80ms/token 以内 |
| 核心链路成功率 | 99.5% |

这里要注意，SLO 不是越高越好。对一个创业阶段产品，99.5% 核心链路成功率可能比 99.99% 更现实，因为后者需要很高成本。工程的本质是约束下的选择。

## 3. 先估算高峰并发

三个月目标 DAU 是 30 万，高峰活跃比例 15%，高峰窗口 2 小时，单次使用 25 秒，每个高峰活跃用户在高峰期平均使用 4 次。

高峰期总使用次数：

```text
DAU × 高峰活跃比例 × 高峰期人均使用次数
= 300000 × 15% × 4 = 180000 次
```

高峰窗口是 2 小时，也就是 7200 秒。平均每秒开始的会话数：

```text
180000 ÷ 7200 = 25 次/秒
```

每次语音会话平均持续 25 秒。根据 Little's Law（利特尔法则：并发数 = 到达速率 × 平均处理时间），平均同时进行的语音会话数约为：

```text
平均并发 = 到达速率 × 平均服务时间 = 25 × 25 = 625 个并发会话
```

> Little's Law 是排队论中最基本的公式之一。它的直觉是：如果每秒有 25 个人进入商店，每人逛 25 秒，那么商店里平均有 625 人。这个公式不需要知道到达分布或服务时间分布，只要系统是稳态的就成立。

这只是平均值。考虑峰值放大系数 3（即高峰期内流量不是均匀的，可能有短时间的突发，比如产品推送通知后大量用户同时使用）：

```text
峰值并发语音会话 ≈ 625 × 3 = 1875
```

这说明什么？说明 30 万 DAU 并不意味着 30 万实时语音并发。真正落到 WebSocket 音频链路上的，可能是几千级并发。当然，如果产品有会议转写、直播字幕这种长时间场景，模型就完全不同。

容量评估第一步，就是把用户数翻译成行为数。

## 4. 估算 WebSocket 连接容量

不是所有在线用户都在说话。假设客户端保持 WebSocket 长连接，用于低延迟开始语音。高峰在线用户数按：

```text
高峰在线 = DAU × 高峰活跃比例 × 峰值系数
```

```text
300000 × 15% × 3 = 135000
```

也就是说，网关层可能要承载 13.5 万长连接。

如果每个空闲连接平均占用 20KB 服务端内存，每个活跃语音连接占用 80KB，峰值活跃语音连接 1875：

```text
空闲连接内存 ≈ 135000 × 20KB ≈ 2.7GB
活跃连接内存 ≈ 1875 × 80KB ≈ 150MB
```

内存看起来不高，但这只是连接状态，不包括 TLS、缓冲区、应用对象、日志、运行时开销和安全余量。按 3 倍冗余估计，网关连接状态需要约 9GB 内存。

如果单台网关机器安全承载 3 万长连接，需要：

```text
135000 ÷ 30000 = 4.5
```

至少 5 台。考虑发布、故障和流量不均，生产上可能需要 8 到 10 台。

这里的经验是：不要按理论上限规划。系统应该在一台机器故障时仍能维持服务。

## 5. 理解连接容量的进阶问题

上面的估算基于空闲连接。但真实业务不可能只有空闲连接。下面补充三个进阶问题。

### 空闲连接 vs 活跃连接

空闲连接和活跃连接的资源消耗差距很大。空闲连接只维持 TCP 心跳，内存为主，CPU 几乎为零。活跃连接持续有数据收发，涉及 read/write 系统调用、buffer 拷贝、编解码和应用层业务逻辑。

每连接资源消耗取决于消息频率和消息大小：

| 场景 | 每秒消息数 | 每消息大小 | CPU 相对开销 |
| --- | --- | --- | --- |
| 空闲（心跳） | 0.03 | 几十字节 | 1x（基准） |
| 聊天消息 | 0.1-1 | 100B-1KB | 5x |
| 实时推送（行情等） | 5-20 | 50-500B | 20x |
| 音频流（Typeflux） | 持续流 | 4KB/s | 50x |
| 视频流转发 | 持续流 | 500kbps-2Mbps | 200x |

混合场景下的估算需要把所有连接折算成"CPU 等效连接"：

```text
CPU 等效负载 = 空闲连接数 × 1 + 活跃连接数 × 对应倍数
```

回到 Typeflux 的例子。单台 8 核 16GB 机器，假设内存上限约 15 万空闲连接。场景：12 万空闲连接 + 1875 个音频流活跃连接。

```text
CPU 等效负载 = 120000 × 1 + 1875 × 50 = 213750
```

纯空闲时 CPU 上限约 15 万等效连接。21.3 万等效意味着 CPU 会先于内存成为瓶颈。这就是为什么文档里给"单台 3 万"——它不是内存算出来的数字，而是混合场景下 CPU 和内存双重约束后的安全值。

> 活跃比例每增加 10%，总承载连接数大约下降 30%-50%。容量规划必须同时给出空闲连接数、活跃连接数和活跃类型，否则估算从根上就是错的。

### SSE 的连接容量

如果产品只需要服务端单向推送，SSE（Server-Sent Events）是 WebSocket 之外的另一个选择。SSE 基于 HTTP 长连接，每连接内存约 8-25KB，是 WebSocket 的 60%-80%。原因是少了双向 write buffer 和帧编解码器状态。

但 SSE 有自己独特的限制：

1. 浏览器对同域名 HTTP/1.1 连接数限制 6 个。用 HTTP/2 的多路复用可以缓解，但 Nginx 默认会缓冲 SSE 响应，必须配置 `proxy_buffering off` 才能实时推送。
2. SSE 没有协议级连接状态。断线重连时，客户端需要通过 `Last-Event-ID` header 恢复。服务端必须保留事件序列用于重放，这部分开销容易被忽略。

以同样的 8 核 16GB 机器为例：

| 场景 | SSE 可承载连接数 | WebSocket 可承载连接数 |
| --- | --- | --- |
| 纯空闲 | 60-120 万 | 50-100 万 |
| 轻度推送（每秒几条） | 15-40 万 | 20-30 万 |
| 高频推送（每秒 20+ 条） | 3-10 万 | 5-15 万 |

选型原则：只需要服务端推送（通知、实时数据流、日志流），SSE 更轻量。需要双向通信或二进制传输（音频、视频），用 WebSocket。

### 资源扩展的非线性规律

升级服务器配置后，容量不是简单地等比放大。不同维度的扩展规律完全不同。

**内存**：对连接数的扩展接近线性。8GB 到 16GB，空闲连接数大约翻倍。但有两个陷阱：一是超过 32GB 堆的 GC 暂停时间会明显增加；二是超过 50 万连接后建议开启 HugePages 减少 TLB miss。

```text
8GB → 16GB → 32GB → 64GB
15万 → 30万 → 60万 → 120万（空闲连接，理论值）
```

**CPU**：扩展效率约为核数的 0.7-0.85 次方。4 核到 16 核，看似 4 倍，实际吞吐提升约 2.5-3.2 倍。原因是锁竞争、缓存抖动和上下文切换会吃掉一部分收益。

**带宽**：几乎线性。网卡从 1Gbps 升级到 10Gbps，基本获得对应提升。但单个 TCP 连接受拥塞窗口和 RTT 限制，小包场景下协议头开销也会降低利用率。

**连接数**：最容易踩坑的维度。单机超过 50 万连接后，Linux 内核参数成为主要瓶颈：

1. TCP 缓冲区自动分配。`net.ipv4.tcp_rmem` 的 max 默认是 6MB，内核会根据实际使用动态调整。百万连接 × 6MB = 6TB，直接爆掉内存。生产环境必须把 max 调小到 256KB-1MB。
2. 连接跟踪表（conntrack）上限。
3. 文件描述符上限。
4. backlog 队列大小。

> 把 TCP buffer 调小是百万连接场景下的必要操作。空闲连接为主的场景调到 256KB 足够，活跃音频流场景需要 1-4MB。这个参数不对，其他优化都是白费。

综合参考（纯空闲 WebSocket 连接）：

| 配置 | 理论上限 | 安全上限（60%） | 主要瓶颈 |
| --- | --- | --- | --- |
| 4C 8GB / 1Gbps | 40 万 | 25 万 | 内存 |
| 8C 16GB / 10Gbps | 80 万 | 50 万 | 内存 |
| 16C 32GB / 10Gbps | 160 万 | 100 万 | 内核连接表 + GC |
| 32C 64GB / 25Gbps | 300 万 | 180 万 | 内核 + GC + 调度 |
| 64C 128GB / 100Gbps | 500 万+ | 300 万 | 内核参数 + GC + 进程模型 |

> 记住这些数字不如记住规律：内存线性，CPU 次线性，带宽线性，内核参数是隐形天花板。掌握规律后，面对新配置自己就能推算。

当单机连接数超过 50 万，瓶颈从"资源不够"变成"操作系统和运行时跟不上"：内核 connection tracking 成为瓶颈，网卡中断需要绑核（RSS），应用可能要从多线程切到多进程（SO_REUSEPORT），GC 暂停造成消息堆积，滚动发布时连接迁移变得极其困难。这时候加机器比加配置更有效。

## 6. 估算音频带宽

假设音频上行平均 32kbps，峰值活跃语音会话 1875：

```text
上行带宽 = 1875 × 32kbps = 60000kbps ≈ 60Mbps
```

考虑协议开销、TLS、重传、峰值抖动和下行结果，按 3 倍冗余：

```text
总实时链路带宽预算 ≈ 180Mbps
```

这个数字不算夸张。但如果场景变成 5 万人同时语音，带宽就会变成：

```text
50000 × 32kbps = 1.6Gbps
```

同样的产品，不同使用场景，容量模型完全不同。这就是为什么容量评估不能只看 DAU。

## 7. 估算 ASR 容量

假设每次语音平均 25 秒，高峰每秒开始 75 次会话（前面 25 次/秒乘峰值系数 3）。

由于每个会话持续 25 秒，而每秒有 75 个新会话开始，所以在任意时刻同时进行的音频流数量约为：

```text
并发音频流 = 75 × 25 = 1875 路
```

这个数字的含义是：ASR 系统需要同时处理约 1875 路实时音频流。每一路都需要实时识别，不能有明显延迟。

如果一个 ASR 实例能同时处理 50 路实时音频流，所需实例数：

```text
1875 ÷ 50 = 37.5
```

至少 38 个实例。考虑冗余，可能要 50 个实例。

这里要进一步拆分：

1. ASR 是自建模型还是第三方 API。
2. 是否支持流式识别。
3. 单路音频 CPU/GPU 成本是多少。
4. P95 识别延迟是否满足体验。
5. 第三方 API 是否有限流。

如果使用第三方 ASR，容量问题不消失，只是从 GPU 变成了 API 配额、成本和外部依赖稳定性。

## 8. 估算 LLM token 容量

假设每次请求：

| 项目 | 平均值 |
| --- | --- |
| ASR 输出文本 | 150 token |
| 系统提示词 | 300 token |
| 上下文 | 500 token |
| 输出 | 400 token |

每次 LLM 请求输入 token：

```text
150 + 300 + 500 = 950 token
```

输出 token：

```text
400 token
```

高峰每秒开始 75 次会话。如果每次都调用 LLM：

```text
输入 token/s = 75 × 950 = 71250
输出 token/s = 75 × 400 = 30000
```

这时你会发现，AI 系统的容量不是 QPS，而是 token/s。HTTP 网关看到的是 75 RPS，LLM 层看到的是每秒 7 万多输入 token 和 3 万输出 token。

如果一个推理集群有效输出吞吐是 10000 output tokens/s，需要：

```text
30000 ÷ 10000 = 3 个推理集群单位
```

但还要看 TTFT、排队时间、显存、KV Cache 和模型大小。吞吐够，不代表体验够。

## 9. 估算 Redis 容量

Redis 在这个系统里可能存：

1. WebSocket Session。
2. 用户配额。
3. 临时上下文。
4. 请求幂等状态。
5. 速率限制计数器。

假设高峰在线 13.5 万连接，每个 Session 状态 2KB：

```text
Session 内存 = 135000 × 2KB ≈ 270MB
```

这不大。但如果每次会话临时上下文 50KB，保留 30 分钟，高峰每秒 75 次会话：

```text
30 分钟会话数 = 75 × 1800 = 135000
临时上下文内存 = 135000 × 50KB ≈ 6.75GB
```

再考虑 Redis 对象开销、过期字典、碎片和冗余，可能要按 2 到 3 倍估算：

```text
Redis 预算 ≈ 15GB 到 20GB
```

这里的关键不是算得多精确，而是你会发现：真正吃内存的可能不是 Session，而是临时上下文。没有这个推导，团队很容易只盯着连接数。

Redis 风险：

1. 用户配额 Key 变成热 Key。
2. 临时上下文没有 TTL（Time To Live）。
3. 单个会话上下文过大，形成大 Key。
4. Redis 异常时核心链路无法限流。

方案：

1. 所有临时状态必须有 TTL。
2. 上下文超过阈值存对象存储，Redis 只存引用。
3. 热 Key 做本地缓存或分片。
4. Redis 不可用时，保留最小限流能力。

## 10. 估算 MySQL 和日志容量

假设每次会话写一条会话记录、一条计费记录、三条事件记录。

三个月目标下，日均使用次数：

```text
300000 × 10 = 3000000 次/天
```

每天写入：

```text
会话记录：300 万条
计费记录：300 万条
事件记录：900 万条
```

如果会话记录平均 2KB，计费记录 1KB，事件记录 0.5KB：

```text
会话数据：300万 × 2KB ≈ 6GB/天
计费数据：300万 × 1KB ≈ 3GB/天
事件数据：900万 × 0.5KB ≈ 4.5GB/天
```

业务数据每天约 13.5GB，不含索引和备份。按索引膨胀 1 倍、主从 2 份副本、保留 180 天：

```text
每天裸数据：13.5GB
含索引：13.5GB × 2 = 27GB
含副本：27GB × 2 = 54GB
保留 180 天：54GB × 180 = 9.72TB
```

这说明三个月后，数据治理已经不是小问题。特别是事件记录，可能更适合进入 ClickHouse、Kafka 或对象存储，而不是全部堆进 MySQL。

生产方案：

1. 会话主表按用户或时间分区。
2. 事件流水进入 Kafka，再落分析库。
3. MySQL 只保留核心交易和索引数据。
4. 旧会话内容归档到对象存储。
5. 日志设置采样、字段白名单和保留周期。

## 11. 估算成本

假设第三方模型价格只是示例（实际价格请参考各厂商最新定价，AI API 价格变化很快）：

```text
输入：每百万 token 0.5 美元
输出：每百万 token 2 美元
ASR：每小时音频 0.2 美元
```

> 注意：2024-2025 年 AI API 价格下降很快。GPT-4o-mini 输入约 $0.15/百万 token，Claude 3.5 Haiku 约 $0.25/百万 token。上面的价格是为了说明方法而设定的中间值。做真实评估时，请用你实际使用的模型和厂商的最新价格。

日均 300 万次使用，每次输入 950 token、输出 400 token、音频 25 秒。

每日输入 token：

```text
3000000 × 950 = 28.5 亿 token = 2850 百万 token
```

每日输出 token：

```text
3000000 × 400 = 12 亿 token = 1200 百万 token
```

每日音频小时：

```text
3000000 × 25秒 ÷ 3600秒/小时 ≈ 20833 小时
```

每日成本：

```text
输入成本：2850 百万 token × $0.5/百万 = $1425
输出成本：1200 百万 token × $2/百万 = $2400
ASR 成本：20833 小时 × $0.2/小时 ≈ $4167
合计：约 $7992/天
```

月成本约：

```text
7992 × 30 ≈ 239760 美元/月
```

这个数字会让团队立刻清醒。技术上跑得通，不代表商业上跑得通。

优化方向：

1. 短文本任务用小模型。
2. 常见模板做缓存。
3. 免费用户限制每日次数和上下文长度。
4. 付费用户按权益分配更高质量模型。
5. ASR 静音片段不上传或不计费。
6. 长上下文先摘要再进入 LLM。
7. 异步任务使用低优先级队列和便宜模型。

## 12. 找出第一批瓶颈

根据上面的估算，第一批风险可能是：

| 风险 | 等级 | 原因 |
| --- | --- | --- |
| AI 成本 | 高 | 月成本可能接近 24 万美元 |
| LLM 输出吞吐 | 高 | 高峰输出 3 万 token/s |
| ASR 处理能力 | 高 | 高峰约 1875 路实时音频处理需求 |
| WebSocket 长连接 | 中 | 13.5 万连接需要网关冗余 |
| Redis 临时上下文 | 中 | 上下文保留策略会显著影响内存 |
| MySQL 数据增长 | 中 | 半年接近 10TB 量级 |
| 日志成本 | 中 | 若全量采集链路日志，成本可能失控 |

这就是容量评估的价值。它把“未来可能有风险”变成了具体风险清单。

## 13. 设计扩容和降级方案

### WebSocket

扩容：

1. 网关无状态化。
2. 连接状态外置到 Redis 或专门状态服务。
3. 至少 N+2 冗余。
4. 发布时做连接排水。

降级：

1. 高峰限制新连接。
2. 降低心跳频率。
3. 对异常重连客户端限速。
4. 关闭非核心实时推送。

### ASR

扩容：

1. 按音频流并发扩容。
2. 区分实时 ASR 和离线 ASR。
3. 对静音片段做 VAD（Voice Activity Detection） 过滤。

降级：

1. 免费用户排队。
2. 非核心语言或低优先级场景延迟处理。
3. 第三方 API 异常时切备用供应商。

### LLM

扩容：

1. 增加推理实例或 API 配额。
2. 使用 continuous batching。
3. 做模型路由。

降级：

1. 长上下文裁剪。
2. 小模型兜底。
3. 高峰限制输出长度。
4. 非付费用户排队。

### 数据和日志

扩容：

1. MySQL 分区和归档。
2. 事件数据进入 Kafka 和分析库。
3. 日志采样和冷热分层。

降级：

1. 高峰降低 debug 日志采样率。
2. 暂停非关键事件写入。
3. 分析任务延迟执行。

## 14. 建立监控看板

容量评估必须落到监控上，否则只是文档。

| 模块 | 关键指标 |
| --- | --- |
| 客户端 | 连接成功率、断线率、重连次数、首包时间 |
| 网关 | 活跃连接、连接建立速率、内存、带宽、发送队列 |
| ASR | 活跃音频流、音频秒处理率、P95 延迟、错误率 |
| LLM | TTFT、TPOT、tokens/s、queue time、错误率 |
| Redis | used_memory、命中率、hot key、big key、延迟 |
| MySQL | QPS、慢查询、连接数、Buffer Pool 命中率、主从延迟 |
| Kafka | produce rate、consume rate、lag、恢复时间 |
| 成本 | 单用户日成本、单请求成本、Top 用户、Top 功能 |

告警不要只看资源使用率。更好的告警是“用户体验 + 饱和度”结合。例如：

```text
LLM TTFT P95 > 1.5s 且 queue_time 持续上升
WebSocket 重连率 5 分钟内增长 3 倍
Redis P99 延迟 > 20ms 且 hot key QPS 异常
单小时 token 成本超过过去 7 天均值 2 倍
```

## 15. 压测计划

为了验证上面的估算，要做四组压测。

### 长连接压测

目标：

1. 10 万空闲连接。
2. 2000 活跃音频连接。
3. 模拟断线重连。
4. 模拟滚动发布。

观察：

1. 单连接内存。
2. 网关 CPU。
3. 带宽。
4. 重连风暴。
5. 连接排水效果。

### ASR 压测

目标：

1. 500、1000、2000 路实时音频流。
2. 不同音频长度和静音比例。
3. 第三方 API 限流场景。

观察：

1. P95 识别延迟。
2. 错误率。
3. CPU/GPU 利用率。
4. 单小时成本。

### LLM 压测

目标：

1. 75 RPS LLM 请求。
2. 输入 950 token，输出 400 token。
3. 混合短请求和长上下文请求。

观察：

1. TTFT。
2. TPOT。
3. queue time。
4. tokens/s。
5. 成本。

### 数据链路压测

目标：

1. 每天 300 万会话记录等比例写入。
2. 事件流 900 万条/天等比例写入。
3. 日志采样不同策略。

观察：

1. MySQL 写入延迟。
2. Kafka lag。
3. ClickHouse 或日志系统写入压力。
4. 存储增长。

## 16. 最终容量结论示例

一份容量评估报告最后应该给出明确结论，而不是堆一堆图。

示例：

```text
在 30 万 DAU、15% 高峰活跃、峰值系数 3 的假设下：

1. WebSocket 网关需要承载约 13.5 万长连接，建议部署 8-10 台网关。
2. 高峰活跃语音会话约 1875 路，ASR 需要约 50 个等效处理实例。
3. LLM 高峰输入约 7.1 万 token/s，输出约 3 万 token/s。
4. AI 成本按当前模型估算约 24 万美元/月，是最高优先级风险。
5. Redis 当前主要风险不是 Session，而是临时上下文，必须设置 TTL 和大小限制。
6. MySQL 半年数据可能接近 10TB 量级，事件数据不应全部进入主库。
7. 上线前必须完成长连接、ASR、LLM 和数据链路四组压测。
```

这类结论才有决策价值。它告诉团队先做什么，后做什么，哪些风险不能拖。

## 17. 读者练习

你可以把上面的数字替换成自己项目的数据，重新算一遍：

1. DAU 换成你的真实用户规模。
2. 高峰活跃比例按你的产品日志估算。
3. 单次使用时长按真实埋点统计。
4. token 数按真实请求抽样统计。
5. Redis Value 大小用线上采样统计。
6. MySQL 单条记录大小用表结构估算。
7. 成本按你使用的云厂商或 API 价格替换。

练习的目标不是得到完美答案，而是训练推导能力。

## 18. 这个案例要记住什么

第一，用户规模不是容量压力，用户行为才是。

第二，QPS 不是 AI 系统的核心指标，token/s、TTFT、TPOT 和成本才是。

第三，长连接系统要看连接数、单连接内存、重连和发布排水。

第四，活跃连接和空闲连接的资源消耗差距巨大。一个音频流活跃连接的 CPU 开销相当于 50 个空闲连接。容量规划必须区分空闲比例和活跃类型，否则估算从根上就是错的。

第五，SSE 每连接内存比 WebSocket 低 20%-40%，但只能单向推送且受限于 HTTP/1.1 连接数限制。选择哪种协议，取决于通信方向和传输类型。

第六，资源扩展不是线性的：内存线性，CPU 次线性，带宽线性，内核参数是隐形天花板。超过单机 50 万连接后，瓶颈从"资源不够"变成"操作系统和运行时跟不上"，加机器比加配置更有效。

第七，Redis 真正吃内存的常常不是你以为的 Session，而是临时上下文、大 Value 和没有 TTL 的状态。

第八，MySQL 的风险不只在 QPS，还在数据长期增长、索引、归档和备份。

第九，容量评估必须落到压测、监控、告警、扩容和降级方案上。

这就是从概念到实战的完整链路。只有把链路走完，知识才会从“我听过”变成“我能做”。

> 最后提醒：这个案例中的所有数字都是为了教学而设定的。你的项目数字一定不同。但推导方法是通用的：从用户规模出发，经过行为模型、资源链路、瓶颈分析，最终得到扩容方案和成本模型。掌握这个方法，比记住任何具体数字都重要。
