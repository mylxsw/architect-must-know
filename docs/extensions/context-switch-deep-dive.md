# 扩展阅读：上下文切换深度解析

> 本文是 [预备章：先把容量评估里的专业词讲清楚](../00-glossary-and-mental-models.md) 第 3 节的扩展内容。

## 上下文切换的底层成本

每次切换，操作系统要保存当前线程的寄存器、栈指针、程序计数器，再恢复下一个线程的这些状态。这本身就要消耗几百到几千个 CPU 周期。更隐蔽的成本是 CPU 缓存失效——切换后 L1/L2 缓存里都是上一个线程的数据，新线程一开始几乎全是缓存未命中（Cache Miss），这比切换本身更慢。

## 怎么查上下文切换

```bash
# 看系统总体上下文切换次数
vmstat 1
# 关注 cs 列：每秒上下文切换次数

# 看每个进程的上下文切换
pidstat -w 1
# cswch/s  — 自愿切换（通常是等 IO）
# nvcswch/s — 非自愿切换（通常是被调度器抢走 CPU）
```

## 生产环境中的参考值

| 场景 | 正常范围 | 需要关注 | 需要介入 |
| --- | --- | --- | --- |
| Web API 服务（8 核） | < 5000 次/s | 5000-20000 次/s | > 20000 次/s |
| 数据库服务 | < 10000 次/s | 10000-50000 次/s | > 50000 次/s |
| 高并发网关（8 核） | < 20000 次/s | 20000-50000 次/s | > 50000 次/s |

这些值和业务强相关，不能孤立地看数字。一个 8 核机器跑 200 个线程，每秒几千次切换很正常；但如果只跑了 4 个线程却有几万次切换，就说明有问题。

## 上下文切换高的三种典型原因

### 第一，线程池设得太大

这是最常见的原因。很多人觉得线程多=并发高=性能好，事实恰恰相反。一个 8 核机器开了 200 个线程，操作系统要在 200 个线程之间来回切换，大量 CPU 时间花在了切换上而不是干活。

经验值：
- CPU 密集型任务，线程数 = CPU 核心数
- IO 密集型任务，线程数 = CPU 核心数 × (1 + IO 等待时间/CPU 计算时间)

### 第二，锁竞争激烈

多个线程抢同一把锁时，没抢到的线程会被挂起，等锁释放后再被唤醒。每次挂起和唤醒就是一次上下文切换。锁竞争越激烈，切换越频繁。

`pidstat -w 1` 中如果 `nvcswch/s`（非自愿切换）特别高，多半是锁的问题。解决方法：减少锁的粒度、用无锁数据结构、或者减少共享状态。

### 第三，短任务过多

如果大量任务每个只需要几微秒就完成了，操作系统会不断做"创建→执行→销毁"或"唤醒→执行→挂起"的循环，切换开销占比就非常高。常见于大量短 HTTP 请求、频繁的定时器回调、或者不合理的批处理粒度。解决方法是合并短任务、用批量处理代替逐条处理。

## 排查案例

某 Java 服务上线后延迟翻倍，CPU 使用率却只有 30%。`vmstat 1` 显示 `cs` 列从正常的 3000 飙到了 25000。`pidstat -w 1` 发现这个 Java 进程的 `nvcswch/s` 高达 18000。排查代码发现线程池从 8 被改成了 200，理由是"提高并发"。改回 16（8 核 × 2）后，上下文切换降到 4000，延迟恢复正常。

**教训：CPU 使用率低不代表系统空闲，有可能是 CPU 在忙着切换线程。**
