# 深入理解熔断器（Circuit Breaker）：从原理到工程实践

> “真正成熟的系统，不是永远不出错，而是出错时不会一起崩。”

---

# 一、什么是熔断器？

熔断器（Circuit Breaker）是一种用于保护系统稳定性的机制。

它的核心思想是：

> 当某个下游服务已经明显不稳定时，不要继续疯狂请求它，而是暂时“断开调用”，快速失败，保护调用方和整个系统。

这个概念来源于现实中的电路保险丝。

当电流异常时：

```text
保险丝熔断
↓
切断电路
↓
避免整套系统烧毁
```

而在微服务系统中：

```text
服务 A
  ↓ 调用
服务 B
```

如果服务 B 已经故障、超时、变慢，但服务 A 仍然继续疯狂请求：

```text
服务 B 更慢
↓
服务 A 被拖死
↓
整个链路雪崩
```

于是熔断器会主动切断调用：

```text
服务 A
  ✕
服务 B
```

避免故障扩散。

---

# 二、为什么需要熔断器？

很多开发者刚接触熔断器时，会产生一个疑问：

> “下游服务挂了，不就是请求失败吗？为什么还需要专门做熔断？”

真正的问题在于：

> 故障并不会停留在一个服务内部，而是会沿着调用链向外扩散。

---

## 一个真实的调用链

假设有这样一个接口：

```text
GET /user/profile
```

它内部依赖：

```text
用户基础信息服务
订单服务
会员权益服务
```

正常情况下：

```text
用户请求
↓
用户服务
↓
订单服务
↓
会员服务
↓
返回结果
```

---

## 问题出现了

某一天：

```text
订单服务变慢
```

原本：

```text
100ms 返回
```

现在：

```text
5 秒超时
```

于是：

```text
请求 1 卡住
请求 2 卡住
请求 3 卡住
...
请求 1000 卡住
```

最终：

```text
订单服务慢
↓
用户服务线程被占满
↓
用户服务也开始超时
↓
网关超时
↓
整个系统大量报错
```

这就是：

# 级联故障（Cascading Failure）

而熔断器的核心价值就在于：

> 不让下游故障把整个系统一起拖死。

---

# 三、熔断器的三种状态

熔断器通常有三个状态：

```text
Closed
Open
Half-Open
```

很多人第一次看到会有点困惑。

因为：

```text
Closed 并不是关闭服务
Open 也不是服务恢复
```

这里的“打开”和“关闭”指的是：

```text
电路是否导通
```

---

# 1. Closed：正常状态

Closed 表示：

```text
调用链路正常
```

此时：

```text
服务 A → 服务 B
```

请求可以正常通过。

但熔断器会持续统计：

- 请求数量
- 错误率
- 超时率
- 慢调用比例
- 平均耗时
- P95 / P99

如果发现：

```text
错误率持续升高
```

则进入：

```text
Open 状态
```

---

# 2. Open：熔断打开

Open 状态表示：

```text
禁止继续调用下游
```

此时：

```text
服务 A ✕ 服务 B
```

请求不会真正打到下游。

而是：

- 直接失败
- 返回默认值
- 返回降级数据
- 提示稍后重试

例如：

```json
{
  "message": "订单服务暂时不可用，请稍后再试"
}
```

或者：

```json
{
  "orders": [],
  "notice": "订单信息暂时无法展示"
}
```

---

## 为什么要这样做？

因为继续请求已经没有意义。

如果下游已经：

- 超时
- CPU 打满
- 数据库连接池耗尽
- Redis 阻塞
- 网络异常

继续施压只会让问题更严重。

所以熔断器会：

```text
先停下来
让下游喘口气
```

---

# 3. Half-Open：半开状态

熔断不会永久保持。

经过一段时间后：

```text
Open → Half-Open
```

进入“试探恢复”阶段。

此时：

```text
允许少量请求通过
```

例如：

```text
只允许 10 个请求访问下游
```

如果：

```text
成功率恢复正常
```

则：

```text
Half-Open → Closed
```

重新恢复正常流量。

如果：

```text
仍然大量失败
```

则：

```text
Half-Open → Open
```

继续熔断。

---

# 四、熔断器完整工作流程

完整流程如下：

```text
正常调用
↓
错误率升高
↓
触发熔断
↓
暂停调用下游
↓
等待恢复时间
↓
进入 Half-Open
↓
放少量请求试探
↓
恢复成功 → Closed
恢复失败 → Open
```

---

# 五、熔断器解决的核心问题

熔断器本质上解决的是：

# “故障扩散”

---

## 1. 防止线程池耗尽

如果调用一直卡住：

```text
线程
连接池
协程
Worker
```

都会被占满。

例如：

```text
1000 个请求
每个请求等待 5 秒
```

系统很快就会资源耗尽。

熔断后：

```text
请求快速失败
```

资源会迅速释放。

---

## 2. 防止雪崩效应

没有熔断：

```text
服务 B 慢
↓
服务 A 慢
↓
服务 C 慢
↓
网关慢
↓
整个系统雪崩
```

有熔断：

```text
服务 B 慢
↓
服务 A 熔断 B
↓
服务 A 自己仍然健康
```

---

## 3. 给下游恢复时间

一个已经过载的服务：

```text
越打越慢
越慢越打
```

最终彻底崩溃。

熔断后：

```text
暂停流量
```

让它有机会恢复。

---

## 4. 提升用户体验

没有熔断：

```text
用户等待 10 秒
最后超时失败
```

有熔断：

```text
100ms 返回降级结果
```

体验反而更好。

---

# 六、熔断器与超时的关系

很多人会误以为：

> “有熔断就不需要超时了”

这是错误的。

正确顺序应该是：

```text
先超时
再熔断
```

---

## 为什么？

熔断器需要知道：

```text
哪些请求失败了
```

而超时本身就是一种失败。

如果没有超时：

```text
请求可能永远卡住
```

熔断器甚至来不及统计。

---

## 合理的超时配置

例如：

```text
正常 P99 = 200ms
```

那么超时应该：

```text
500ms ~ 1s
```

而不是：

```text
10 秒
30 秒
```

超时过长：

```text
调用方被拖死
```

超时过短：

```text
正常请求被误杀
```

---

# 七、熔断与重试的关系

这是很多系统里最容易出问题的地方。

---

## 重试的目标

重试是：

```text
失败了，再试一次
```

适合：

- 网络抖动
- 临时连接失败
- 短暂 502
- 瞬时超时

---

## 熔断的目标

熔断是：

```text
失败太多了，先别试了
```

---

# 为什么“无脑重试”很危险？

假设：

```text
原始流量 = 1000 QPS
```

每次失败重试两次：

```text
实际流量 = 3000 QPS
```

如果下游本来就已经崩了：

```text
重试会把它彻底打死
```

---

## 正确组合

工程里通常是：

```text
短超时
+
少量重试
+
熔断保护
```

而不是：

```text
无限等待
+
疯狂重试
```

---

# 八、熔断与限流的区别

很多人会混淆：

- 熔断
- 限流
- 降级

它们其实完全不同。

---

| 机制 | 解决什么问题 |
|---|---|
| 限流 | 流量太大 |
| 熔断 | 下游不健康 |
| 降级 | 核心功能保护 |
| 超时 | 避免无限等待 |
| 重试 | 处理偶发失败 |

---

## 用现实世界理解

```text
限流：
人太多了，别都进来

熔断：
里面着火了，先别进去

降级：
正餐没了，先给简餐

超时：
等太久就不等了

重试：
刚才失败了，再试一次
```

---

# 九、熔断与降级的关系

熔断只是：

```text
停止调用下游
```

但停止之后：

```text
返回什么？
```

这是降级策略决定的。

---

# 场景一：首页推荐服务挂了

降级前：

```text
首页打不开
```

降级后：

```text
返回热门内容
```

---

# 场景二：会员服务挂了

降级前：

```text
整个用户中心崩溃
```

降级后：

```text
仅隐藏会员权益
```

---

# 场景三：支付服务挂了

这里不能乱降级。

错误做法：

```json
{
  "pay_status": "success"
}
```

正确做法：

```json
{
  "pay_status": "unknown",
  "message": "支付服务暂时不可用"
}
```

---

# 十、熔断器常见参数

---

# 1. 统计窗口

例如：

```text
最近 10 秒
最近 30 秒
最近 1 分钟
```

窗口太短：

```text
容易误判
```

窗口太长：

```text
反应太慢
```

---

# 2. 最小请求数

避免：

```text
2 个请求失败 1 个
失败率 = 50%
```

这种误熔断。

通常要求：

```text
至少达到一定请求量
```

才允许熔断。

---

# 3. 失败率阈值

例如：

```text
失败率 > 50%
```

触发熔断。

常见范围：

```text
30% ~ 80%
```

---

# 4. 慢调用比例

有些服务：

```text
不报错
但非常慢
```

这同样危险。

例如：

```text
正常 100ms
现在 3 秒
```

于是可以配置：

```text
超过 1 秒算慢调用
慢调用比例超过 60% 触发熔断
```

---

# 5. 熔断持续时间

例如：

```text
10 秒
30 秒
60 秒
```

太短：

```text
下游还没恢复又被打爆
```

太长：

```text
服务恢复了却迟迟不放量
```

---

# 6. Half-Open 试探请求数

例如：

```text
5 个
10 个
20 个
```

用于检测服务是否恢复。

---

# 十一、一个完整案例

假设你有一个 AI 文本整理服务：

```text
用户语音输入
↓
ASR 转写
↓
LLM 整理文本
↓
返回最终结果
```

其中：

```text
LLM 服务调用第三方 API
```

某一天：

```text
第三方模型服务大量超时
```

如果没有熔断：

```text
请求不断堆积
↓
连接池占满
↓
整个输入法卡死
```

---

## 加入熔断后

配置：

```text
最近 30 秒超时率 > 40%
↓
熔断 20 秒
```

熔断后：

```text
不再调用 LLM
```

而是降级为：

```text
只返回原始转写结果
```

这样：

```text
用户至少还能正常输入
```

而不是整个系统不可用。

# 十二、Go 中的简单实现

---

# 伪代码

```go
func CallWithCircuitBreaker() error {
    if breaker.IsOpen() {
        return ErrCircuitOpen
    }

    err := callDownstream()

    if err != nil {
        breaker.RecordFailure()
        return err
    }

    breaker.RecordSuccess()

    return nil
}
```

---

# 常见 Go 熔断库

常用方案：

- sony/gobreaker
- Sentinel Go
- resilience4go

---

## gobreaker

适合：

```text
轻量项目
简单熔断
```

---

## Sentinel Go

适合：

```text
限流
熔断
热点保护
系统自适应保护
```

一起做。

# 十三、熔断器不是万能的

熔断器只能：

```text
阻止故障扩散
```

但不能解决根因。

真正的问题可能是：

- 慢 SQL
- 索引缺失
- Redis 阻塞
- 网络抖动
- CPU 打满
- 连接池耗尽
- 磁盘 IO 问题

熔断器更像：

```text
安全气囊
```

而不是：

```text
发动机修复器
```

---

# 十四、工程中的完整稳定性体系

真正成熟的系统：

不是只靠熔断。

而是：

```text
限流
+
超时
+
重试
+
熔断
+
降级
+
隔离
+
监控
+
告警
+
压测
+
容量评估
```

共同组成。

---

# 一个典型链路

```text
用户请求
↓
限流
↓
超时
↓
重试
↓
熔断
↓
降级
↓
监控与告警
```

---

# 十五、总结

熔断器的本质是：

> 当下游服务已经明显不健康时，主动停止调用它，让请求快速失败或走降级逻辑，从而保护调用方、防止故障扩散，并给下游恢复的机会。

它并不能让系统永远不出错。

但它能做到：

```text
失败更快
失败更可控
失败不扩散
```

而这，正是现代分布式系统稳定性的核心。
