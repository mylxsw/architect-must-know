# P99 深度解析：为什么平均延迟很好，用户却还是觉得系统很卡？

在高并发系统中，我们经常会看到这样的现象：

> 平均延迟只有 20ms，但用户仍然反馈“系统偶尔很卡”。

这时，如果只看平均值，很容易误判系统状态。真正暴露问题的，往往是另一个指标：

> **P99 延迟。**

P99 不是一个炫技指标，它是判断系统稳定性、用户体验和容量风险的重要信号。

---

# 1. 什么是 P99？

P99，全称是：

> 99th Percentile Latency（99 分位延迟）

它表示：

> 把所有请求耗时从小到大排序后，排在第 99% 位置的那个请求耗时。

换句话说：

```text
P99 = 99% 的请求都不超过这个耗时
```

如果某个接口的 P99 是 800ms，意思就是：

```text
99% 的请求 <= 800ms
1% 的请求 > 800ms
```

注意：

> P99 不是平均值。

---

# 2. 为什么平均值会骗人？

假设：

```text
999 个请求耗时 1ms
1 个请求耗时 10s
```

平均延迟：

```text
≈ 11ms
```

平均值看起来非常健康。

但真实情况是：

```text
有一个用户卡了 10 秒。
```

所以：

```text
平均值描述整体趋势
P99 描述尾部风险
```

---

# 3. 为什么 P99 特别重要？

因为真实用户体验不是平均体验。

用户最容易感知的是：

```text
偶发卡顿
```

而不是：

```text
平均性能
```

尤其是：

- 登录
- 支付
- 搜索
- IM 消息
- API 聚合
- 推荐系统

这些场景里：

> 只要偶发卡顿严重，用户就会认为系统不稳定。

---

# 4. 什么是 Tail Latency（尾延迟）？

P99 属于：

> Tail Latency（尾延迟）

意思是：

```text
请求耗时分布中最慢的那一部分。
```

现代高并发系统真正困难的地方：

> 往往不是平均值，而是尾部失控。

---

# 5. 为什么高并发系统容易出现 P99 问题？

因为请求不仅是在执行代码。

它还会争抢：

- CPU
- 内存
- 锁
- Redis
- MySQL
- RPC
- 网络 IO
- 队列
- GC

系统压力一大：

```text
最慢的一批请求会先变慢
```

于是：

```text
平均值可能还正常
P99 已经开始爆炸
```

---

# 6. P99 升高通常意味着什么？

常见原因：

| 原因 | 说明 |
|---|---|
| 锁竞争 | goroutine 等锁 |
| GC 压力 | 内存分配过多 |
| 下游变慢 | Redis / MySQL / RPC 慢 |
| 队列积压 | worker 消费不过来 |
| goroutine 过多 | 调度成本变高 |
| fan-out 放大 | 一个请求调用多个下游 |
| 重试风暴 | 超时后大量重试 |

---

# 7. 一个典型的 P99 雪崩链路

```text
下游变慢
    ↓
部分请求耗时升高
    ↓
P99 开始恶化
    ↓
调用方超时
    ↓
客户端开始重试
    ↓
流量进一步放大
    ↓
队列积压、锁竞争、连接池耗尽
    ↓
系统雪崩
```

所以：

```text
P99 往往是系统开始失稳的最早信号之一。
```

---

# 8. P99 多少才算合适？

没有统一答案。

真正应该问的是：

```text
用户能接受多久？
系统 SLA 是多少？
```

不同业务，对“慢”的容忍度完全不同。

---

# 9. 不同系统的 P99 参考值

## 普通 API

| P99 | 体验 |
|---|---|
| <100ms | 非常优秀 |
| 100~300ms | 很好 |
| 300~800ms | 可接受 |
| >1s | 用户明显感知卡顿 |
| >3s | 用户怀疑系统坏了 |

---

## 搜索 / 推荐

| P99 | 评价 |
|---|---|
| <300ms | 很好 |
| <500ms | 常见目标 |
| >1s | 用户明显感觉慢 |

---

## Redis

通常要求：

```text
P99 < 1ms
```

---

## MySQL

| P99 | 状态 |
|---|---|
| <10ms | 很优秀 |
| <50ms | 正常 |
| >100ms | 需要关注 |
| >500ms | 很危险 |

---

# 10. fan-out 为什么会放大 P99？

例如：

```text
请求
 ├── 下游 A
 ├── 下游 B
 ├── 下游 C
 └── ...
```

只要其中一个下游慢：

```text
整个请求就慢
```

所以：

> fan-out 越多，碰到慢节点概率越高。

---

# 11. 队列积压如何导致 P99 升高？

worker pool：

```text
请求
 → 队列
 → worker
```

如果：

```text
入队速度 > 消费速度
```

那么：

```text
队列越来越长
```

最终：

```text
总耗时 = 排队时间 + 处理时间
```

可能：

```text
业务处理只需要 10ms
排队却等了 2 秒
```

于是：

```text
P99 爆炸
```

---

# 12. 锁竞争如何导致 P99 升高？

例如：

```go
mu.Lock()

queryDB()
writeLog()

mu.Unlock()
```

锁内做了慢操作。

结果：

```text
大量 goroutine 排队等锁
```

于是：

```text
部分请求 5ms
部分请求 2s
```

---

# 13. GC 如何影响 P99？

如果系统：

- goroutine 太多
- 临时对象太多
- JSON 编解码频繁

那么：

```text
GC 会越来越频繁
```

于是：

```text
部分请求被拖慢
```

---

# 14. 如何排查 P99 升高？

建议顺序：

1. 看 P50 / P90 / P99 / P999
2. 看流量是否变化
3. 看 Redis / MySQL / RPC
4. 看队列长度
5. 看 goroutine 数
6. 看 GC
7. 看锁竞争
8. 看是否存在重试风暴

---

# 15. 如何优化 P99？

## 设置超时

必须设置：

- 请求超时
- RPC 超时
- Redis 超时
- DB 超时

---

## 减少 fan-out

fan-out 越多：

```text
碰到慢节点概率越高
```

---

## 使用缓存和 singleflight

热点 key 过期时：

```text
1000 个请求同时回源 DB
```

singleflight 可以：

```text
只允许 1 个请求回源
```

---

## 控制队列长度

不要使用无限队列。

否则：

```text
延迟会被隐藏在队列里
```

最终：

```text
内存上涨
P99 爆炸
```

---

## 做背压

背压就是：

```text
系统明确告诉上游：
我处理不过来了
```

---

## 熔断和降级

下游持续失败时：

- 熔断
- 快速失败
- 返回 fallback

---

# 16. P99 和容量评估

如果：

```text
QPS 增长 20%
P99 增长 300%
```

说明系统已经接近瓶颈。

健康系统通常：

```text
QPS 增长时
P99 缓慢上升
```

不健康系统通常：

```text
QPS 一过某个点
P99 突然爆炸
```

这个点：

```text
就是系统容量边界
```

---

# 17. 最后总结

```text
P99 是最慢 1% 请求的延迟门槛。
```

```text
平均值很好，不代表用户体验好。
```

```text
P99 升高，通常意味着系统开始出现资源竞争或容量问题。
```

```text
高并发系统真正优化的，往往不是平均延迟，而是尾延迟。
```

真正成熟的系统：

> 不是永远不慢，而是在压力变大时，仍然能以可预期的方式失败。
